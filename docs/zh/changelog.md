### [Unreleased]

#### 新增

- **TOML 也有不建事件树的事件流，并回答第一个生产者留下的空字段** — `pyrs_toml::parse_stream`
  描述的正是 `from_toml` 构建的同一份文档。它刻意不采用 `pyrs-json` 需要的那第二次扫描走查：
  TOML 的表规则（哪个表头可开哪条路径、哪个点号键把哪一层关死、表数组在哪儿追加一个尾巴）在
  `register_header` / `register_kv` 里只写一次，再来一趟就是写两遍。所以事件出自 AST 投影所读的
  同一份中间表示，一个扫描器的裁决对两个读者同时成立（26 个拒绝样本 × 2 个方言，外加 16 份种子
  语料，仍然作为测试被问一遍）。共享词汇在三个字段上拿到第二种格式的答案：`tag` 到底不是 YAML 的
  私有物——date-time 带着 `!timestamp` / `!date` / `!time` 到达，二进制整数带着 `!!int`，与树里存的
  一模一样；`anchor` 继续为空；`style` 只报告 IR 留下的东西，所以字面量 `'…'` 与基本串 `"…"` 长得
  一样，因为"敲的是哪种引号"根本没被存下。两处位置只存在于流里：关闭事件带上它所关闭构造的起始偏移
  （TOML 从不写结束符），而表头的 `[` 在它声明的名字之前——于是一个表的键与它的 `MappingStart` 按
  结构顺序而非字节顺序上报。IR 为每个键、每张表、每条注释付出几个 `usize`；这条代价由指令数门禁
  裁决。— 详情：quality-ledger (dx)、`docs/dev/event-stream.md`。

- **JSON 如今有不建事件树的事件流（`pyrs_json::parse_stream`）** — 共享词汇表等来的就是第二个生产
  者，这次它按 2026-10-13 的裁决成形：自己走一遍 AST 路径已在用的那些扫描器，于是没有任何 sink
  被穿进建树的遍历，那份 +1.5% 的代价谁也不必再付。`pyrs-json` 新增一条 `no_std` 的 `pyrs-event`
  依赖，每个事件都带上树给不出的行与列。九个测试记下第二种格式回答了什么：`anchor` 与 `tag` 恒
  为空、`Alias` 从不出现；`style` 报告标量当初是怎么写的，所以 JSON5 的 `'k'` 键在流里是
  `SingleQuoted`、在中枢里是 plain；非有限字面量原样到达，`.inf` 这层投影只住在 `hub_scalar` 一
  处；32 个畸形文档与 14 份种子语料被两条遍历以同一个 `ParseError` 拒绝，33 个被接受的文档则回放
  成直接解析器建出的那棵树。词汇表仍答不出的那一个问题被点名而非遮掩：`{"a": 1 /* x */, "b": 2}`
  与 `{"a": 1, /* x */ "b": 2}` 产出完全相同的事件，而引擎把这条注释归给了不同的节点——所以回放定
  位的是结构、值与每条注释的文本，不是那个槽位。— 详情：quality-ledger (dw)、
  `docs/dev/event-stream.md`。

- **依赖更新如今按计划到达，并在一条边界内自行合并** — `.github/dependabot.yml` 现已跟踪 `cargo`（工
  作区与 `fuzz/`，各有自己的锁文件）、`uv`（`pyproject.toml` + `uv.lock`）以及 CI actions，每周针对
  `main` 运行。权威仍是那道已经挡住人的门禁：`Test matrix (all legs)` 对该 head 提交报 `success`
  （`skipped` 与 `cancelled` 算作拒绝），判定写在 `scripts/dependency_merge_gate.py`，由
  `.github/workflows/deps-automerge.yml` 执行。只有解析结果的变动会自行合并——`Cargo.lock`、
  `uv.lock`、`prek.toml` 与 action 的 pin；清单、工具链或已提交的类型桩仍留在人手里，因为动它们会伴
  随 bot 无法履行的义务（maturin 的版本锁与随之而来的桩对账规则、解析器大版本那份实测迁移、受支持的
  解释器下限）。所以 PyO3 0.30+ 带着 `python-floor` 标签到达——一个绿色检查不会顺手放弃 Python 3.8。
  全程没有 `--admin`。CI 给 bot 的锁文件豁免（`scripts/check_changelog_coupling.py`）被断言与合并白
  名单指向同一批文件，因为两者一旦漂移，某个更新就会要么红着合不进、要么带着未声明的变更进入主干 —
  详情：quality-ledger (dv)、`CONTRIBUTING.md`。

- **具名形状必须一轮就收敛（`crates/pyrs-yaml-core/tests/settles_in_one_round.rs`）** — 把 fuzz 层的
  “定点”契约拿去问 libFuzzer 找到、`cargo fuzz tmin` 最小化过的形状，而不是只指望有限预算碰运气：注
  释放置规则一旦被改动，现在会按名字弄红一个具名测试，而不是某次偶然的抽样。quality-ledger (ds) 记下
  真正修复之前被实测否掉的两个补救。

- **新增一份记号语料，向每个写入器问它自己的读取器会回答的问题。** — #432 修的缺陷是写入器的裸 token
  判定问得比读取器语法更宽松，而属性层发现它只是因为 20 000 次抽样恰好造出了 `00.`。现在两个表驱动的
  测试就普通标量能携带的每种记号问这个问题——JSON、JSONC、JSON5 共 24 种拼写，TOML 共 18 种——于是下一
  次分歧会点名拼写与方言，而不是作为随机失败出现。实测它确实会咬：把 `json5_integer_part` 退回"数字
  然后一个点"，语料就在 `json5 wrote "[00.]" for the spelling "00."` 处失败。—（详情：quality-ledger
  (dn)）

- **读取器会解析成同一个键的映射，写入器该怎么处理，如今已定案，并且两侧都被钉住。** — #336 问的是：
  一个映射里既有带注释的 `!E null`，又有裸的 `!E null`，`to_yaml` 应该怎么办。写入时折叠这一对曾经实
  现并量过价：五个 `serialize_*` 场景从 +31.481% 到 +33.655%，`parse_small` 一动不动，而门禁只容
  0.50%（`docs/dev/perf.md`）；报告它同样要遍历每个映射的每个键，所以两者都不该放在写入路径上，放在
  那里也没必要。真正解析键的边界，是调用方会走到的那一层：`doc["~"] = 1` 之后再 `doc["null"] = 2` 只
  写出 `~: 2` 一行，重读时只有一个 null 键——先出现的拼写保留，最后写入的值生效
  （`tests/test_edit.py::TestKeyIdentityAcrossSpellings`）。直接用 Rust 构造的 `NodeMap` 仍然写出两
  行，把它们当作重复键拒绝、或返回比树少一项结果的，是读取器；这个形状现在是被钉住的，而不是推断出来
  的（`serializer::the_write_path_keeps_both_lines_of_a_pair_its_reader_resolves_as_one`）。行为没有
  改变 ——新增的只有 `#[cfg(test)]`、文档，以及 `ROADMAP.md` 里那张空的未决事项表。

- **防线矩阵现在度量一条属性究竟断言了多强，而不只是数它有几条。** — `property_functions()` 数出 25
  个 `prop_*` 函数，而页面一直把这个数目当作属性层的覆盖率。`conditional_property_assertions()` 逐个
  读取函数体，找 `if let Some(_) = try_*(..)` 这类守卫，在 25 条里找到 7 条：这些属性对自己的辅助函
  数没返回的样本什么都不说。守卫背后的比率是量出来的，不是争出来的 —— 从 `arb_custom_node()` 抽 4000
  棵树，逐一与它的重读结果比较，结果是 **3423 条被过滤、0 条无法解析** —— 这正是那个把文档的 `? *x`
  键写成 `null: v`（比产生它的树少一项的另一个映射）的写入器，在属性层照跑时全绿的原因（#410 修的是
  写入器；这里记的是为什么没人看见它）。这个盲区以 `property-tier:conditional-assert` 登记，退出条件
  写成可核对的状态，在 `QUALITY_MATRIX.md` 里列出，并在两个方向都钉住：守卫清单为空时洞就消失；页面
  测试把自己那句话钉在实测的两个计数上；而在样本树上，探针只点名被守卫的那个函数 —— 不是*定义*辅助函
  数的文件，用「文本里有没有提到 `try_roundtrip`」来探，会把后者当成覆盖率报出来。

- **Python 运行不再替一个比磁盘源码更旧的二进制说话。** — `python/pyrs_yaml/` 里放着最后一次构建
  留下的那个扩展，所以 `jj edit` 或 `jj rebase` 之后的一次 `pytest` 可能在静默地测另一个分支的引
  擎，而结果看起来就是一个答案：本仓库曾在同一个会话里被这样误导三次，这正是 AGENTS.md 要求移动工
  作副本后重新构建的原因。那条义务此前只是文字。`tests/test_extension_freshness.py` 把已加载的原生
  模块同每一个被编译进它的文件——各 crate 的 `src` 树与 Cargo 清单——作比较，并点名越界者与重建命
  令，而不是留下一场二分。两个决定让它诚实而不聒噪：crate 根在 `#[cfg(test)]` 下声明的模块被排除，
  且这些名字是从那些声明里推导出来的、不是手抄的清单（改一个属性测试再跑 Python 并不需要重建，而清
  单会腐化成什么都没排除）；装在工作副本之外的扩展带着理由被跳过，因为这些源码没有构建它。以突变验
  证：某个 crate 的 `src` 树下多出一个文件就会让这一轮变红并点名自己，删掉它又回到绿。

- **指令门禁现在测事件流路径，于是标量归属的裁定有了可对账的数字。** — 门禁此前从未进入
  `parse_stream`：每个 `parse_*` 场景都构建 AST，各桥接场景也一样。维护者于 2026-10-14 裁定：中性事
  件应当借用其标量文本（`Cow<'a, str>`，只有经转义解码出来的才自有），这是关于分配的主张，所以先有场
  景、再改代码：`stream_medium` 把 `MEDIUM_YAML` 经 `parse_stream` 读两千次并统计事件数，基线为
  275,227,226 条计数指令，而同一文本的 `parse_medium` 是 321,836,091，三次样本逐指令一致（离散
  0.000%）。改动之前先取数，为的是让门禁把收益算出来，而不是由一句话断言出来。`QUALITY_MATRIX.md` 第
  2 节的场景计数随之变成 twenty-two，而今天刚加的正文计数测试先是正确地红了——它如今要防的那类错位，
  恰是这次改动本来会悄悄引入的那种。

- **解析器接受的空显式键，现在是写清且有测试钉住的形状。** — 在被锁定的解析器下，单独的 `?`、后跟一
  个空格的 `?`、后跟一个制表符的 `?` 都是文档而非错误：三者都读成键为 null 标量的映射，而写入器没有
  为*空*显式键准备的标记，所以唯一诚实的输出是 `~: ~`。源文的拼法丢了，数据没丢——`? a\n: b` 也因同样
  的道理紧凑地回到 `a: b\n`——只有离了标记就无法往返的键才保留标记（`? ?` 写出嵌套显式形式
  `?\n  ~: ~\n:\n  ~`）。2026-10-14 裁定：接受而非拒绝，因为判定 YAML 是否合法的是被锁定的解析器，拒
  绝会让本库拒收 `yaml-test-suite` 接受的输入。
  `serializer::tests::a_degenerate_explicit_key_is_accepted_and_re_emits_the_null_pair` 现在断言六个
  此类输入的确切再写出形状，并断言每一个在一轮之后即是不动点；`docs/dev/boundaries.md` 把它记在其他
  显式键族旁边。

- **防线矩阵里的一句计数，现在与它所描述的文件对账。** — `QUALITY_MATRIX.md` 第 2 节写着基线含
  “seventeen”个场景，而 `.ci/ir-baseline.json` 实际有 twenty-one 个——那也正是刷新作业打印的数字，
  也是本仓库自己的测试 docstring 里写的数字。该文件的键早已被钉住，所以读者会以为这条声称是绿的；
  这正是本文件记录的其余缺陷的同一种形状：一项检查因为与它所保证之事毫无关系的原因通过。
  `tests/test_ir_baseline_workflow.py` 现在会数基线里的场景数，并要求第 2 节说出同一个数，所以往
  `benches/ir_gate.rs` 增加场景就必须回头改这句话，否则运行变红。以突变验证：把旧的“seventeen”放回，
  只有这一条测试失败，随后页面按字节还原。同一段还有两处测量声称，被今天的跨主机复核（PR #402 的
  评论）证明不够准确，本文选择改正而非删除：那句“与他处生成的基线最多相差 0.10%”对引擎通道成立，
  而在绑定通道上比所写更宽（`to_python_medium` +0.26%、`to_python_small` +0.19%，相对该通道自身的
  0.076–0.24% 运行内离散），因此现在按通道分别命名；而 `serialize_block_scalars`——曾以名字承载旧
  1.45% 漂移的那个场景——如今在 WSL2 上读作 12,288,634，刷新作业为 12,288,686，两台主机之间相差
  0.0004%。

- **指令数门禁现在能说明一个场景的指令去了哪里。** — `docs/dev/perf.md` 里每一轮优化都始于同一个一次
  性探针：构建未 strip 的 release 基准，在 callgrind 下跑两遍，减去 `--setup-only`，再按函数排名。
  `python scripts/ir_gate.py --profile serialize_medium` 就是把那个探针登记成工具（`--top N` 加宽表
  格，本树并不构建的场景名会被拒绝，并列出它真正构建的那些）。草稿版本踩过的两个坑如今是测试：手工解
  析 callgrind 事件文件，为一场 summary 自身写着 4,506,831 的运行累计出 8,854,254 条指令，且几乎全归
  到 `?`，所以这个工具改为解析 `callgrind_annotate` 的表格；按函数名正则分桶曾把 TOML 的哈希成本报成
  12.46%，因为 `Hasher` 命中的是 `IndexMap<…, BuildHasherDefault<…>>::insert*` 的*类型参数*而不是任
  何摘要计算——于是每一行都按原名打印、绝不归并，`tests/test_ir_profile.py` 断言这一点。门禁的二进制
  是 strip 过的，profile 出来是 `0x000000000006cc10'2` 而非 `write_plain_scalar`，所以该旗标自行保留
  符号；这改变的是产物字节而非被测代码，判定路径也未被触碰——`--profile` 打印后以 0 退出。

- **`no_std` 作业现在会跑每个基础 crate 的宿主测试。** — 该作业为 `thumbv7em-none-eabi` 构建全部
  五个 crate，却只测试 `pyrs-ast` 与 `pyrs-schema`，于是 `default-features = false` 下已有的 112 个
  宿主测试（`pyrs-json` 58 个、`pyrs-toml` 54 个）从未在它们声称支持的路径上跑过；而
  `cargo test --no-default-features -p pyrs-toml` 甚至编译不过：嵌套深度限制用例为了拿到 16 MiB
  栈要起线程，而线程在 `no_std` 下不存在。该用例现在标了 `#[cfg(feature = "std")]`，并把原因与
  `no_std` 侧因此少了什么写在能读到门禁的地方；被测的深度守卫本身是 `alloc` 逻辑，同样的代码在
  `no_std` 下照旧运行。为裸机目标构建只证明能链接，能证明可用的是测试，而现在它们会跑。

- **`pyrs-event`：文档事件词汇表成为独立 crate。** — 这是架构支柱中与 AST 并列的第二个核心抽象。
  `StreamEvent` 及其十一个变体从 `crates/pyrs-yaml-core/src/parser/stream.rs` 移入一个
  `#![no_std]` + `alloc` 的 crate，只依赖 `pyrs-ast`——为的是共享 `ScalarStyle` 与 `Tag`，让事件流与
  由它构建的树不会在 style 或 tag 的含义上产生分歧；引擎仍重新导出这两个名字，所以
  `pyrs_yaml_core::parser::{StreamEvent, StreamEventType}` 依旧可解析，没有任何调用点需要改动。类型
  形状刻意保持不变：它仍是 YAML 的词汇表，因为中性的词表必须针对第二个生产者来设计，而那个生产者还不
  存在。`docs/dev/event-stream.md` 记录了裁定（option B）与让它成立的顺序——JSON 生产者、TOML 生产
  者，再到一个回放属性测试（证明事件能重建成直接解析器所构建的 AST）；本条就是该路线图的第一步，这也
  是 crate 自己的文档要写明哪些字段属于 YAML 语法、而不是宣称 JSON 也有锚点的原因。无行为变更，无新
  依赖，热路径没有增加任何东西：该 crate 的 thumbv7em `no_std` 构建就是保持这层依赖诚实的门禁，它现
  在与其它基础设施 crate 一起跑在 `no_std` 作业里。— (details: quality-ledger (cu))

- **CI 开始在 Python 3.15 上跑套件。** — 正式版已发（devguide 版本表记首次发布于 2026-10-09，状态
  `bugfix`），`3.15` classifier 与 `abi3t` + `abi3t-py315` 特性早已入库，abi3 wheel 也能装在 3.15 上
  ——但从来没有任何作业在它上面跑过套件，于是版本是被宣称而非被验过的。`test` 现在覆盖 3.8-3.15（21
  腿 → 24 腿）；`test-freethreaded` 从单解释器变成两条矩阵：`3.14t` 是装不上已发布 `abi3t` wheel 的
  那个情形，`3.15t` 才是那份 wheel 的开始。README 两份与 `docs/*/installation.md` 同步改了说法，并解
  释为何存在两个自由线程 wheel。3.15 两条腿只能由 CI 首次实测：本机 `uv` 还没提供 3.15 正式版构建。
  三个竞品包（`ryaml`、`yaml-edit`、`yaml-rs`）已限在 3.15 以下：它们没有 3.15 wheel，钉住的 PyO3 又
  拒绝该解释器，于是安装在本套件跑起来之前就死了 —— 这些对比套件现在在 3.15 上跳过。矩阵也不再
  fail-fast：一条腿的失败曾取消了同批 22 条腿，那次运行对其他任何解释器都没能报告。— (details:
  quality-ledger (ci))

- **CI 作业不能再拿着从未下载的语料跑套件。** — `coverage` 作业调 `pytest tests/` 却没有任何

  结束（`to_python_medium` +0.26%、`from_json_medium` −0.00%）。`cargo tree` 确认图中确实是 v2.0.0。

- **两个 mapping 键只在读取器判定的地方才是同一个键。** — 决定两个键在文本上是否冲突的规则
  `keys_collide_in_text` 只比较 scalar 的原始值，其余一概忽略：它把 `!a k:` 与 `!b k:` 当成一个键，
  把 `null:` 与 `'null':` 也当成一个键，可把输出的文本读回来的读取器在这两组里都保留两个条目（tag 是
  行内的一部分；plain 的 `null` 解析为 null 键，加引号的拼写仍是字符串）。这条规则正是写入器折叠即将
  依据的模型，模型过宽就会折掉文档本可容纳的两个条目。现在它会比较 tag，并把 plain 的 null 拼写与加
  引号的双生拼写视为不同的键——解析成布尔或数值的 plain 拼写不豁免，因为读取器在那里确实按文本比较。
  把规则与它所模拟的写入器、读取器一起钉住的那张表从 15 类增加到 18 类。

- **Schema 校验先问 tag，再看文本。** — validate 规则原先只查标量的*拼写*，于是写下 `v: !!str 1` 的
  文档能通过要求 int 的规则，而 loader 把这个值读成字符串 `"1"`，JSON 与 TOML 写入器也把它输出成字符
  串——同一棵 AST，两种含义（#340）。现在遇到标准 tag（`!!str`、`!!int`、`!!bool`、`!!float`、
  `!!null`，以及完整形式 `!<tag:yaml.org,2002:...>`）就按 tag 解析，用的是 spoke 写入器已经在用的语
  法（`standard_tag_kind` 加 `TagKind::resolve`），让这套语法只有一个来源，而不是两处需要保持同步。
  文本无法满足的 tag 会被拒绝而不是改回字符串：`!!int hello` 不再当作字符串通过。规范未定义的 tag
  （`!x 1`）仍走通常的隐式解析，所以它还是数值。`!!int 0b1010` 现在按它声明的整数 10 通过校验，词法
  集就是 loader 已实现的 YAML 1.1 那一套。

- **`CustomNode` 是 144 字节，不再是 208。** — 节点的一半曾是它的 `NodeMeta`：208 字节里的 128 字
  节，五个 `Option` 槽位，而这个尺寸正压在每条读取热路径上——建节点要写它，节点移动要拷它，销毁树时还
  要逐字段检查它（`docs/dev/perf.md` — `memcpy` 占 `from_json_medium` 的 7.88%，拆解占 4.58%）。两步
  作为一个改动落地，因为单独哪一步都不免费。除 `pyrs-ast` 之外的每个 crate 现在都走该类型自己的访问
  器：`comment()`、`set_comment()`、`take_comment()`，anchor、tag 与 source range 也各是同样三个；装
  箱的首行注释用 `decor_mut()`；序列化器原先用模式问「此节点是否不带 comment、anchor、tag」，现在问
  `is_identity_clean()`；逐个点名字段的构造字面量改用 `with_comment()`、`with_tag()`、`scanned()`。
  只有带 anchor 或带 tag 的源码才会填的两个槽位，现在共用一个指针。在性能门禁固定的编译器上配对测量
  （rustc 1.97.1）：`from_json_medium` −4.8%、`serialize_anchors` −4.0%、`parse_inline_merge`
  −3.5%、`parse_medium` −1.5%、`from_toml_medium` +0.7%，没有任何场景越过 0.50% 容差。哪些字段可以搬
  走是这次的结论：把 source range 也装箱——YAML 适配器为*每个*节点都记录它——会让 `parse_medium`
  +5.9%，只为换来 `from_json_medium` −7.4%，所以每节点写入的槽位保持平铺，只有 `{anchor, tag}` 进
  箱。`node_layout_is_part_of_the_hot_path_contract` 钉住元数据的 72 与 64，以及节点在两种构建下的各
  自尺寸——默认 `std` 是 144，节点映射换用自带哈希器的 `no_std` 是 128——因为这个形状的节点是一条测量
  出来的声明，不是实现细节。

- **TOML 二进制整数保住自己的写法。** — `b = 0b1010` 回来时变成了 `b = 10`。这条 spoke 是有意归一化
  的：YAML Core 没有 `0b` 词法，一个不带标签的 plain `0b1010` 到了中枢会被重读为*字符串*，而设计规则
  D1（只保留 YAML Core 也接受的写法）选择丢写法而不是坏掉取值。桥梁学会读标签之后，这个理由就过期了
  （`(bu)`，也是 #340 定下的顺序）：投影现在保留文本、把类型说出来，于是 `from_toml("b = 0b1010")`
  就是中枢标量 `!!int 0b1010` —— 加载器读成 `10`，`to_toml` 写回 `0b1010`，JSON 写入器投影成 `10`。
  一份文档、一个类型，在每个见到它的格式里都一样，TOML 文本一轮就稳定。仍谈不上忠实的还是 TOML 自己
  都拼不出来的东西：`0b1101_0110` 会丢掉分隔符，手工构造的*无标签* `0b1010` 依旧重读为字符串——承载类
  型的是标签。尚未裁定的 `!!binary` 映射不受影响，仍留在那个 issue 上。— (details: quality-ledger
  (cp))

- **覆盖率门禁不再重复跑一整套。** — `coverage` 作业自己建 venv、下载 ubuntu wheel、克隆三个语料，然
  后把 `pytest tests/` 再跑一遍，解释器正是 `test` 已覆盖的 ubuntu/3.12。现在它只是那条腿上多一个
  旗标（`--cov-fail-under=78` 不变），而三条克隆步骤进了共用的 composite action
  (`.github/actions/fetch-corpora`)，由两个跑整套件的作业共用。这个形状恰好能掩盖克隆门禁要抓的漏洞
  —— 什么都有，看起来像什么都没 —— 所以 `tests/test_ci_corpus_gates.py` 现在会跟着局部 `uses:` 走进
  action 自己的步骤，并由新测试钉住两头：解析出的名字必须覆盖每个语料，路径无法解析时必须报出全部
  缺失。把 action 目录改名会让三条测试变红，这正是解析在承重的证据。扇入 `needs:` 去掉了
  `coverage`——拿它与文件里每个作业对比的门禁本就会要求这么改。— (details: quality-ledger (ci))

- **`bytes` 值现在写成它本意的标签。** — 内建插件此前写出 `!binary`，那是一个*本地*标签。标准名是
  `!!binary`，于是本库写出的每个二进制文档对被它借用的那套库都读不出来；而 `{"d": b""}` 写出的是
  `!binary` 后面空无一物，重读时得到 `None` 并在插件里抛 `TypeError`。现在导出走 `!!binary`，空载荷
  也一样，并且已断言 PyYAML 能读我们写出的文本。本地拼写仍注册用于加载：删掉它会让一次拼写修正变成
  已有文档的数据丢失。— (details: quality-ledger (bq))

- **给出 `path` 的校验规则会断言它所指名的节点。** — 改动前先测量：`$.config` 配 `mapping_of: str`
  在 `config` 是标量或序列时通过，`$.port` 配 `type: int` 在 `port` 是映射时通过，`sequence_of: int`
  对 `[[1, 2]]` 也通过。每项检查都写在一个 `if let` 里，只覆盖它能描述的那一种节点，其余节点被直接
  走过 —— 校验器对从未看过的文档回答「合法」。成员同样被断言：嵌套序列不是 `int`。不带路径的规则
  保留原先不同的语义：它无法指名节点，于是按形状筛选自己能描述的节点 —— 无路径的 `type: str` 仍意为
  「所有标量都是字符串」，不管文档其余部分是什么。关于别名节点的规则仍不作判定：别名承载的是名字
  而非形状，而校验器不持有锚点表。— (details: quality-ledger (bm))

- **一个 `[*]` 只指代一个元素，而非整棵子树。** — `$.rows[*]` 过去也会匹配 `$.rows[0].a`，因为匹配器
  只比较前缀与后缀，并要求中间存在某些字符。在规则忽视形状时这一点不可见；一旦规则开始断言形状，被
  命中元素之下的每个嵌套值都成了虚假违规。`$.rows[*].a` 仍可抵达它指名的成员。— (details:
  quality-ledger (bm))

- **一条校验规则只承载一项检查。** — 同时书写 `type` 与 `mapping_of` 的规则只运行最后写入的检查，对
  前者只字不提，因为解析器的每个分支都赋值给同一字段。一条规则出现两项检查现会使 schema 解析失败；
  `required` 与检查正交，仍可与任一项组合。— (details: quality-ledger (bm))

- **严格 JSON 写出遇到非有限浮点数时改为拒绝，而不是换个写法。** — RFC 8259 没有无穷与 NaN 的字面
  量，`to_json` / `to_jsonc` 过去的回答是把中枢文本加引号：`{"b": ".inf"}`，而 `load_json` 会把它当
  字符串交回去。数字在输出时变成了字符串，与一份本就写着该文本的文档无法区分——这与 #312 修的是同一类
  失真，只是方向相反。其余候选是量出来的而非拍板的：`null`（`JSON.stringify` 的答案）是另一个数，裸
  `Infinity` 则是本库严格读取器有意拒绝的文本（此处我们比 CPython 的 `json.loads` 更严）。现在写出会
  抛 `YamlSerializeError`，消息就是稳定原因键 `json-cannot-represent-non-finite`；拥有该词法的
  `to_json5` 仍是无损往返。拒绝也不再伪装成内部故障：新增 `SerializeError::UnsupportedValue` 专门表
  示「该格式装不下这个值」，而键、别名、null 与时间戳此前都被报成 `internal-error`。

- **`pyq validate` 接受 `--input`，并按真正读到的格式处理。** — 它原先硬编码 YAML 解析器，指向
  `pyproject.toml`、`package.json` 这类配置时一律拒绝。现在接受
  `--input auto|yaml|json|jsonc|json5|toml`，并走共享加载器。

- **PR 层 fuzzing 改为阻塞，崩溃无法被合并过去。** — 步骤级的 `continue-on-error` 只是暂时棘轮：
  `main` 上还留着这一层正确标记出的漂移。针对当前树重新验证：四个目标干净重放已提交种子语料
  （5/59/6/5 个种子，nightly-2026-08-15，cargo-fuzz 0.13.2）。 — (details: quality-ledger (aa))

- **文档工具链升到当前稳定版，存根生成器刻意按住不动。** — `zensical` 0.0.56 → 0.0.69、
  `mkdocstrings-python` 1.11.1 → 2.0.9（连带 `mkdocstrings` 1.0.6、`griffelib` 2.2.0，两者都要求
  Python 3.11），而 `maturin` 保持 1.14.1 —— 已提交的 `.pyi` 与漂移检查的调和规则描述的就是它的输
  出。配置里的 14 个 handler 选项逐个对照已安装的 `PythonOptions` 校验过；未被识别的选项构建时静默忽
  略，所以只能由测试检出。— (details: quality-ledger (ba))

- **API 参考现在由库自身的 docstring 与类型存根生成。** —
  `docs/<locale>/api/{reference,yaml-document,yaml-instance,node,merged-view}.md` 都加上了
  `mkdocstrings` 指令，站点上的签名出自代码而不是手抄。四个语言均已构建并核验：`YamlDocument` 下 23
  个签名、`Node` 下 41 个、模块页 48 个，而未写指令的那页仍为 0。`exceptions.md` 保持手写 —— 生成的
  类型存根只声明了四个类，不含任何异常类型。— (details: quality-ledger (be))

#### 修复

- **`version()` 如今报告文档的 `%YAML` 指令，而不是读取器自己的版本** — granit 在
  `Event::DocumentStart` 里就把声明的版本交给解析，而 AST 路径把这个参数丢掉了，于是声明 `1.1`、
  `1.2`、`1.3` 的文档与什么都没声明的文档一律回答 `1.2`。`parser::parse_document` 与
  `parser::parse_all_documents` 现在把指令连同节点一起返回，文档层据此作答：多文档流逐个回答，
  `reparse()` 也会重读。实测：每个声明版本都如实返回自身，未声明的文档仍回答 `1.2`（本读取器自身的
  版本，保留已发布的 `-> str`，不为一个只表示“未设置”的值放宽成 `Optional[str]`），而指令不改变任何
  解析结果——Core 模式下 `%YAML 1.1` 里的 `yes` 仍是字符串。范围只是报告：写入器不重发指令，所以已
  声明文档的 `to_yaml()` 会被读回成未声明；要在输出里带上它就需要 AST 里的文档级槽位，本轮已裁定不
  做。详情：quality-ledger (du)

- **跟在 CR 换行之后的注释不再在第二轮改换主人** — 决定一条行尾注释属于前一个节点还是后一个节点的
  那道行判定，只在两者之间扫 `\n`，于是仅用 `\r` 断行的文档被读成一整行，换行之后的每条注释都往回
  绑到上一个容器上。`!-\r\r\r- :\r\r\r\r- #-` 与它的 `\n` 拼写是同一份文档，fuzz 层早已让 `\n`
  那一份一轮收敛，而这一份需要两次发射：第一次按块式写出该条目，第二次改用紧凑的 `- key: value`
  形式。`line_break_between` 现在两种换行都问——这正是 granit 用来断行的集合，注释扫描器、标量裁剪与
  空白裁剪本就都在用。把这一族的三个形状及各形状的两种拼写做 A/B：每一次发射都逐字节相同，动的只有
  入口处的槽位，从容器的行内注释变成它的前导注释，而那本就是 `\n` 拼写一直给出的位置。实测：633 个
  Rust 测试、20 000 次抽样下的 26 项属性测试；输入已归档为
  `fuzz/seeds/yaml_roundtrip/cr-only-break-note-ownership.seed`，并由
  `settles_in_one_round::a_note_after_a_cr_only_break_annotates_the_item_that_follows` 钉住 —
  详情：quality-ledger (dt)

- **块式正文上方键的注释不再在第二轮搬家** — 写入器把文档自己的注释停在正文最后一行，而 granit 的节
  点区间延伸到*它自己*那行的换行处，于是重读把那条注释报成值的，`write_pair` 对槽位归属的答案随之翻
  转：第一次发射骑在键对行上，第二次就把键的注释抬到键对上方。`write_pair` 现在只在值不可能占用的地
  方问那一行——起始于下一行的标量或空值正文留下行尾槽位空闲——并保留两处实测划出的例外：写在下面的容器
  会让 `<<:  # note` 连同流式正文被读成空的 merge 键，而只含标签的行尚未闭合。实测：两个崩溃形状都在
  一轮内成为定点，632 条 Rust 测试、20 000 例下 26 条属性测试通过，fuzz harness 对两者也是绿的，因此
  它们得以进入 `fuzz/seeds/` ——（详情：quality-ledger (ds)）

- **流式集合里被锚定的节点，不再从别的节点文本里取名字。** — 那个从源码回读 `&name` 的恢复过程会沿整
  行向左扫描，于是一个同时含逗号与引号的普通键（`$,":`）会把它之后的引号状态全部带偏：下一个成员的带
  引号键里的 `#` 被当作注释，该成员自己的锚点被当成注释文本跳过，而写在键*内部*的 `&` 反而成了名字。
  于是第二次转储改写了锚点名，指向它的别名全部悬空。现在搜索被限制在节点自己的窗口内 —— 即构建器在本
  容器里最后消费掉的那个节点的结尾。实测：三次更窄的文本或上下文读法都留下残差，而这一版在 20 000 例
  属性测试层干净通过；单元钉既显示纯文本读法答 `w`，也显示带窗口的读法答 `v`。事件流读取器也从同一个
  单调数值取这条边界：最近一个非空区间的结尾 —— granit 把块容器自己的起点和它的 `End` 都写成空区间，
  那并不指认任何真正结束过的文本，在那里划界会把下一个节点自己的 `&` 隔出去（详情：quality-ledger
  (dr)）

- **TOML 多行数组里的注释归属于它的元素。** — 数组扫描器会跳过 `#` 行并把文本丢掉，所以
  `arr = [⏎ # lead⏎ 1⏎]`、`arr = [⏎ 1 # trail⏎]`，以及元素逗号与下一元素之间的注释，全都会收成一行且
  注释消失。元素现在携带与内联表成员相同的两个批注，含有注释的数组会跨行写出，每条注释都放在读取器回
  报它的位置——实测第二次发射逐字节相同，而没有注释的数组仍然写在一行。最后一个逗号之后的注释没有可归
  属的元素，作为仍然丢失钉住。—（详情：quality-ledger (dq)）

- **内联表成员键行上的注释现在会被写出，不再跳过。** — `to_toml` 只看两个注释槽：键自己的独行列表，
  以及值上的行内注释。中枢把流式成员的注释交到*键*的行内槽上，因为在那里结束键行的注释归键所有，于是
  两个槽都对不上，注释发射出去就丢了：首成员前有独注行的内联表会收成一行且注释不见。不对称就是线索——
  值行上的注释两跳都活着。#428 记下这处丢失并钉住它，而没有声称修好；这一条把它关掉。TOML 没有任何槽
  能把键的行内注释回报回来，所以注释占成员上方自己的那一行，也就是 TOML 读取器回报注释的位置。实测：
  第二次发射逐字节相同，原先钉住丢失的两个 Python 测试现在钉住存活。—（详情：quality-ledger (do)）

- **根层的内联表不再被改写成节标题。** — `to_toml` 把文档根上任何非空映射都归为节，忽略了自家读取器
  刚刚设下的 `flow_style` 位。`p = { a = 1 } # t` 回来时变成 `[p]` 标题加正文，这不是风格选择而是形
  状改变：TOML 要求一个表的普通键排在它的子表标题之前，于是同级键被挤到前面，注释也从键值行挪到了标
  题行。嵌套位置和数组位置的内联表本来就保留形状，所以这种不对称就是线索。如今一轮 TOML 往返即是不动
  点，而原先钉住"提升"的测试——其中两个断言的正是这次修复不再产出的标题文本——改为钉住内联形式。大括号
  里自占一行的注释仍会被中枢丢掉，这个丢失是被钉住的，而不是声称已经修好。— (details: quality-ledger
  (dj))

- **JSON5 写入器不再写出它自己读取器会拒绝的数字拼写。** — 裸 token 判定只问了"数字，然后一个点"，于
  是拼成 `00.` 的普通标量就原样发了出去。JSON5 没有这样的整数部分：它要么是一个单独的 `0`，要么是非
  零数字后接数字，所以本库刚写出的文本会被 `from_json5` 拒绝，而 `prop_json5_output_reparses` 在 20
  000 例里恰好抽到了这个形状。方言装不下的拼写现在和其它非 JSON 记法一样走 schema 解析，保住值、只放
  弃源码形式；合法的 `5.` 仍逐字往返。—（详情：quality-ledger (dm)）

- **容器键自己的注释不分隔两个键，而键身份模型并不知道这一点。** — `KeyIdentity` 把每个非空容器和每
  个带标签标量都归成 `Other`，按节点比较，理由是节点映射会把这样的两个键分开。映射确实分开；*文本*不
  会。属性层抽到了没人能说清的那一对：`? - null` 写两遍，其中一个带着注释，发射出来就是两个一模一样
  的显式键块，重读报 `duplicate key: Sequence { .. }`，于是 `prop_idempotent` 在「输出可再解析」处失
  败。一对一对量下来的结果是：挂在键节点上的注释不分隔任何东西，而键的拼写（`[a]` 对 `- a`）与内容会
  分隔——恰如读取器比较它们的方式。模型现在把这些写成类别（`Tagged { text, tag, style }`、
  `Sequence { items, flow, tag }`、`Mapping { pairs, flow, tag }`，等值与哈希为手写），`Other` 收缩
  到上述类别没有覆盖的部分；生成器据此拒绝它的读取器会拒绝的键对——判定与生成用同一个表达式，因为「读
  取器解析成什么」和「调用方能构造出什么」不能是两套模型。钉测表新增五类，每一类两侧都带读取器的实测
  结果。
  —（详情：quality-ledger (dl)）

- **普通键文本里的方括号不再打开引用区。** — 这是 #421、#425 一族的第三个成员。属性层 20 000 例的一
  次抽样给出 `!!t /[": &Ilr |-8  # &m^fake`，键自己的文本里就带一个 `[`。#425 允许引号在流指示符之后
  作为节点起始，于是那个 `"` 打开了一个永不闭合的区域，真正的 `#` 被判成区域内容，写在注释里的 `&`
  反倒成了节点的名字—— 锚点被改名，指向它的别名全部悬空。现在指示符本身必须开启一个 token，这正是流
  集合与恰好带方括号的普通键的分界；成员之间的逗号则无论前面是什么都开启下一个节点，因为
  `[a, " #", &x ~]` 里的 `#` 被引号包住，它后面的锚点必须站得住。— (details: quality-ledger (dk))

- **不打开任何节点的引号藏不住注释。** — #421 教会锚点名扫描忽略引号里的 `#`，但它让空白之后的任何引
  号都算开启了这样一个区域。于是普通键文本自己带的撇号（`a '`）开启了一段幻影字符串，它的闭合落在注
  释内部，真正的注释起始反而没被看见，写在注释里的那个 `&` 就成了节点的锚点名：值回来时是
  `&*~=9VjQq=8`，那是别名的写法，任何锚点都装不下。带引号的节点始于一个词元，所以扫描现在改问引号之
  前是哪个词元——是边界，还是节点所跟随的锚点或标签属性。

- **嵌套容器的注释写在自己那行之上，绝不写在正文之下。** — 写器给容器行内注释留的最后退路，是在该容
  器的缩进处补一条独立注释行；而读取器只把一个节点跨度到它*自己*那行的换行符：写在比列 0 更深的地
  方，注释就落在跨度之外，被记到紧随其后的那一行上，第二次发射便把它丢了。往返属性层先收缩到一个
  `- - |-` 下面带着正文的形状，随后在没有块标量时也收到同样的丢失，所以这条规则按缩进表述。列 0 保留
  旧写法——那里注释行就是文档末尾，读取器确实会把注释报回容器。

- **键的注释只贴自己那一配对行，绝不贴进嵌套表头。** — #419 教会写器在值是块标量时把键的注释放到
  表头行上，但它查的位置是「最后写下的块表头」，而在文档里那可以是任何地方。值的容器会在那之后写下
  自己的配对，于是外层键的注释落进了内层配对的表头行：`A: >` + `# a` + `-5` 把表头劈成两半、把两条
  注释合成一条，剩下的正文再没有块声明它 —— 输出文本根本不再可解析。是属性层 2 万例的那一轮找到它的
  （`misplaced bracket`）；如今只有表头行与配对行同一行时才用这个槽位。

- **锚点在一个看似注释的 `#` 前保住自己的名字。** — 读取器从解析器指向的节点往左扫描来恢复锚点的
  显示名，行内注释起始 `#` 之后的每个 `&` 都会被跳过。那道守卫把*引号内*的 `#` 也当成注释，依据是
  「同一行里锚点不会跟在带引号的值后面」—— 块配对确实如此，flow 集合里却不是：
  `{a: &x "x # y", b: &y 2}` 把 `b` 读成了 `&x`，于是两个节点共用一个名字，每个 `*y` 引用都指向空。
  扫描如今会跟踪引号 —— 单引号内的 `''`、双引号内的反斜杠，且只在标量能够开始的位置把引号算数，
  因为 granit 的名字语法允许锚点名本身就带一个 `"`。它所属的那一类来自往返层的测量：抽 4000 棵树里
  有 11 处锚点名发生变化，而这就是归约器缩到的形状。

- **紧凑式 `- key: value` 如今会打印第一个键自己的注释。** — `write_mapping_pair` 会把简单键的前导注
  释写在配对上方，紧凑序列循环照抄了这条规则，唯独漏了第一对 —— 第一对与短横共用一行，本身没有可写的
  一行：`- null: " "` 回来时键上的 `# 2` 已经不见了。如今这些注释写在条目那行的上面。发现方式是把属
  性层残余的注释丢失归约到「仍会丢注释的最小树」；这一类补上后，抽 4000 棵树实测的丢失是每 4000 棵一
  棵 —— 块值上的独立注释，记在台账里而不是被吸收掉。

- **块映射键的行内注释不再因为值占了行末槽位而丢失。** — `key: value  # one` 只有一个行末槽位，
  键与值都要它时，写器把槽位给值、键的注释就此消失：`? a # kn` + `: b # vv` 写出的是 `a: b  # vv`。
  如今这条注释改占一个换行，与 flow 路径一直以来的做法相同。这个位置是先实测再选定的：只要不是映射
  的第一项，直接写在某个键上方的注释行就归**那个键**所有 —— `a: 1` + `# K` + `b: 2  # V` 读回时
  `K` 仍在 `b` 上，注释保住了它的主人；只有第一项会把键的注释上交给外层容器，两种情形文本都还在。
  紧凑式 `- a: 1` 与块标量正文原本有同一个缺口，一并补上。抽 4000 棵树里，从未进入输出文本的注释
  由 907 处降到 257 处，其中键位那一类由 707 处降到 34 处。

- **块标量在表头换行或带上注释后不再丢值。** — 缩进指示符是从*父节点*数列的：PyYAML、ruamel
  与本引擎自己的读取器都这么认（在 `a: |2`、`- |2`、`? k` 几种拼法上实测）。写器却从表头所在行
  数列 —— 值被一条前导注释挤到自己一行之前，两者本来就是同一列 —— 于是正文比表头上写的数字深
  两列，任何读取器都把那两列当作内容：值 `" "` 读回成 `"   "`。第二个形状同属一类：简单键的行内
  注释在 `:` 之前没有位置，写器把它贴在配对行末尾，而块值的行末是*正文*最后一行，那里的 `#`
  是内容 —— 带注释的键配一个 `|-` 会写出 `abc  # n`，读回 `"abc  # n"`，多出树里从未有的三个
  字节。两处都由属性层按节点位置给失配归因挖出：抽 4000 棵树里 434 棵带着这一位移，两个修复
  之后一棵也没有。注释现在贴表头行，读取器会把它交给值。

- **块标量不再凭空补上它表头所表示的行尾换行。** — `key: |-\n  line1\n  line2\n` 读出来是
  `line1\nline2`；跟这个节点要 clip（`set_chomping("clip")`，或交给写器一个 `Clip` 但值不以换行结尾
  的树），它写出的是 `|` —— 而 `|` *表示*一个行尾换行，于是文本比产生它的树多回一个字节。
  `effective_chomping` 如今只纠正没有哪种表头能拼出的那类声明：值不带行尾换行时，`Clip`/`Keep` 改为
  `Strip`；`Strip` 声明照旧保留，因为 `-` 可表达，而选它正是调用方要的编辑
  （`test_set_chomping_strip` 钉住那一个方向）。来源是属性层的失配分类学：抽 4000 棵树里 255 棵是这
  一类，且形状全同 —— 长度 N 的值读回 N+1。钉死的块标量样本的值都以 `\n` 结尾，所以字节级断言换过五
  代也没碰到它；那五处现在写 `|-`/`|-4`，那才是正文实际带的拼法。

- **随包发布的类型契约开始描述运行时那个类。** — `python/pyrs_yaml/pyrs_yaml.pyi` 由扩展生成，而
  `python/pyrs_yaml/__init__.py` 是在导入之后才把 `node`、`find`、`walk`、`scalars`、`merged`、
  `set`、`set_many`、`insert`、`append`、`delete`、`rename`、`sort_keys` 挂到 `YamlDocument` 上，这
  十二个成员因此只活在运行时，检查器要读的那份文件里一个都没有：用 mypy 2.4.0 对着已安装的包实测，
  `document.node` 指的是一个类型存根从未声明的成员。第一块多米诺骨牌压在上一层 —— `parse` 与
  `parse_file` 的公共包装被标注成 `-> Any`，`parse_all_docs` 被标注成 `list[Any]`，把绑定自己写明的
  `YamlDocument` 抹掉了，于是检查器从用户最先调用的入口根本走不到那个类。两半各在它所属处修好：包装
  给出诚实的返回类型，另加一条已声明的调和规则 —— 从编译模块的类上读出成员（参数、默认值与 docstring
  一律照抄）写进类型存根，并按 `EXPECTED_ATTACHED_MEMBERS` 计数，让成员的增减成为一次复核，而不是一
  份悄悄变窄的契约。包自己没有标注的成员会让推导停下来，而不是被写成 `Any`；类型检查门禁如今也会把存
  根自身 import 的同级模块一起放进临时包 —— 只装一个 `.pyi` 的临时包此前会把每个 wheel 都含有的文件
  报成 `import-not-found`。`Node` 与 `MergedView` 从来不在这个洞里，它们是 `py.typed` 包自带的
  Python 模块，检查器本就读其源码 —— 待办表在这一处把缺口说大了。检查器与对象如今对这调用意见一致：
  `document.node("a")` 在检查时报「参数过多」，在运行时也一如往常抛 `TypeError`。删掉那十二条声明，
  `test_the_stub_declares_every_public_member_of_a_class_it_names` 会点名全部十二项而变红。

- **流式集合成员的注释会被写出去，而不是丢掉。** — `{A: x  # V}` 读进来的树里留着 `V`，再产出时却是
  `{A: x}`：读者给每个流式成员只留一个槽位，也就是挂在它行尾的那条注释，而流式写入器一个都没用上 ——
  注释只活在内存里，下一个读文本的人再也看不见它。在 4020 棵抽样树上量过：其中 1650 棵最先的差异就落
  在注释上。现在注释写在打开它的那个括号再深一列处（`- {A: x  # V` 换行 `}`），因为 `#` 结束了本
  行，而 `- {` 或 `k: {` 之下第 0 列的值会被读成「流式续行缩进错误」—— 八种拼法逐一实测可读，且都是
  自己的不动点。一个成员带两条注释时没有第二个槽位，于是该容器转块式，每条注释各保一行（维护者裁定，
  2026-10-14）。同一处还回答了第二个问题：流式映射里把映射或序列当键时，回来会变成键 `null` —— 与
  PR #410 修掉的别名键丢失是同胞 —— 如今保留 `?` 标记（`{? {}: v}`），ruamel 读它得到一个空映射键。
  注释文本按读者交还的样子写出（两端空白去掉，无话可说的注释哪里都不写），所以第一次产出就是规范形，
  而不是第二趟才安定。

- **作为映射键的别名会被写回，而不是丢成 `null`。** — 在 `a: &x [1, 2]` 加上一个 `? *x` 键时，写入器
  重新产出的是 `null: v`：`write_mapping_pair` 里的复杂键判定只覆盖映射与序列节点，别名于是落到普通
  键路径上、什么也没解析出来 —— 那是另一个映射，比产生它的树少一项。紧凑的 `*x: v` 并不是可选写法，
  而待办表里恰恰在这一点上写错了：本引擎的读取器拒绝它（`simple key expected ':'`），所以写入器带上
  `?` 标记 —— 块式风格里写在标记行（`? *x`），流式映射里写在大括号内（`{? *x : v}`），而锁文件解析出
  的每一个 ruamel.yaml 版本都同样读得进这两种写法：3.8 那几条腿是 0.18.16，其余是 0.19.1，只有后者会
  对紧凑写法抛错。关于扫描器的那句一概而论让 3.8 的三条腿变红，改成把两个版本都实测过。为什么各层都
  没看见这次丢失：AST 策略从不构造以别名为键的映射，而往返属性对不上的树是被*过滤掉*而不是判失败，于
  是变了形的文档被丢弃而非上报。`pbt::tests::prop_alias_key_survives_the_round_trip` 现在会构造这个
  形状并无条件断言；把写入器的判定改回去，只有这条属性和块式的单元测试失败 —— 344 条里 2 条，其余不
  动 —— 而 Python 层逐字节钉住产出，也钉住 ruamel 能读它。

- **不可哈希键的拒绝信息，不再指向两条同样会拒绝它的路径。** — 跟着复杂键投影一起进来的那条消息，让
  读者用 `to_json()` 或 `to_toml()` 去投影文档。在本树上实测，复杂键在两处都报错：JSON 写入器答
  `json-object-key`，TOML 那个答 `toml-keys-must-be-scalars`。所以这条建议把人引向另外两个错误，而不
  是出口，而且它同函数自己的注释相矛盾——那注释说消息只点名形状、就此停下。文本如今写明唯一走得通的路
  （用 `parse()` 读取，把键留在 AST 上），并直说其他投影同样拒绝这个键。`tests/test_parse.py` 把两半
  都钉住，重新塞回一条推荐就会失败。哪些输入会抛异常并未改变，而这句错话从未进入任何发布版本。

- **复杂映射键不再以节点的 Rust 调试文本抵达 Python。** — `safe_load("? ?")` 交回的字典，其键是
  `'Mapping { pairs: {Scalar { value: "~"…'`；`? [1, 2]` 也是同样形状的字符串，因为转换宁可造一个调
  试格式，也不肯丢掉这一对。两种选择都不对：丢掉会少掉文档写下的一项，而编造的键是普通字符串，会被再
  次写出 —— 损坏于是以“不动点”的样子进入下一篇文档。2026-10-14 对参考库实测后按形状分开处理：序列键
  转为 tuple（`{(1, 2): 'v'}`，与 ruamel.yaml 给出的完全一致；PyYAML 会拒绝它，这是朝“保住数据的那
  家”记录的有意分歧）；嵌套容器由 Python 自身的 `unhashable type: 'list'` 拒绝，因为只有外层会被转
  换；映射键与别名键由本引擎拒绝，并在消息里点明形状。标量键 —— 包括构造器返回不可哈希值的带 tag 键
  —— 保留原有文本回退：那条路径没有坏，这次也未改动。十一条测试覆盖它，并做突变检查：换回旧代码时这
  十一条全红，而这两个文件里其余 173 条不动。`ROADMAP.md` 记下这次发现而没有粉饰的另一半：别名位于键
  位仍被写成 `null: v`，那是序列化器的缺口，不是投影问题。

- **路径编辑找的是读取器所指的键，不是它见到的拼写。** — 对读取器来说 `~`、`NULL` 与 `Null` 节点是同
  一把 mapping 键，而带不同 tag 的两个标量是两把键；可编辑层只比键的*文本*。于是在含 `~: 2` 的文档里
  设置 `null` 会漏掉那个条目、追加第二行，交回的文本正是自家读取器以 `duplicate key: null` 拒绝的那
  种（#336）。现在路径段会解析到读取器为这把键解析出的东西，那次编辑就成了同一行的 `~: 3`；该保持区
  分的仍然区分：加引号的 `'null'` 键仍是独立条目，`yes` 也不是 null。

- **CLI 测试工装不再因为一次拒绝关掉 stdin 而 panic。** — `run_with_stdin` 写子进程的 stdin 时对所有
  错误都 panic，可 CLI 若拒绝自己的参数，会在读取之前就退出，于是这次写与已关闭的管道相撞：同一条调
  用在本机通过，却把 `msrv-check` 写红，报 `write stdin: Os { code: 32, kind: BrokenPipe }`。工装现
  在先取过句柄、容忍写失败，并在等待之前把它关掉——这也正是真要去读的子进程需要的（EOF，而不是一直挂
  着的管道）。这不算把问题抹平：退出码与 stderr 上的断言仍然决定测试结果。
  `a_refusal_closes_stdin_before_the_harness_finishes_writing` 喂进 240 KB（超过一个管道缓冲）把这个
  交织变成确定性的；对着旧工装它每次都红（`Os { code: 109, kind: BrokenPipe }`），修好后 48 条 CLI
  测试全过。— (details: quality-ledger (cs))

- **重读紧凑 JSONC/JSON5 不再抹掉同一行的多条注释。** — 一个节点若被两条以上同行注释引导，此前只留下
  最后一条：读侧把同行注释放进单个 inline 槽，后来者覆盖前者。紧凑 writer 正是这样写一个节点的注释，
  于是库自己产出的文本重读时会丢注释（`{/* note 0 *//* note 1 */`），第二轮结果也不同。这样的连续注
  释现在整体进入 leading 列表，它按源序容纳任意多条；单独一条同行注释仍独占 inline 槽，人类书写的拼
  法不变。代价是一处细节，如实记下：同一行有多条时 writer 已无法分辨哪条是同行注释，所以 pretty 形态
  会把它们各自成行。没有任何注释被丢弃，也没有任何东西在两轮之间移动。— (details: quality-ledger
  (ch))

- **`to_jsonc` 与 `to_json5` 不再丢文档里带着的注释。** — JSONC 注释能站的十一个位置里，有三个
  `to_yaml` 会写出、两个方言 writer 却丢掉：pair 值节点上的独立注释、其键上的行尾注释，以及末成员
  之后的注释。映射循环只读了四个槽位中的两个，而输出仍是合法 JSONC —— 这正是丢失无人察觉的原因。
  pretty 路由现在把缺的两处打在 pair 上方；compact 路由改用 `/* … */`，因为 flow 容器里单独成行的
  `//` 会被重读成“跟在它所引导的成员后面”，两条还会交换位置 —— writer 的固定点不容许这种移动。
  文本含 `*/` 的注释在 compact 形态里被中和，以免提前闭合自己。— (details: quality-ledger (cg))

- **超出 64 位的 Python 整数不再被转储器写成浮点。** — `safe_dump({"k": 10 ** 30})` 此前写出
  `k: 1000000000000000000000000000000.0`：本为“协议可转换类型”准备的兜底调用了 `extract::<f64>()`，
  而它对任何 `PyLong` 都会成功，于是调用方给的数被换成最近双精度的十进制拼法。键同样被改写，两个宽
  键因此可能在重读时碰撞。两条写入路由现在都对超出 `i64` 的 `int` 发出 `str()` 的逐位数字；文本不是
  数字的 `int` 子类保持原路由。读取侧的 `i64` 上限不变，所以 `safe_load` 把这些数字返回为字符串 ——
  值保住了，类型没有。— (details: quality-ledger (cf))

- **JSON5 不再接受它自己语法禁止的前导零。** — `[012]`、`[-01]`、`[-012]` 此前能作
  为 JSON5 数字解析，因为解析器里写着一条明文放宽“JSON5 容忍前导零”，而且有用例把
  这条声明钉成预期行为。但 JSON5 的 `DecimalIntegerLiteral` 就是 `0 | NonZeroDigit
  DigitalDigits?`，与 RFC 8259 同一生产式，`pyjson5` 三例全拒。放宽已删除、用例已反向
  钉住。三条原本只在本地量过的方言规则现在进了断言：合法 JSON 必须被两个 superset 接受；
  参考实现拒绝的非法文档我们也必须拒绝；JSONC 只能在注释标记存在处偏离严格 JSON。JSON5
  的语料放宽从 30 降到 27，包含性仍零违反。— (details: quality-ledger (ce))

- **`to_toml` 写出的文本本身不是合法 TOML。** — 两处转义缺陷，都由新加的 toml-test 编码向
  语料发现：DEL（U+007F）在 basic string 里被原样发出（`k = "x<DEL>y"`，`tomllib` 与本
  crate 自己的解析器都拒绝它）；连续换行时只转义第一个，其余按真换行写进单行字符串。现在
  一串里的每个换行都转义，DEL 在两种字符串形式里与 C0 码同列。发现它的那个门禁拿 `tomllib`
  判定我们的输出，而不是拿我们自己的读取器。— (details: quality-ledger (ca))

- **空的带标签值不再写出文档里根本没有的空格。** — `write_anchor_tag` 会在标签后补一个
  分隔空格，好让标签 token 在其内容之前结束；而空的 plain scalar 从不带内容，所以
  `n: !!null` 会重写成 `n: !!null `，`n: !!null  # c` 更在注释前写出三个空格。这次去掉发生在
  `write_scalar`：那里空值、样式与标签都在作用域内，且就在记录 `pending_tag_insert_at` 前
  一字节，所以会被后续注释闭合的行仍写作 `!- ~`，没有注释换主人。此前两条路已被实测否定：
  在终止处 pop 会让 pending 机制取到的索引 panic，抑制键分隔符则把注释移出它的主人所在行。
  关闭 #339。— (details: quality-ledger (bz))

- **标准标签现在在每个格式里都决定类型，不再只在加载时生效。** — #335 让加载器开始尊重 `!!str` /
  `!!int` / `!!float` / `!!bool`，但通往 JSON、JSONC、JSON5 与 TOML 的桥梁仍然只解析标量*文本*、丢掉
  `meta.tag`，于是一份文档有了两个答案：`v: !!str 1.20` 加载为字符串 `"1.20"`，而 `to_json` 却发出
  `1.2`——类型变了，作者特意写下的末尾零也没了。规则现在只存在一处：`pyrs-schema`
  （`standard_tag_kind` / `TagKind::resolve`，用 YAML 1.1 词法，`!!x` 简写与完整形式
  `!<tag:yaml.org,2002:x>` 都认），JSON 写入器、TOML 写入器与 CLI 的类型化比较统一来问它。文本凑不上
  标签所宣称的类型时报错（`*-tag-text-mismatch`），而不是悄悄当字符串。本地标签（`!int`）、未知的
  `!!` 后缀、尚未裁定的 `!!binary` 映射均维持原状，并已钉住。代价在施测镜像上量出并被接受：现在会先
  问一次标签的键值循环让 `to_json_medium` 花 +1.12%、`to_jsonc_medium` +1.03%、`to_json5_medium`
  +0.82%，而 `to_toml_medium` 动 -0.07%，其余没有一项越过那条线。`.ci/ir-baseline.json` 在本 pull
  request 内重新生成，并把这三个场景点名给漂移守卫；同一次刷新顺带把 `from_json_medium` 收
  紧 -0.46%、`from_jsonc_medium` 收紧 -0.42%，这并不是我们要求的。— (details: quality-ledger (bu))

- **编辑不再用旧值的标签覆写新值的类型。** — `doc.set("$.d", b"hi")` 发出的是
  `d: aGk=`。这次赋值本会构造一个携带 `!!binary` 的标量，但拼接式编辑器的元数据继承从被
  替换的节点拿走了 `comment`、`anchor` *以及* `tag`，于是调用方指定的类型被那个写下“替换的
  标量保留其注释/锚点/标签”的函数亲手删掉了。规则现在按字段分开：注记与锚点名归文档（同一
  文档里的别名仍必须能解析），类型归值本身。带入的值没有标签时保留作者的写法——
  `port: !!int 8080` 被设为 `9090` 仍读作 `!!int`——映射、序列与空值同样如此，因为它们共享
  同一个缺陷。— (details: quality-ledger (bt))

- **null 的两种写法是同一个键；生成器此前会把两个都交给写入器。** — 两万用例的属性层为
  `!E null: A  # 0` 与 `!E null: a` 报告了 `DuplicateKey("null")`。`Null` 节点本身不携带文本，
  写入器为它写出 `null` 这个词，于是这两行重读后是同一个键。`keys_collide_in_text`——那条保证
  生成的映射可被表示的规则——只看标量文本与空容器，从未看过 null。如今它覆盖读者会解析为 null
  的每一种写法，并把真正能区分两个此类键的东西（标签；以及仅在已有标签时才生效的锚点）与什么都
  区分不了的东西（随整行走的注释，并不随键走）分开。规则、写入器与读者被双向钉住：规则判为不同的
  键对，其文本严格重读后必须仍占两个条目；规则判为相同的键对，必须被拒绝或被折叠。—
  (details: quality-ledger (br))

- **内联 dict schema 不再丢掉序列化器不认识的那部分。** — `safe_load(schema={...})` 与
  `YAML(schema={...})` 靠 `_schema_to_yaml` 把 Python dict 转成引擎解析的 schema 文本。它逐行拼接文
  本，只认 `extends` 与 `rules`，所以带了 `validate` 段的 dict 会被静默删掉那些规则注册进去——而无规
  则的 schema 接受一切文档，于是没有任何东西报告此事。它那唯一一条手写的引号规则（值含撇号就用双引
  号）对同时含两种引号的正则会产生内部未转义的双引号标量：
  `invalid trailing content after double-quoted scalar`。现在整个 dict 交给 `from_dict` 写——就是其他
  地方用来保障往返保真的那个序列化器——于是每个键都能活下来，任意模式文本也能按原样被正确引用。—
  (details: quality-ledger (bp))

- **两个公开函数不接受自家桩声称它们接受的关键词。** — `pyrs_yaml.read_markdown(path="note.md")` 抛
  `TypeError`，而已提交的桩把该参数声明为 `path`：`__init__.py` 里的 Python 包装层把它改成了
  `content`，而这个函数打开的是它收到的文件；于是名字引导出的调用 `read_markdown(content=text)` 反而
  在文件系统上失败。现在包装层叫 `path`，`read_markdown_str` 保留 `content`，两者均写下区别。同一种
  漂移反方向发生在 `validate_against_schema`：桩里叫 `schema_yaml`，而调用方一直用 `schema`；现在原
  生参数已重命名，桩沿声明路由重新生成。— (details: quality-ledger (bo))

- **三个语言的 API 页面写出了库中不曾存在的参数。** — zh/ja/ko 参考页写了
  `register_schema(name, schema: str | dict)` 与 `register_type(tag, type_handler, priority)`，而两
  层声明都是 `register_schema(name, schema_yaml: str)` 与 `register_type(name, handler)`——而且
  `priority=` 会招来 `TypeError`。英文页是对的，所以这是翻译阶段的偏差而非陈旧副本：页面现在写对象接
  受的东西，而门禁会拒绝任何语言里再出现一次。— (details: quality-ledger (bo))

- **带位置的校验错误仍然说出它匹配的 `path`。** — `SchemaValidationError` 要么打印
  `line:column: message`，要么打印 `path: message`，因此节点一旦带有源码区间，schema 作者就失去了自
  己书写的那一半：`1:9: expected map but got sequence` 从不说明是哪个键。现在两半都打印。— (details:
  quality-ledger (bm))

- **映射键终于与同样的文本作值时同义。** — `1: a` 读作 `{"1": "a"}` 而 `a: 1` 读作 `{"a": 1}`，
  `~: 1` 读作 `{"~": 1}` 而 `a: ~` 给 `{"a": None}`：同一份文档因标量位于 `:` 的哪一侧而有两种含义，
  以整数、布尔或 null 作键的配置根本无法被查到位。现在键走与值相同的 schema 路径，与 PyYAML、ruamel
  一致；`load_toml` 会把任一 YAML schema 会重新定性的键加引号。— (details: quality-ledger (as),
  (at))

- **锚点名文法与读取器对齐，收掉一整族漂移。** — 写手可能发出读取器拒绝再摄入的锚点名
  （`found unknown anchor`），破坏「绝不发出不可解析输出」的契约：以 `:` 结尾的名字每轮掉一个字符，
  带引号的名字吞掉换行，裸扫描器还会从注释文本与重叠的 `&` 里凭空造出锚点。现在按 granit 的方式读，
  即锚点字符的一个极大连续串。 — (details: boundaries — Fuzz findings, (x), (y), (z))

- **注释在标记、标签与容器之间守得住自己的归属。** — 一族「首次发出与再读之间注释换主人或消失」的位
  置：只渲染出标签的值（`k: !`）把紧随其后的注释行据为己有；容器自己的行内注释落在无法承载它的行上；
  引号标量里的 `#` 因为裸字节扫描而挤掉注释；紧凑的 `- key:` 分支只复制文本不复制注释槽位；而前导注
  释的单个 *槽位* 只保留一叠注释的最后一条 —— `# alpha` + `# beta` + `key: 1` 回来时只剩 `# beta`。
  前导注释现在是列表，所有写手都尊重它。— (details: quality-ledger (h), (i), (m), (n), (p), (t),
  (u), (v), (ad))

- **合并的身份与深度问题修复，不再爆原生栈。** — `<<: &b` 是字面的 null 值合并键，却与下方真正的
  `<<:` 折叠在一起，折叠时搬走了被丢弃条目的注释却没搬它携带的锚点；带注释的非标签 `y` 与合并来的
  `y` 是两个不同的 `IndexMap` 键，于是 `to_yaml` 在同一层打出两次 `y:`；嵌套或自引用的合并链在环守卫
  已弹出之后喂给解析器的尾递归，深度无上界地爆栈（58 字节的 libFuzzer 发现）；而带注释的 `<<` 键节点
  对该遍完全隐形。— (details: quality-ledger (o), (q), (r), (s), (y))

- **块标量一次发出即收敛，指示符也被正确识别。** — `>+8\r\r#` 读作值为一个换行、`Keep` 且显式缩进 8
  的折叠标量；写手保留指示符发出 `>+8\n\n`，它再读变成 `Clip` 且无指示符，于是*第二轮*发出 `>\n\n`，

  `4RWC` 式显式缩进与首行为空的字面块由同一批工作在再解析下闭合。 — (details: quality-ledger (aa),
  (ab), (r))

- **Unicode 空白、BOM 与标签后缀不再损坏文档。** — 方言 fuzzing 触及的空白集、BOM 位置与标签后缀边界

  让那些字节藏在别的字符里。这套论据 `pyrs-schema` 的 `needs_quotes` 早已在用，只是写入器这份没跟
  上。后者是一个按宽度索引的 `Vec<String>` 缓存——每行一次长度判断、每加深一层一次 `resize`、每个不同
  宽度一次 `" ".repeat` 分配，然后再借用表项去复制——现在换成对一个常量 64 列空格串取切片。钉住的是等
  价而不是速度：`needs_double_quoted_agrees_with_the_scan_for_every_code_point` 把六遍扫描的形式留作
  参照，对 U+10000 以下的每个码点、在五种位置（单独、行首、行尾、中间、紧挨空格）各问一遍，再按步长
  抽样星平面并显式包含非字符。它没等别人帮忙就抓到了第一版的错：结尾写成 `!saw_high_byte || …`，给所
  有纯 ASCII 字符串都加了引号，参照实现在 `"a b"` 上先于其他任何测试指出分歧。把 `b == b':'` 从字节
  判定里删掉，会让等价测试和 `prop_output_always_parses` 一起变红。在 rustc 1.97.1 上以同一分支三个
  提交产出三个二进制配对测量，两次重复逐指令一致：字节扫描给出 `serialize_anchors` -28.01%、
  `serialize_medium` -18.09%、`serialize_block_scalars` -13.05%；缩进表给出
  `serialize_medium` -8.20%、`serialize_block` -10.82%、`serialize_small` -29.81%；合起来
  `serialize_medium` 是 -24.81%，对照组 `parse_medium` +0.00% 两个都不调用。

- **TOML 写入器不再为它输出的每一小块分配临时对象。** — `to_toml_medium` 数到 53,218,850 条指令，而
  同一份文档的 `to_json_medium` 只有 21,283,040 条：每一行输出都走 `writeln!`，每个键和每个值都先成
  为自己的 `String`，再复制进文档，数组和内联表还先建一个 `Vec<String>` 来 join、再格式化、再复制一
  遍。按同一分支三个提交产出的三个二进制分别测量，于是每一步带着自己的数字：文档输出改为 push
  （−19.00%），`quote_key`/`quote_basic`/`quote_multiline`/`value_str` 变成写进调用方缓冲区的
  `push_key`/ `push_quoted`/`push_multiline`/`write_value`（−33.27%），合起来 −45.95%，53,218,850 降
  到约 28,761,000 条计数指令；对照组 `from_toml_medium` −0.15%、`serialize_medium` +0.01%、
  `to_json_medium` +0.00%，它们一个都不调用。要主张的是逐字节一致，而不只是正确，而测试给不出这个结
  论：测试断言输出"应该是什么"，不是"没变"。于是让两棵树都跑完仓库里的每一份 TOML 文档（按内容哈希去
  重后 712 个输入：777 份 toml-test 有效样例加上 fuzz 语料与种子，路径是 TOML → 中枢 AST → TOML，并
  且再走一遍以抓住只在第二次输出才移动的文本），结果完全一致：242 份产出文本，SHA-256 全部相同，每个
  拒绝都是同一个错误类，两侧不成不动点的那 9 个形状也相同，0 条记录有差异。让差分比较真正有意义的那
  一步：在信任"改动前" 那棵树的输出之前，先 grep 确认它没有新的辅助函数（0 处命中）——两棵一模一样的
  树之间的差分，其通过理由与什么都没改时的通过理由完全相同。`quote_key` 已删除；`quote_basic` 与
  `quote_multiline` 作为 `quoted` 和 `multiline` 留在测试模块里，因为断言需要一个返回值，而发布的代
  码不需要。`docs/dev/perf.md` 保留了归因、算术，以及写入器仍然花掉的那部分。

- **JSON 读取器不再为两次"无事可做"的调用买单。** — 对 `from_json_medium` 做归因后发现
  `Parser::ws` 占了该场景的 6.63%，而这份 fixture *完全没有空白字符*：每次解析约九十次调用，每次
  三十多条指令，而答案几乎都是"下一个字节不是分隔符"。`attach_pending` 是同样的形状，在没有注释的
  文档上占 3.23%，每个键和每个值都会遇到它。现在 `ws` 是单个谓词 `at_separation` 的内联守卫，循环
  原样移到 `ws_extended`，`attach_pending` 一看到空列表就返回。守卫是循环的可靠超集，方向是要紧的
  那个：只要循环会消费某个字节，守卫就答"是"。这一点由
  `the_whitespace_guard_never_declines_what_the_loop_would` 钉住——它对全部 128 个 ASCII 字节、五个
  多字节分隔符外加一个不是分隔符的字符、三种注释形态和三种方言，向守卫与循环问同一个问题，并要求
  返回相同的位置与待处理注释数。做过变异检查：让守卫对 `/` 答 `false`，JSONC 下的 `"//x\n1"` 就以
  `left: (0, 0) right: (4, 1)` 失败，那正是会悄悄丢掉注释的漏判。在 rustc 1.97.1 上以同一分支的三个
  提交产出三个二进制配对测量，于是每个守卫各自带着自己的数字：`from_json_medium` −4.33% 再
  −1.56%，`from_jsonc_medium` −3.52% 再 −1.25%，`from_json5_medium` −4.49% 再 −1.40%，对照组
  `to_json_medium` +0.00%，因为它两个都不调用。`docs/dev/perf.md` 记录了第一行为何超过按调用次数算
  出的预测，以及守卫没有收回的那部分。

- **两个读取器改为整段复制源码，不再逐字符解码。** — 单引号 JSON5 扫描器和 TOML 单行基本字符串
  扫描器是最后两个仍按码点调用 `chars().next()` 与 `push(ch)` 的读取器，而双引号 JSON 扫描器早就
  改成快进到下一个需要判断的字节、整段复制这一段。用门禁自己的测量装置看，一个 9 字符的 TOML 值
  要花约 540 条计数指令。在 rustc 1.97.1 上配对测量：同一棵树、两个二进制交替运行、重复两次且
  逐指令一致，`from_toml_medium` −5.55%、`from_json5_medium` −5.76%，并以 `from_json_medium` 的
  +0.00% 与 `to_toml_medium` 的 −0.00% 作对照，说明动的只有这两个。停止集合没有改变，每一半都由做
  过变异检查的测试钉住：TOML 仍拒绝基本字符串里的控制字符与行结束符，JSON5 在那里仍*接受*控制字符，
  两者都仍拒绝多字节文本之后未闭合的输入。`docs/dev/perf.md` 保留了找到它的归因、本次改动刻意没碰的
  多行字符串孪生实现，以及 TOML 读取器剩下的结构性开销——同一份文档 169,449,833 条指令对 JSON 的
  98,994,186 条，因为它先建一个中间表模型再投射到中枢 AST——记为下一个问题，而不是已关闭的问题。

- **指令数地板下调到新引擎实测达到的位置。** — node-map hasher 进入 `main` 后，`Ir baseline refresh`
  工作流在施测镜像（`github-runner ubuntu24`、rustc 1.97.1）上重新测量了全部 21 个场景，其产物现在
  就是已提交的基线：`from_json_medium` 120,751,446 → 99,000,356（−18.01%）、`from_toml_medium`
  −16.25%、`parse_anchors` −12.95%、`to_python_anchors` −11.17%，写入场景落在 +0.03%…−1.80% 之间。
  地板若比实测高出 18%，门禁就等于默许 18% 的回退，所以"零回退"承诺如今以这些数字为准。数值并非
  手抄，而是由施测镜像上的 `scripts/ir_gate.py --update` 写出的。

- **节点映射在所有构建上都改用 FxHash 计算键哈希，不再只在 `no_std` 下。** — 开启 `std` 时
  `NodeMap` 就是 `IndexMap<K, V, std::hash::RandomState>`，所以往表里放一个映射键都要付
  SipHash-1-3 的代价：`callgrind` 测得从 `CustomNode::hash` 走到 `Hasher::write` 的自耗时
  10,214,000 条指令、180,000 次调用——占 `from_json_medium` 的 8.98%——而特性开关的分歧甚至让节点
  大小都不一致（144 字节对 128）。两侧现在都明确指向本 crate 自带、定种子的 `FxHasher`，即嵌入式
  构建一直使用的那个。在门禁钉住的 rustc 1.97.1 上配对复测：`from_json_medium` −12.75%、
  `parse_medium` −4.95%、`to_json_medium` +0.11%。`no_std` 一侧早已接受的取舍如今属于整个构建，
  并写进 `NodeMap` 的文档而不再含糊：没有 HashDoS 随机化，因此刻意制造碰撞的文档会让节点映射退化
  为线性探测。落地它还必须把约 40 处写成 `IndexMap<CustomNode, CustomNode>`——也就是没说出口就要了
  `RandomState`——的调用点改为指名 `NodeMap`。（详见 docs/dev/perf.md「The node map was hashing
  its keys with SipHash」）

- **标量解析器不再裁剪本就没有空白的文本。** — 每个 JSON、TOML 与 YAML 标量都要问
  `resolve_core_type` “这是数字还是一个词？”，而这个答案做的第一件事是用一次双端谓词遍历去掉首尾分隔
  字符：每次调用 38 条计数指令，而这些字符串几乎从不以空白开头或结尾；YAML 1.1 标量更要把这笔开销付
  两次，因为 `resolve_yaml11_type` 在委托给 core 链之前先裁剪了一遍。YAML 接受的所有空白都是 ASCII
  （`SP TAB CR LF NUL`），而 UTF-8 不会把 ASCII 字节放进多字节序列，所以首尾两个字节就足以判定有没有
  东西可裁：改为读取一张在编译期*由* `is_yaml_blank` 生成（而非把它重述一遍）的分类表两次，遍历只在
  某一端确实是空白时才执行。同一个 harness 二进制的一对测量：`from_json_medium` −0.74%、
  `from_toml_medium` −0.92%，而写入器同样经由这个 crate 解析标量，于是 `to_json_medium` −1.68%、
  `serialize_medium` −0.36%；作为对照的 `parse_medium` 重复在 +0.0014%，正是它让前面两个差值成为证
  据。给守卫加 `#[inline]` 测得 −0.003%，落在同一二进制的重复误差之内，于是删掉而不是留下一个未经测
  量的提示。— (details: quality-ledger (ct))

- **指令数下限搬到了 `main` 上的代码。** — 已提交的基线还停在 `d7177efc`/`dd211c8d` 之前的数字上，于
  是门禁的余量是被漂移撑大的、不是被决定撑大的：`from_json_medium` 比引擎现在的实测高 21.61%、
  `from_jsonc_medium` 高 19.83%、`from_json5_medium` 高 16.72%——这么大的回退会一声不响地通过。基线经
  `Ir baseline refresh` 通道在施测镜像上重新生成：工具链从文件里读（`rustc 1.97.1`）、镜像
  `20261004.327.1`、每个场景取三次采样的最大值、二进制摘要与数字一道写入，所以没有任何值是手抄的，也
  没有任何场景向上越过 0.5% 线——动了的三处只有 0.0001% 的进程噪声。写出场景没动，这正是一个改键哈
  希、一个改键引号应当留下的形状。

- **给字符串定引号不再扫它三遍。** — 每座桥都要问 `needs_quotes`「这段文本若写成 plain 标量会不会被
  误读」，而它的答案先按字符读一遍，再为 NBSP 与 BOM 各搜一遍。ASCII 文本里两者都不可能出现，所以现
  在一遍字节扫描就定下 ASCII 的情况，凡是带高于 `0x7F` 字节的文本仍原样交给字符规则。穷举式对照
  `needs_quotes_agrees_with_the_char_rule_for_every_code_point` 把两条路径与字符规则在全部 1,114,112
  个码位上比对，并且能判出一条写错的字节规则：把边界挪一格（把空格算作控制符）它就红了，报
  `first: Some((32, true, false))`。`callgrind` 在门禁的 harness 上、同一台主机测得：
  `from_json_medium` -6.89%、`from_json5_medium` -1.87%，而本改动进不去的 `from_toml_medium`
  （-0.0009%）与 `parse_medium`（+0.0002%）在两次运行间复现——正是这一点让前两个差值成为证据，而不是
  环境噪声。— (details: quality-ledger (cr))

- **节点的摘要只读相等性真正读取的那些字段，于是每条读取路径都变便宜了。** — `CustomNode::eq` 比较标
  量的取值、风格、chomping 与三个身份字段，显式的块缩进指示符并不在其中，可 `Hash` 却把它算了进去。
  于是映射视为同一个键的两个节点被路由到不同的桶——这正是 `plain_and_noted` 为另一个字段已经守住的那
  条契约。`Hash` 现在不再读 `block_indent`，而无装饰的节点不再为元数据写下三个 `Option` 判别值，而是
  什么都不写。`callgrind` 在指令门禁自己的 harness 上、同一主机同一编译参数下定价：`Hasher::write`
  自身成本 20.95M → 9.95M 条指令，整个进程 `from_json_medium` -7.80%、`from_json5_medium` -7.71%、
  `from_toml_medium` -5.66%、`parse_medium` -3.38%。键比较并未变多（`__memcmp_avx2` 10,720,143 →
  10,720,033），所以更便宜的摘要没有牺牲该夹具上的探测质量。被测的是 `std` 路径——节点映射在那里以
  `RandomState` 为键，而 `no_std` 早已改用定种子的 FxHash（`ast.rs:29`）。裁决权仍归施测镜像上的
  `.ci/ir-baseline.json`，而这些场景预期会向下移动。— (details: quality-ledger (cq))

- **方言写出器不再丢注释，代价以计数指令记在账上。** — `to_jsonc` 与 `to_json5` 现在会读每对键值此前
  从未看过的那两个注释槽位（#359），`ir_gate.py` 量出变宽的键值循环：`to_jsonc_medium` +4.77%、
  `to_json5_medium` +3.78%、`to_json_medium` +0.94%。`.ci/ir-baseline.json` 在施测镜像上重新生成，这
  三个场景用 `--accept-drift` 点名；同一次刷新把 `to_toml_medium` 收紧了 -4.90% —— 那是基线原地不动
  时积累的漂移，不是回退 —— 并记下两个 harness 二进制的 SHA-256，从此每个差值都点名它所描述的字节。
  容差未变。—（详情：quality-ledger (cg)）

- **标签发出改为表驱动，转义不再分配内存。** — 把标签编码挪到读取器自己的字符类上，就让逐字节的归属
  判定进了序列化热路径，于是它变成一张 128 项的编译期表（字母数字判定折进同一次查表），而 `%XX` 转义
  从十六进制字符表写出，不再用 `format!` —— 后者每个被转义字符都要新建一个 `String`。
  — (details: perf — Leaderboard & Performance Status)

- **大量 null 键的文档解析时间降为线性。** — null 键折叠原先每见一个 null 键就重扫整个映射：在全
  null 文档上看不见（折叠项就在 0 号槽），在真正要紧的形状上是二次的 —— 2k 个不同键后接 2k 个 null
  键，输入放大 4 倍耗时增长 12.4 倍（8k + 8k 时 99 ms）。映射现在记住 null 键的槽位，扫描只作为正确
  性兜底。 — (details: quality-ledger (ae))

- **10% 以下的问题由已提交的指令基线来裁定。** — 两个 runner 作业测出的 `serialize_block_scalars` 相
  差 1.44%，而同一二进制自身重复在 ±0.0005% 内 —— 低于 runner 噪声的墙钟时间说明不了任何事。基线现在
  记录产生它的环境，`scripts/ir_gate.py` 在来源不同时报注一句。— (details: quality-ledger (am),
  (as))

#### 变更

- **granit-parser 1.1 → 1.3** — 将 YAML 事件解析器从 1.1.0 升级到 1.3.0。这是 1.x 版本线内语义化版本
  兼容的次级升级：1.2.0 为特殊文档的限制新增了可选的 `Options` 字段，1.2.1 按 YAML 规范收紧了若干解
  析结果，1.3.0 为 `Input` trait 新增了两个带默认实现的方法（`fetch_block_scalar_line` 与
  `take_quoted_scalar_ascii_chunk`），让扫描器更快地跳过块级与引号标量字节。本项目通过
  `Parser::new_from_str` 使用解析器，只实现 `EventReceiver` / `SpannedEventReceiver`，从不实现
  `Input`，因此无需改动源码——新增的 trait 方法解析到其默认实现。全套测试通过：
  `cargo nextest run --all`（359）、`pytest`（1436 + 43 numpy）、纯 Rust `--no-default-features` 构
  建，且 YAML 测试套件合规门控保持不变。
- **原生 JSON 与 TOML 内核** — `serde_json` 和 `toml_edit` 依赖已全部移除。
  `pyrs-yaml-core` 自带 RFC 8259 JSON 引擎（字节级扫描、数字保留原文，因此
  `from_json → to_json` 字节稳定且不会丢失大整数/浮点精度，行/列错误带类型，
  严格拒绝尾逗号、前导零、孤立代理对、未转义控制字符、多根文档）以及覆盖
  完整语法的 TOML 1.0 引擎 — bare/quoted/dotted 键，basic/literal/多行字符串，
  十进制/十六进制/八进制/二进制整数允许下划线分隔，浮点支持 `inf`/`nan`/指数，
  以及 offset/local 日期、时间与日期时间 — 所有拒绝都以 granit-parser 风格的
  `ParseError::Syntax` 携 0-indexed `line`/`col` 上报。公开 API 保持不变，
  回环测试与 `tests/test_toml.py` 在新引擎上全绿。
- **内部重复代码清理** — 基准 fixture 改由共享块拼接，PyO3 路径编辑方法委托给现有
  `apply_metadata_edit` 助手，重复的文件读取/错误映射与行偏移样板收敛为共享函数。
  公开行为无变化；jscpd 测量的重复代码率从 5.25% 降至 3.45%。
- **`YamlDocument.validate()` 缓存编译后的 validator** — schema（JSON 文本或 dict）首次校验成功后即
  缓存编译好的 `jsonschema` validator；后续调用跳过 schema 解析、meta-schema 检查与 validator 构建。
  dict schema 按对象身份键控并辅以深拷贝快照守卫：原地修改会在下次使用时通过 `==` 检出并透明重编
  译。缓存路径抛出 `exceptions.best_match(validator.iter_errors(instance))`，与
  `jsonschema.validate()` 语义完全一致。WSL 实测：`document_validate` −98%。
- **解析/序列化内核结构化去重** — mapping 与 sequence 渲染共享单一 `write_container_node` 骨架（输出
  字节级一致，`serialize_*` 中位数 −5~11%）；单/多文档解析入口共享同一 `load_ast` 错误契约；schema

  化。仓库重复代码率 3.38% → 2.60%。

#### 修复

- **`\u` / `\x` 转义后紧跟多字节字符时解析器 panic** — 定宽转义读取器按字节偏移切
  `&self.text[pos..pos+width]`；JSON `\u` 或 TOML `\xHH`/`\uXXXX`/`\UXXXX` 后跟多字节字符时切片落在
  字符中间而 abort（#153 非 ASCII 切片崩溃的同族）。现改为字节切片 + UTF-8 校验，畸形转义干净报错。
  由方言 fuzz 发现，两处解析器均有确定性 Rust 回归测试固定。
- **字面 `<<` 键（非 merge 值）被静默丢弃** — `load(safe_dump({"<<": None}))` 返回 `{}` 丢了键。
  merge 解析器把任意 `<<` 都当 merge 消费，即使值是 Null/标量。按 YAML，`<<` 仅当值为映射别名/内联映
  射/ 其序列时才是 merge；Null/纯标量 `<<`，以及不含别名且无内容可合并的 `<<`（`<<: []`、
  `<<: [1, 2]`、`<<: {}`）现保留为普通键并往返保真。Alias/映射/序列路径（含 #166 自引用守卫）不变，
  yaml-test-suite 仍 405/406。由往返属性 fuzz 非确定性地暴露（正是 #163/#165/#166 类缺陷），并新增确
  定性 Rust 回归测试锁定。
- **TOML 深嵌套耗尽原生栈并 abort 进程** — TOML 解析器此前无嵌套预算（JSON 有 `DEFAULT_MAX_DEPTH`、
  YAML 有 `parse` `max_depth`），`parse_value` → `parse_array`/`parse_inline_table` 无界递归。深嵌
  套数组/内联表直接崩掉解释器（已验证：退出码 `0xC00000FD` STACK_OVERFLOW）——即 TOML 版的 #166 YAML
  merge 栈溢出。解析器现追踪 `depth`，超过 1000 返回类型化 `ParseError::MaxDepthExceeded`，与 JSON
  对称。由进程内 Python 边界测试 + subprocess 崩溃金丝雀 + 大栈 Rust 单元测试共同守护。
- **方言 writer/parser 丢失或错置文档级注释** — 三个定点属性抓到的 defect：(a) JSONC/JSON5 值前的文
  件首 `// note` 被误判为行内注释（空白扫描启发式中偏移 0 前无换行）并被首个对象成员占取，而非落在
  writer `emit_root_leading` 所标注的根容器上——空 `{}` 或根标量时彻底丢失；(b) JSON 家族与 TOML
  writer 逐字输出注释体而 parser 存的是 trim 后的文本，未 trim 的注释会在多轮 pass 间振荡尾随空白
  ——writer 现在输出时也 trim，首次拼写即稳定；(c) 纯注释 TOML 文档（`# note` 后无 key 消费）重解析
  时丢注释、空根序列化为 `""`——遗留的独立注释现在挂到空根表上。至此五格式的 leading 注释均达到逐位
  稳定的定点。由 `jsonc_file_leading_comment_stays_on_the_root`、
  `jsonc_comment_text_is_written_trimmed`、`comment_only_document_keeps_its_note_on_the_root` 钉
  住。
- **嵌套块标量的正文保持父行缩进** — 嵌套键下的字面/折叠标量把正文行按固定
  一级缩进从第 0 列输出，而不是落在 `b: |` 头部行下一层，导致所有嵌套块标量
  形态（键值对、序列项、紧凑 dash 映射、任意深度）序列化出的文本重解析为报错
  或错值。标量写入器现在贯穿 `block_base`（父行列位）参数；七种嵌套形态的
  round-trip 文本逐位忠实。由 TOML 热点基准经由共享 serializer 暴露。
- **serializer 只输出可重解析的 YAML** — 文本级门控抓到的五个拼写 defect：
  换行分支对子节点预输出 anchor/tag 而子节点（标量/null/flow 容器）自己也会
  输出，产生双头部（`A: !a` … `!a null`），现仅限 block 容器；flow 容器内的块
  标量（`[|`、`{k: >}`）及键位块标量降级为双引号；起新行的 flow 容器丢失行首
  缩进，复杂键（`?`）的值标记 `:` 落在第 0 列而关闭外层集合——两者现在都从
  父级缩进；带独立注释/tag 的复杂键产生歧义文本（注释现在移到 `?` 上方，键体
  整体下移一级独占行）；flow 集合内首尾带空白或嵌入 flow 指示符（`,` `[` `]`
  `{` `}`）的 plain 标量现在加引号——不加引号会截断 token 或在重解析时消失。
  另：带 tag 的空 block 容器把头部并入 `{}`/`[]` 行；紧凑 dash 项不再内联带独立
  注释的值。九个钉住的 Rust 测试加参数化 Python 回归守护每类缺陷。
- **TOML 拒绝合法的最小 i64 整数** — `from_toml`/`load_toml` 在 `-9223372036854775808`（`i64::MIN`）
  上失败：带符号路径先按无符号绝对值解析，取负号前就溢出。现在符号与数字一并解析（`i64::from_str` 向
  负方向累加），带符号浮点保留指数拼写，旧的取负通道已删除。由新的 Python 侧 Hypothesis 方言模糊测试
  （`tests/test_property_dialects.py`，以 stdlib `json`/`tomllib`/`pyjson5` 为预言机做类型严格相等比
  较；同时钉住两类 AST 歧义拼写——JSON5 裸 `Infinity`/`NaN` 字面量与超 i64 数字串）发现。Rust 回归：
  `toml::parser::tests::i64_lower_bound_negative_integer_is_accepted`。
- **错误缩进的流序列续行再次被拒绝** — 将 YAML 解析器升级到 granit-parser 1.3（见*变更*）后，开始静
  默地*接受*这样的输入：多行流集合的续行缩进不比其所在块键更深（yaml-test-suite `9C9N`：`flow: [a,`
  后接列 0 的 `b,`），使严格性从 `405/406` 回退到 `404/406`——由于 suite 的 ≥95% 阈值门，它对 CI 不可
  见，因而带着“绿”混过。现在 AST receiver 里一个解析后的 in-tree 守卫会跟踪所在块的缩进，并拒绝缩进
  不足的流续行，恢复 `405/406`。守卫只用解析器已算好的 span，因此正确缩进的多行流不受影响。`9C9N` 现
  被固化为逐例硬门（字面输入、无 `skipif`）写进 `tests/test_yaml_suite.py`，另加一个 Rust 单测
  （`parser::tests::flow_continuation_under_indented_is_rejected`）。
- **自引用合并键不再溢出原生栈** — 展开后指回自身锚点（`a: &a` 内含 `b: {<<: *a}`）的 `<<` 会在
  `resolve_merge_keys` 中无限展开，耗尽原生栈并拖垮整个解释器进程（Windows 退出码 `0xC00000FD`，即
  段错误）。循环 guard 此前只在*收集*合并对时生效，从不在*遍历*展开结果时生效，因此递归重入从未被拦
  截。现在锚点 guard 与别名展开一样按路径作用域：某锚点名在其展开被遍历期间始终留在递归路径上，解析
  回该路径上已存在的祖先的合并会终止为空展开而非递归。无环 AST 无法承载 PyYAML 的循环 dict，因此自
  引用合并现在收敛到 `{}` 而不再崩溃。同批修复 4 个相关合并语义缺陷：null/标量/序列合并源不再残留为
  字面 `<<` 键；直接作为合并值的内联映射（`<<: {x: 1}`）现在会被合并；合并序列中的非别名元素
  （`<<: [*a, {y: 2}]`）会保留其内联映射。由 6 个 Rust 与 9 个 Python 回归测试覆盖（`merge::tests`、
  `tests/test_gaps.py::TestSelfReferentialMerge166`）。由
  [@bourumir-wyngs](https://github.com/bourumir-wyngs) 在 #166 报告。
- **NumPy 序列化不再在不持有 GIL 时读取 Python 内存** — ndarray 写入器曾通过 `unsafe { as_slice() }`
  借用数组数据缓冲区，并在 `py.detach` **内部**（即已释放 GIL 之后）遍历该借用切片。无论来源为何，
  `&[T]` 都是 `Send`，因此借用检查器无法拦截；但这块内存归 Python 所有，其他线程可并发 resize 或写
  入，构成不健全的数据竞态 / UB，仅在并发下暴露。现改为在**仍持有 GIL** 时把缓冲区快照为 Rust 自有
  内存（`slice.to_vec()`），仅标量→节点转换离线程执行。这是绑定层**唯一**一处 `unsafe` 缓冲区借用；
  其余全部 `py.detach` 站点已审查，仅触及 Rust 自有状态（AST、源文本、`BufWriter<File>`）。回归覆盖
  见 `tests/test_numpy.py::TestNumpyConcurrency`。由
  [@bourumir-wyngs](https://github.com/bourumir-wyngs) 在 #165 中报告。
- **重复的别名引用不再解析为 `None`** — `to_dict()` 在一个**全局** visited 锚点集合
  后展开别名，且从不清理，导致任一锚点只有**第一次**引用产出值，之后全部静默降级
  为 `None`：
    ```yaml a: &x 1 b: *x      # 1 c: *x      # 原为 None，现为 1```
    影响面比“第二次引用”更宽：同一容器内的两个兄弟引用也会互相污染
    （`{a: &x {p: 1}, b: {q: *x}, c: {q: *x}}` 中 `b` 有值而 `c` 为 `None`）。现将该 guard 限定在当
    前递归路径上——仅在一次展开期间压入，随后弹出——因此重复引用与兄弟引用各自获得完整构建的值，而真
    正的环路仍会终止。`<<` 合并解析与 AST 本身经审查不受影响。`tests/test_direct_load.py` 新增 6 个
    与 PyYAML 对齐的用例锁定该行为，另有两个此前将错误输出当作预期的测试被重写。由
    [@bourumir-wyngs](https://github.com/bourumir-wyngs) 在 #163 中报告。
- **首层值为嵌套容器时文档头注释不再丢失** — 解析器曾为所有进行中的容器共用单一注释槽，嵌套容器的
  start 会提前抹掉尚未落位的 standalone 头注释（在 parse 层即丢弃；`to_dict` 不可见，`dump` 致命）。
  现改为每容器独立槽的栈式管理。
- **splice 编辑不再重复前导注释** — 重生成的区域文本携带 pair/item 自身的 standalone 注释时，被替换
  区域未覆盖旧注释行，两条注释并存；plan 现将区域回扩至注释行（`pyq set`/`delete` 与 bindings splice
  路径共享此修复）。
- **`!timestamp` 在所有受支持 Python 上接受结尾 `Z`** — `datetime.fromisoformat` 仅从 3.11 起识别
  UTC-`Z` 后缀；插件现将 `...Z` 归一为 `+00:00`，修复 3.8–3.10 上 YAML `!timestamp` 标量及
  `load_toml` / `from_toml` 引入的 TOML datetime 报 `Invalid isoformat string` 的问题。

- **迁移到 granit-parser** — 用 granit-parser 1.0.1 替换 saphyr-parser，借助原生 `Event::Comment` 输
  出消除了全文 `scan_yaml()` 预扫描。parse_small -18%、parse_large -21%、roundtrip_large -18%。

#### Fixed

- **紧跟“只有标签、没有正文”的值之后的注释，既保住归属又一轮即稳定** — 只渲染成标签的值
  （`k: !`、`k: !-`、`k: !!str`）会让扫描器停留在“值未完成”状态，因此紧随其后的注释行会被报成
  该**值**的前导注释：注释换了主人，文档要第二轮才稳定。有三条路径以这样到达——
  `crash-cf49fe85`（容器自己的注释在 pair 行的槽位已被占用时只能另起一行）、
  `crash-c5b367d3`（23 字节；merge 键的注释被重新安家到它贡献的那一对之前），以及前两者在任意
  tag 写法下的表现。写手现在于写出注释行之前先闭合挂起行，写出该值自己的 null 正文
  （`k: !- ~`），从而让注释留在 AST 指定的节点上；注释本可行内留在 pair 行时，输出保持原样不变。
  若两者确实冲突（容器注释必须另起一行、又要保住归属），则以往返契约的稳定为先，且该取舍已写在
  决策处而非默认假设。
- **映射自己的注释不再漂到“裸 tag 值”那一行后面** — 当块式映射 body 的最后一对，其值只
  渲染成一个孤立的 `!`（非特定标签、无正文）时，把容器的 inline 注释追加在那行之后，重读
  会变成该**值**的 leading 注释，于是容器在重读时失去它，文档要晚一轮才稳定（`~: ! # -` →
  `~:  # -\n  # -\n  ! `；libFuzzer `yaml_roundtrip`，`crash-cf49fe85`，最小化到 13 字节）。
  写手现在把注释放在读者会报告它的位置，因此一次发射即是不动点，而 AST 仍按解析结果把注释
  留在容器上。*具名* 标签（`!-`）会闭合自己的属性、注释留在行内也能正确重读，所以未被改动
  ——为该形状已存的两个 pin（`crash-11ced252`、`crash-22cb5f67`）仍断言其原文本。代价：指令数
  门禁三次拒绝后的结果——逐对做判定时 `serialize_small` +2.75%，判定提出循环但实参仍被急切求值
  时 +1.39%，直到罕见路径单独成循环、常规路径保留原形状后 +0.54%。
- **被折叠的重复 `<<` 不再把它定义的 anchor 变成孤儿** — `<<: &b` 是字面量、空值的合并键，
  按我们自己的规则它是普通键；它与下方真正的 `<<:` 折叠到了一起，而折叠只把被丢弃条目的
  **注释**重新安家，没有管它携带的 anchor。于是发射出的文本用了 `*b` 却全文再无 `&b` 定义
  ——那是我们自家解析器都会拒绝的文本（`found unknown anchor`，破坏了"从不发射不可解析
  输出"的契约，`crash-43eca7a3`，18 字节，用修复前的二进制最小化到 15：已修复的输入无法再
  被缩减）。接收器现在会留下被丢弃的节点，并在文档收尾时把它内联进每一个"名字已无定义"的
  别名处：正常共享的别名完全不被动到，且只有折叠真的删掉了带 anchor 的条目时才走这一次遍历，
  常规路径零开销。`<<: &b LF <<: LF : *b` 现在发射 `<<: ~ LF ~: &b ~`——一轮即稳定，值不变。
  一句实话：孤儿别名会被它指向的节点替换，因此值语义保住而"共享同一节点"的拼法不再保住；
  定义都没了，本就无可共享的身份。
- **只由换行组成的块标量值不再退化成空串** — `>+8\r\r#` 读作一个值为单个换行、chomping 为 `Keep`、显
  式缩进为 8 的折叠标量。写手保留了缩进指示符，发射出 `>+8\n\n`；它重读时值不变但变成 `Clip` 且无指
  示符，于是下一轮发射 `>\n\n`，值就成了 `""`——Clip 会剥掉尾部换行，而该值仅有的那一个换行无处安放。
  让*空* body 保持幂等的那两条规则（丢弃不可恢复的缩进指示符；写出能重读回同一值的 chomping）都以
  “空”为条件，而“全是换行”的 body 并不为空（libFuzzer `yaml_roundtrip`，`crash-2f6b1eff`，6 字节——
  已是最小：输入不再崩溃，`tmin` 无从缩小）。两个写手现在都以“没有内容行”为共同条件，形状一轮即达不
  动点，值也保住了。代价：首版对同一个值多扫了一遍，`serialize_block_scalars` 实测 +0.65%——在 runner
  上是 +2.11%，越过指令数门禁的 2% 容差，于是门禁在合并前拦下了这次改动。改为复用写手已经算出的首个
  内容行判据后降到 +0.15%，回到容差内。
- **合并键不再把 anchor 挪到别名的后面** — 展开 `<<:` 时合并对曾被前插到映射开头，于是
  在较早的自有键上定义 `&b`、又在被合并的映射里使用 `*b` 的文档，会先发射 `*b` 再发射
  `&b`：那是自家解析器都会拒绝的文本（`found unknown anchor`），破坏了引擎“从不发射不可
  解析输出”的契约（`crash-9b77aea4`，78 字节，最小化到 15）。展开现在插入在 `<<:` 原本占
  据的下标，也就是作者写下的顺序 —— 合并键在首位时仍是 0，所以文档里 `<<: *defaults` 的
  写法不受影响（Rust 测试 487 → 489、Python 测试 1781，全部无需改动即通过）。
- **`float_to_yaml_string` round-trip 修复** — Rust Display 丢失小数部分时
  补 `.0`（`42` → `42.0`），使 float 按 float 而非 int 正确往返。
- **回退 `count_nodes` 预分配** — 全 AST 遍历的开销大于其避免的重新分配
  （serialize_10mb 慢约 14%）；缓冲扩容交给 Vec。

#### Added
