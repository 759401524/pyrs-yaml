### [Unreleased]

#### 修正

- **コンパクトなシーケンス項目内のエイリアスキーが `null` と綴られなくなります** — シーケンス項目で
  あるブロックマッピングはコンパクトな `- key: value` 形を取り、そのキーライタは非スカラを何でも
  `null` と綴るため、エイリアスキー `*x` が項目自身の null キーの隣に字面の `null:` として出力されま
  した。再読み取りは二つの null キーを一つに畳んで一対を落とし、出力は一巡で収束しませんでした
  （libFuzzer `yaml_roundtrip` crash-cd7fab01）。コンパクト形のガードは今、マッピングキーとシーケン
  スキーを既に排除するのと同じようにエイリアスキーを排除するので、項目はブロック本体形を取り、ペアラ
  イタが `? *x` を出力してエイリアスが自分の同一性を保ちます（`docs/dev/quality-ledger.md` (lp)）。
- **ネストしたブロックシーケンス内のコメントが巡をまたいで行を保ちます** — 二つのスロットが
  コメントを移動させ、エディタの出力は一巡で収束しませんでした。ライタはブロックコンテナ項目の
  先頭コメントをシーケンスマーカーへ一段高く持ち上げ、次の読み取りがまた持ち上げました（libFuzzer
  `edit_yaml` crash-92e7b87c）。今はコメントを項目自身の本体に残します。また granit は空スカラの
  イベントをその下のコメント行より後へ遅延させるため、リーダはスカラの*下*にあるコメントをその
  先頭コメントとして取り込み、ライタがそれをスカラのヘッダの上へ持ち上げました（crash-12c96086）。
  下のコメントは今、スカラ自身の行が完結し、ドキュメント末尾前に実ノードが続く場合のみ次の兄弟へ
  載り、そうでなければ値自身の先頭コメントとして残ります（`docs/dev/quality-ledger.md` (lo)）。
- **エイリアスで終わるシーケンスの後の末尾コメントが移動しなくなりました** — 行内コメント付きの
  エイリアスで終わるシーケンス（`- *x  # A`）には `A` のスロットが無く、リーダはそれを本物の列 0
  末尾コメント（`# B`）の前に取り残し、ドキュメント末尾のフラッシュが `B` をルートの上へ押しやる
  ため、エディタの出力は一巡で収束しませんでした（libFuzzer `edit_yaml` crash-e3294ab5）。エイリアス
  末尾のコメントはシーケンス自身の行内スロットに載り、余分な末尾コメントは破棄されず先頭コメント
  として保存されるため、出力は固定点になります（`docs/dev/quality-ledger.md` (ln)）。
- **エイリアス末尾のコンテナ注釈が初回出力で固定点になります** — 最後の値がエイリアス
  （`*x`）であるマッピングに付いた注釈はその対の行末スロットに乗りますが、エイリアスは
  メタデータを持たないため、再読は注釈をその対の*キー*に振り分け、キーの書き手はそれを
  外側の `&a` ヘッダ上方へ持ち上げます。注釈は二巡目で移動していました。書き手は今、
  ブロックがエイリアス値で終わるとき、初回出力で注釈をヘッダ上方へ持ち上げます——再読が
  それを安置する位置です（`docs/dev/quality-ledger.md` (lm)）。
- **エイリアスをアンカー定義より上へ持ち上げる移動は拒否されます** — `*x` を含むサブツリーを、それが
  名指す `&x` の定義より上の目的地へ移動すると、リーダが `found unknown anchor` で拒否するテキストを
  出力していました（libFuzzer `edit_yaml` crash-aaf32b09）。set 入口は、ペイロードがエイリアスを含む
  とき、定義が目的地より前にあるかを問います：ペイロード内部の定義はそれと一緒に移動し、外部の定義は
  すでに上方になければなりません。そうでなければ `anchor-is-referenced` と答え、ドキュメントを変更し
  ません（`docs/dev/quality-ledger.md` (ll)）。
- **空のブロックスカラー上方のコメントが chomping 指示子を落とさなくなりました** — テキストが
  `>` または `|` で始まる独立コメント（例 `# >`）が空のブロックスカラー上方にあると、ヘッダ
  検出器がコメント内の記号をヘッダと誤読し、`>+\n` が `>\n` と再読まれて `Keep` 指示子が
  二巡目で `Clip` に減衰していました。検出器はコメント開始位置で走査を止め、本来のヘッダを
  読むことで、作者の chomping を固定点に保ちます（`docs/dev/quality-ledger.md` (lk)）。
- **JSON5 輸出は、解析器がテキストと読む数字の綴りを保ちます** — 整数解析の範囲を超える十六進の
  長い綴りはテキストに解決され、中枢の書き手がそれを引用していたため、一度の `from_json5` →
  `to_json5` 往復で JSON5 の数字が文字列に変わっていました。`write_plain` は、テキストがその出口
  自身の文法で数字トークンを綴っているときにそのまま通します——JSON の文法、および JSON5 モード
  での十六進・裸の点・前置 `+` の形——そして先に JSON の文法を尋ねるので、よくある綴りは一度の
  走査で済みます（`docs/dev/quality-ledger.md` (lh)、(li)）。
- **未知の `extends` 名は基底なしへの劣化ではなく拒否されます** — `extends: cored` はかつて
  基底をまったく持たないスキーマを登録していました：すべてのスカラはテキストのままで、`type: int` は
  `port: 80` を拒否するのに、何も綴りの誤りを指摘しませんでした。読み手は
  `unknown schema 'cored' in extends` と既知のスキーマ一覧を添えて答えます。インライン辞書入口は
  `extends` を同じテキストに書き込むため、一つの拒否で両方の入口をカバーします
  （`docs/dev/quality-ledger.md` (kh)）。
- **スキーマのテキスト入口は辞書入口と同じく空の `rules` を拒否します** — `register_schema` と
  `load_schema` は `rules: []`、`rules` キーの欠落、打ち間違いの `rule:` を受け付け、型変換を
  一切行わず診断も出さないスキーマを登録していました。インライン辞書入口は同じ形を拒否して
  いました。テキスト入口は三つの形すべてに `schema must contain a non-empty 'rules' list` と
  返すようになりました。スキーマ言語は検証ではなく型変換を行うため、この拒否が回復するのは
  診断であって検証ゲートではありません（`docs/dev/quality-ledger.md` (kg)）。
- **拒否は、拒否した側の形式を名乗ります** — `ParseError::Syntax` は YAML・JSON・TOML・schema の
  どの読み手も構築するのに、その `Display` はすべてのメッセージに `YAML parse error:` を付けて
  いました。そのため TOML の拒否は
  `YAML parse error: TOML parse error: unterminated array …` と読め、四つの JSON 入口は JSON の
  拒否を YAML のものと呼び、schema 文法の拒否は YAML が解析できたあとなのに YAML 解析エラーと
  名乗り、`register_schema` は YAML の受け渡しで接頭辞を二重に運んでいました。ラベルはメッセージを
  書く側のものになりました。前後で入口の応答 53 件を実測すると、YAML の 36 件はバイト単位で同一、
  16 件が変化し、そのいずれも JSON・TOML・schema の入口が自分のものでないラベルを手放したものです
  （`docs/dev/quality-ledger.md` (kc)）。
- **編集のページは起こらない三つの拒否を名乗っていました** — エイリアスを経由する書き込みは
  `cannot-edit-alias` を投げ、`set()` は `anchor-is-referenced` に答えると文書化されていました。出荷
  済みのビルドで実測すると `set`・`delete`・`rename` はいずれも `use: *x` を書き換え、
  `cannot-edit-alias` に届く `set` の経路は一つもありません — そのトークンは削除・リネーム・移動・メ
  タデータの各経路に住んでいます。エイリアスの*親*は依然として拒否され、エイリアスノード上の十二個の
  メタデータの動詞も同じです。`api/exceptions.md` は到達可能な十五個の理由トークンとそれぞれに答える
  呼び出しを一覧にし、`validate()` の二つの依存は使い手が触れる場所に書きました：本プロジェクトが配
  布するものは `jsonschema` をインストールせず、テキストとして渡したスキーマはまず `json.loads` で読
  まれるため、YAML つづりのスキーマは `json.decoder.JSONDecodeError` を投げます。
- **文書の先頭にあるタグヘッダーの下の注釈が、第一回の出力で決まります** — 自分の行に
  乗せられない注釈は、読み手が報告するヘッダーの上に書きます。ところがヘッダーを探す
  走査はヘッダー行より*前*の改行をたずねるので、ヘッダーが文書の第一行なら持ち上げが
  起きず、注釈は隙間に残ったままです。その位置では再読がそれをルートの注釈として扱う
  ため、次の出力がヘッダーの上へ移しました。`!base:` が字下げのない列を従える形で、
  第一回は `!base: ` / `# fuzz 47` / `- etss: &a0 !s: ~  # fuzz 47`、第二回は注釈行を
  先頭に置いていました。crash-92f3fc65 と crash-e392c402（81 と 82 バイト）と
  29 バイトに縮めた入力は、いま第一回で不動点になります。`fuzz/seeds/edit_yaml` の
  47 件はすべて緑に再生され、`cargo nextest run --all` は 895 件通過です。同じ回の
  三件目は別の置き場 — 行末注釈を読み手がひと階層上へ帰属させる形 — なので
  issue #732 に残します。
- **入れ子の `?` マーカーから持ち上げた注釈がヘッダーの隙間に落ちなくなりました** —
  `hoist_marker_note` は内側のマーカーに乗った注釈をそのマーカー自身の階層へ上げます。
  読み手が報告するのはその場所です。ところが上げられた行は書き手の末尾に足されて
  いました。そのマーカーが `&a !tag:` が先頭に立つ組の値にあるなら、末尾はヘッダー行の
  下の隙間です。granit はその行を終える改行までノードをまたぐので、再読は注釈をひと
  階層上へ帰属させ、二回目の出力がヘッダーの上へ移しました。いまこの書き込みも
  `note_line_above` が既に使う隙間の規則に従い、保留中のタグだけの行を先に閉じてから
  行います。issue #732 と #733 が名乗る入力をひとつずつ再生すると、17 件の
  `yaml_roundtrip` 入力が `serialization not idempotent` から不動点へ変わり（最小で 44
  バイト）、監査した集合では失敗 36 件から 19 件になります。`yaml_roundtrip` の 128 件は
  すべて緑に再生され、`edit_yaml` は 47 件、`cargo nextest run --all` は 896 件通過です。
  残る 19 件はそれぞれの issue に残します。
- **ブロックスカラーの `chomping` 指定子がその上の注釈行に耐えるようになりました** — 本文が
  空のブロックスカラーは、その前の行で読まれていました。ヘッダ探索は本文から直前の非空行へ戻るため、
  注釈に当たりヘッダが見つからず Clip と答え、作者の `+` を落とします。そのドキュメントは一度目で
  固定点になりませんでした — `# Irrr` と `>+4` がまず `>+`、次に `>` を出力します — つまり指定子は
  エンジンが書いたテキストから消えていました。ヘッダ探索は sigil の行自身へ退避し、それも上方の
  走査がヘッダを見つけなかったときだけに限るため、`>` で始まる内容行は従来の経路のままです。実測:
  この問題を引き当てた 2 件の fuzz 入力（`crash-aa8a0447`、`crash-95b66309`）は失敗集合から外れ、
  `yaml_roundtrip` は 9 から 7、`edit_yaml` は 14 のまま。2 件とも種子として登録し、コーパスは 284
  から 286、`seed_reach` はその四つの往復目標が当時保持していた 242 件のうち 11 件が届きません
  （この門は現在六つの目標を歩き、259 件のうち 10 件を報告します）。
- **深さ 1000 の TOML 文書は、Rust パニックでなく型あるエラーで変換されます** — `from_toml` はドット
  区切り鍵の列を深さちょうど 1000 まで読みます（読み手の予算がその値です）。そこで YAML 書き手にテキ
  スト形を求めると、同じ数で拒否されます。その拒否はかつて `serializer::to_yaml` の `expect` に落
  ち、Python には `PanicException: serialization failed: MaxDepthExceeded(DepthError(1000))` として
  届いていました。`Exception` ではないので、言語中のあらゆる `except Exception` を素通りします。四つ
  の変換（`from_json`、`from_jsonc`、`from_json5`、`from_toml`）はいまや一つの失敗しうる経路を共有
  し、既存の `max-depth-exceeded` 鍵で `YamlMaxDepthError` を返します。JSON の三方言は読み手が一段手
  前で止まるため、この症状を出しませんでした。実測：深さ 999 では四つとも 1,000,001 バイトを出力し続
  け、`tests/test_max_depth.py` の新規 3 件が境界を固定します — helper を `to_yaml` に戻すと 1 件が
  まさにそのパニックで赤くなります。これが直さないもの：YAML 読み手は granit 既定の
  `block_nesting_limit` と `flow_nesting_limit` の 255 で動いており（どちらも容器単位で数えます）、
  ライブラリがうたう他の深さ予算はすべて 1000 なので、255 容器を超えた変換は自家の読み手が拒否する
  テキストを返したままです（`docs/dev/quality-ledger.md` (jq)）。
- **schema の `type` 拒否は 5 つの綴りだけ挙げ、実際は 9 つを通していた** —
  `YamlTypeKind::from_name` は 5 つの正式名のほか `boolean`、`integer`、`double`、`string` も
  通すため、`type: integer` と書いた人は既に処理されていたのに、`type: number` の人には有効な
  集合が `null, bool, int, float, str` だと伝えて、欠けていない同義語を探させていました。拒否
  メッセージは `(aliases accepted: boolean, integer, double, string)` を添えるようになりました。
  受け入れる集合は変えておらず、ガイドの 5 行表は別名が仕様か偶然かの裁定を待つままです
  （`docs/dev/quality-ledger.md` (jz)）。実測：`register_schema` は四つの別名をすべて受理し、
  `number` と `Int` は拒否します。新しい名前付き用例はメッセージ中の別名一覧と四つの綴りの受理
  の両方を固定するので、どちらかを消すとこの実行は赤くなります。
- **空の merge ソースは普通のキーではなく、merge のエントリーではありません** — 2 つの shipped ルー
  ルが「`<<:` だけを持ち、何をも生やさないマッピング」に収束する場合、どちらのレベルが残るかで異なっ
  ていました。一つは「何も生やさない merge キーを merge 内容として貢献する（これにより外側の `<<` を
  消費）」を採用し、もう一つはそのようなソースを普通のキーとみなします。同一ファイルの他の陳述（特に
  `is_merge_key` は注記かアンカーは元データではないという立場を持っており）は、注記の行位置がどちら
  の解釈を含めかの唯一の deciding factor になりました——`860ec5b7`、`a3dded4d`、`d360e9fd` と
  `f3a2f8cf` は同じ綴りで二つのレベル、別の綴りで一つのレベルを量定しました。`collect_inline_pairs`
  は「キーが merge キーであり、ソースが null、スカラ、または alias である」pair をいまや除外します。
  これで空の merge ソースには解釈するためのイデンティティがありず、何も貢献しません：同じチェーンフ
  ォームの両方の綴りが二つの merge レベルを残します、そして (jg) が二つの解釈を釣り上げたものを一個
  の期待値に収めた主張が、別の綴りが到達することを主張しています（`docs/dev/quality-ledger.md`
  (jg)、(lj)）。実測：merge テスト 30 件、`pyrs-yaml-core` テスト 500 件、`cargo nextest run --all`
  の 919 件が全て通り、clippy の二つのスコープがクリーン、`prek run --all-files` がクリーンです。

#### 内部

- **`edit_yaml` は一つの名前が何組に答えるかを数え、名前が消えたかを問わない** — `rename` と `move`
  が動かすのは、検索が同一性の通過で解析するその一組です。文書が同じ鍵テキストを二つつづると、兄弟
  の一組は検索が移る綴りの通過でその名前に答えたままなので、「古い名前は消えた」は出力が立てる主張で
  はありません。2026-11-02 の `edit_yaml` 残り三件の入力がこの同型で（issue #732）、`!base k: 1` と
  `k: 2` なら 19 バイトで再現します。この層はこれから `duplicate_fold_count`（`on_duplicate` 方針が
  すでに使っていた兄弟カウンタ）に、各動詞が残した名前がちょうど一組減ったことを求め、`move` は
  `delete` の `all` の保証を借りず自分の主張を述べます。「一組も動いていない」と尋ねれば 19 バイトと
  26 バイトの入力がともに赤くなりますが、赤くなるのは語庫の `edit_yaml` 種子 45 件のうち 15 件で
  す。この数が受け持つ範囲は、そのために書いた二つの最小入力よりはるかに広い範囲に及びます。
  エンジンの答えは
  `rename_moves_one_pair_of_a_name_the_document_spells_twice` とその隣の `move` のテストで
  固定します。三つの入力と二つの最小入力をその語庫に加え、語庫は `-runs=0` で緑に再生され、
  マトリクスは Rust の `#[test]` 931 件と種子 302 件を読みます。

- **目標が拒否する種子は、保護として信用されず計上されるようになりました** — 六つの fuzz 目標はいず
  れも型ある拒否を通過として扱います（`yaml_roundtrip` と `edit_yaml` は `parse(Schema::Core)`、
  `json_roundtrip` と `parse_json` は三つの JSON 方言、`toml_roundtrip` と `parse_toml` は TOML の二
  つの門）。だから読み手が拒否する保存入力は `-runs=0` で緑に再生され、その入力を登録した理由である
  書き手の約束は一度も問われないまま、コーパスの総数だけがファイルを数えていました。
  `crates/pyrs-yaml-core/tests/seed_reach.rs` は各目標自身のエンジン呼び出しを問い、
  `.ci/seed-reach.txt` と実測がどちらの方向にも食い違えば赤になります。六つの目録の 259 件で届かない
  のは 10 件で、`scripts/quality_matrix.py` は一覧が名指す目標ごとに `seed-unreachable:<target>` を
  導出します — いま三件、いずれも解除条件付きで登録済みです。`parse_json` と `parse_toml` はこの項目
  を書いてから対象に入りました。`parse_json.rs:36` と `parse_toml.rs:57` は拒否で `continue` してす

  は投げます。`as_is`（既定）はまさにその答えであり、`error` は空キーと統合キーも拒否し、`last_wins`
  は `allow_duplicate_keys=True` が常に意味してきたもの、`first_wins` は先に現れたペアを残し、畳み込
  まれたペアの注釈とアンカーをその側へ運びます。二つの綴りを同時に渡すのは拒否され、知らない値は意図
  された四つを名乗り、すべての読み込み入口と十二個の CLI コマンドが `--duplicate-keys` を取ります。
  fuzz の対象は既定で解析するので、名前をつけた三つの代替値はまだあの層に入っていません。
- **`note_placement=` と `on_duplicate=` は残りの曖昧さを呼び出し側に置きます** — `&a` / `!tag` の見
  出しの下で、書き手はペアの行末注釈を読者が上として分類する位置ではなく見出しの隙間においていまし
  た。`note_first`（既定）は読み込みが置く位置に書くので最初の出力が不動点になり、`header_first` は
  古い位置を、定まらないものとして文書化して残します。二つの鍵は一つの名前をつづれる — タグかアンカ
  ーだけが区別するので、一方を消すと他方が再読時にその名前で答えていました。
  `delete(path, on_duplicate=...)` は `one`（既定）、`all`、`error`（`duplicate-key-target`、木はそ
  のまま）に答えます。`delete_path_with_policy` はアンカーの監視をやり直すので、エイリアスがまだ名乗
  る定義は宙ぶらりんで出力せず拒否されます。
- **`load_json_lines(text)` は NDJSON を一行ずつ読みます** — `__next__` ごとに一文書を解くイテレータ
  なので、10,000 件の流は全体 3.861 ms、第一件 0.343 ms で読まれ、行ごとの `load_json` は 8.440 ms
  かかります。空行・注釈だけの行・継続行は行を名乗って投げます。任意の `parallel` feature は分片ごと
  に自分だけの受け口とスレッドを与えます：200,000 行は一つの受け口で 112.3 ms、24 個で 18.9 ms
  （5.96x）。`parse_file` は任意の `mmap` の経路を得て、ファイル全体の確保を一つ減らします。既定は
  off です。
- **ストリームは受け手が言えば止まり、すべての事象が自分のバイトを名乗ります** —
  `parse_stream(..., on_event=...)` は最初のコールバックの前にすべてを集めていたので、`False` でも全
  体の走査分を払っていました。`EventSink` は今 `ControlFlow` を返します。`False` が止めるものはフォ
  ーマットの事実です：JSON/JSON5 は次の事象のバイトの前で止まり、TOML は出力を止めるので拒否された文
  書は先に投げ、YAML のアダプタは中断不能な解析のあと delivery を止めます — `load_stream` は YAML の
  増分の表面のまま。すべての `StreamEvent` は `offset`/`end` を運び、事象の辞書にも二つの鍵が入りま
  した。dumper は loader が返す tuple を受け取ります（`safe_dump(safe_load("? [a, b]\n"))` は受け入
  れた入力上で投げていました）。入れ子の鍵の列は引き続き `unhashable type: 'list'` を投げます。
- **テスト層は暗かった面を得ました** — フォーマット横断の注釈の橋（`json -> jsonc` と他にも四つの一
  方通行の組は一度も踏まれていませんでした）、YAML 型の鍵を持つ文書に対する JSON Schema の面の性質の
  層、三つの方言にわたる JSON の木の等値、古い生成器が届けなかった家族を名乗る生成式の Python の葉
  （`bytes`、日付、`Decimal`、無界の整数）、呼び出し箇所のない公開 callable を拒否する API の呼び出
  し表面の門 — あの門は `get_plugin` と `YamlDocument.flush_source` が一度も呼ばれていないことを突き
  止めました。fuzz の語庫は内務も整いました：種子のない成果物は `former-crash-*.seed` としてアーカイ
  ブされ、対象ごとに一件の issue を発見とともに開き、対象別の種子の個数を公開して門をかけました。

#### 修正

- **畳み込みが唯一の定義を落としたエイリアスは、使用に届く位置で定義を得ます** — 重複キーの畳み込み
  は `x` を定義するペアを落とすのに、生き残った `&x` はエイリアスより後ろの鍵に乗っていたため、`*x`
  はすべての `&x` より上に出て、読み手は自分の出力を `found unknown anchor` で拒否していました。修復
  は今、名前が*この使用より前に*定義されているかを尋ね、統合の通りは自分が削除する生き残りを内挿し、
  `delete_path` は鍵のノードのアンカーも読みます。エイリアスから書き直された鍵は着いた場所で畳まれ、
  引用符で終わるアンカー名はその名を保って、再読で引用ノードを開きません。
- **五つの往復の形が最初の出力で不動点に届きます** — `?` マーカーの本体の中の第一項目の注釈はもうマ
  ーカーの上へ登りません、ブロック列の第一項目は自分のダッシュの下に前置きのスタックを残します、マー
  カーの持ち上げは乗ってほしいしくない見出しを跨ぎません、タグのみの閉じが下の行を伸ばすとき注釈はも
  う値を二行に割りません、コンテナの最後のペアを消すことはその注釈をペアの行へ引きずりません。各自は
  `yaml_roundtrip` か `edit_yaml` のクラッシュ入力で、入力は種子としてアーカイブされました。
- **ノードのメタデータだけが区別する鍵は拒否されます** — 読み手はタグ付きの鍵を丸ごとのノードとして
  比較していたのに対して書き手はスタイルとアンカーを選ぶため、自分の出力が `duplicate key` で返って
  いました。鍵は今やタグと値で追跡します — YAML のスカラーの等値です — 統合も同じことを尋ねます。書
  き手が同じくつづる二つのコンテナの鍵については、コンテナの鍵が何をつづくかを書き手に尋ね、二つが等
  しく読み返るならその入力を拒否します。射影はテキストで鍵を引くため、`c: 0` と `!A c: "!"` は TOML
  の読み手が拒否し `json.loads` が一つに畳む項目を出しました：両方の書き手は今や
  `YamlSerializeError` を投げ、`to_dict`/`safe_load` はテキストを名乗る `YamlTypeError` を投げます。
  `to_yaml()` は変わりません。
- **繰り返された JSON の鍵は、置き換えた値の内の注釈を保ちます** — 重複の畳み込みは最初の位置と最後
  の値を保つので、落とす鍵と値のノード上の注釈だけ生き残りの側へ手渡していました。そのため落とされた
  コンテナの内の注釈も一緒に消えていました、一方でイベントのストリームはそれを報告していたのに。
  `subtree_notes` は今やノードとその下的一切を元の順で集めます。繰り返しの間に注釈付きの鍵があれば最
  後から二番目ではなく最後の値を残します。要素の二つの注釈の組は互いに上書きするのではなく一つのスロ
  ットに着き、ルートの行末の注釈はすべての入口で書かれます：`{"a": 1} // after` は `{"a": 1}` に往復
  しなくなりました。
- **JSON5 は数字らしく見えるだけの文字列を引用し、その拒否は自分の文法を名乗ります** — 裸のトークン
  の検査は数値の照査の前に先頭の符号を一つ落としていたため、`+-33337333333373333333733333` はこのエ
  ンジンの読み手が拒否するテキストとして裸で出されていました。符号なし本体の上の先頭 `+` だけが
  JSON5 のつづりなので、そういう文字列は引用され、`+7` と `+1.5` は裸のトークンを保ちます。鍵の位置
  ではメッセージは引用された鍵を要求していましたが、JSON5 は裸の識別子も取ります。文言は今や方言自身
  の旗から来ていて、厳密な JSON と JSONC は従来の文言を保ちます。
- **生きるスロットのなかった TOML の注釈が読まれるようになりました** —
  `to_toml("sec: # note\n  x: 1\n")` は `[sec]\nx = 1\n` を返していました：セクションの通りはマップ
  自身の行内スロットしか読んでおらず、ハブは鍵のノード上で鍵行の注釈を手渡すからです。五つのメンバの
  注釈スロットも同じく読まれておらず、一つの要素の注釈は二回書かれていました。すべてのペアが払いま
  す：執行イメージ上で `to_toml_medium` +1.58 %、`to_toml_long_strings` +1.25 %。
- **点線の経路も他のすべての降下と同じく限界を持ちます** — `parse_inline_table` はメンバの鍵のパスを
  `parse_value` の外に並べて展開しており、`DEFAULT_MAX_DEPTH` が効くのはその内側です。そのため 1,059
  区画は `from_toml` が受け、1.1 の読み手が拒否し、長い経路はネイティブのスタックを溢れさせました（2
  MiB のスレッドで `0xC00000FD`）。二つの降下は今ひとつの予算を共有します：1,000 区画なら往復して定
  着し、1,001 は型付きの `max depth exceeded` です。
- **登録済みのハンドラは自分が名乗るスカラーを所有します** — 両方の書き手は登録表より先に配列の経路
  と数値プロトコルを尋ねていたため、`numpy.ndarray` のハンドラは負け、`__bool__` だけを持つクラスは
  AST の経路が出せるのとは違う行に書かれていました。検査は float の形だけに向けて書かれていたので、
  `__index__` を持つ `python_type` は素通りされ、`Money(500)` は裸の整数としてダンプされていました。
  ハンドラの探索は今やあらゆる位置で最初で、`int` と `int` のサブクラスは整数のつづりを保ち、`str`
  のハンドラはテキストに手をつけません。
- **NumPy の配列のダンプは Python 3.15 でプロセスを終えなくなりました** — 配列の経路は `rust-numpy`
  を通じて対象を cast しそのメモリを読んでいましたが、`cp315-abi3t` の wheel ではそれを健全にできま
  せん。`safe_dump(numpy.arange(8))` はセグメンテーションフォルト（終了 139）で死にました。経路は今
  や配列自身に `dtype`・`shape`・`tobytes()` を尋ね、そのバッファを Rust で復号するので、どんな成果
  物も numpy の C API に触れません。二つの欠陥も一緒に倒れました：転置したビューは転置していない格子
  を書き、数値プロトコルは要素一つの配列に対して次元を落として答えるため、出力される shape はインス
  トール済みの numpy に依存していました。
- **注釈は自分の行を割れなくなり、ブロックスカラーは自分が持つ改行をつづれるようになりました** — 生
  成器は注釈のテキストを印字可能な ASCII からのみ引いていたので、一行の注釈の受け手が負う平坦化にど
  の性質テストも到達できませんでした。改行も引くと四つの性質が赤くなりました — 両方の書き手が改行の
  後のテキストを文書に入れてしまうからです。両方の書き手は今や改行を空白一つに平坦化し、改行を持つブ
  ロックスカラーは `~` で失う代わりにそれを引用します。
- **一行の文書のストリームが再び線形時間になりました** — `LineTable::line_col` は事象ごとにその行の
  先頭から文字を数え直していたので、改行を含まない元コードは事象ごとに O(n) を払いました：1.5 MB の
  圧縮された JSON の配列は 224,006 件の報告に 4.9 秒を費やしていました。いまは 19 ms で流れます。
  JSON と TOML はテーブルを共有し、YAML は自分の位置を計算するのでこの費用を持っていませんでした。
- **何も測らずに成功を報告できた門と監視** — 六個の検査スクリプトは空の glob、読めないパスの一覧、何
  も一致しない `--only` の名前のうえで OK を印字しており、六つとも今や終了 2 です。空のイテラブルで
  通っていた十個のアサーティオンは、測った個数を名乗る床を得ました。どの要求ファイルも名乗らない
  `importorskip` で `psutil` を要求していたメモリ上限 — すべてのレグがカバレッジに見えるスキップを報
  告していました — は、stdlib の `tracemalloc` のスケーリング不変量になりました（2,000 行と 200,000
  行の両方で追跡済み 3,168 バイト、バッファする走査は 199,854,440 バイト）。`yaml_edit` の順位表の行
  は「新しいリリース」を責めていましたが、固定済みのビルドは三つのフィクスチャすべてで投げていまし
  た：0.2.0 がインストール済みで、その行は自分が測るもので門がかかります。
- **報告された fuzz の発見が消えなくなりました** — ダウンロードはアーカイブのルートをクラッシュのデ
  ィレクトリへ直接展開していたので、`artifacts` と `collected` という二つの幻影の対象が生まれ、一つ
  のアーカイブの三件の入力は二件の issue に開かれていました。計数は `-eo pipefail` の下で
  `grep -c .` を使っており、空のアーカイブは issue を開く前にステップを終えていました。panic の署名
  は最初のコロンで止まっていたため、連続五回の定時実行は仕分けのできないもので赤く返っていました。対
  象はいずれかのルートの次の区画で、ゼロは報告できる計数で、署名は位置とメッセージの第一行を保ちま
  す。
- **公開済みのドキュメントの訂正** — `Node.is_valid()` は変更済みの文書も拒否すると書かれていました
  が、テストするのは文書の参照だけです。同じ `repr` は失効したノード・存在しない経路・辞書の射影が拒
  否する経路を一つにします — 読みはすべて `to_dict()` を通ります。`rumdl fmt` の MD038 の「修正」は
  コードスパンの*内側*の空白を消すため、五つのミラーと台帳が静かに書き換わっているのにフックは
  `Passed` を印字していました。MD038 は今や無効化されています。地域化された changelog のページは自分
  の節を版本の見出しと同じ階層に置いていたので、サイトは各自をその版本の兄弟として描画し、ミラーの検
  査もそれを読むようになりました。

#### 変更

- **単一文書ルートに頼まれた流は拒否されるようになりました** — `parse`、`parse_file`、`safe_load`、
  `to_toml` と `YAML()` の等価版は一つの文書を読むのに、二文書の入力は走査が最後に着いた方を返してい
  ました：`a: 1\n---\nb: 2\n` は `b: 2` でした。今や二番目の文書の位置で `multi-document-input` を開

  す。
- **すべての Rust のベンチマークは自分だけのプロセスで走り、両方のロックファイルは自分の範囲が許す最

  で、一つが残したアロケータの状態が次を染めることはありません。合併を決めるものは何も動きませんでし
  たが、この bump をまたいだ CodSpeed の傾向は一つの測定ではありません。`similar` 3.2.0 → 3.2.1 は八

#### 性能

- **書き手の出力は中間確保の料金を払わなくなりました** — あらゆる書き手は `String::new()` で始まって
  おり、その 512 バイトへの七回の再確保が設定ファイルサイズの書き込みの大半でした。門が固定した
  `rustc 1.97.1` の下で `to_json_medium` 22,884,635 → 17,718,056（−22.6 %）、`to_toml_notes`
  16,468,905 → 12,071,715（−26.7 %）、`serialize_block` 14,518,712 → 10,899,301（−24.9 %）、
  `serialize_note_flow` 64,411,669 → 59,227,943（−8.1 %）— 十六の書き手シナリオすべてが下がり、最小
  は `to_toml_long_strings` の −5.2 %。変わらない木は `to_json_medium` の床を +0.002 % で読みます。
  注釈の平坦化を一巡にしたことで、`to_jsonc_notes` と `to_json5_notes` は各自の PR がコミットした床
  より 38.27 % と 38.11 % 下に残ります。出力バイトは一つも変わりません。
- **文字列の本体、TOML の行、エスケープの走査は SSE2 で十六バイトずつ走ります** — SSE2 は x86_64 の
  baseline に含まれるので新しい依存はなく、`std` も要りません。ホストでは、5000 バイト文字列の 2 MB
  の JSON が 2.47 → 1.97 ms、2 MB の TOML basic が 2.36 → 0.99 ms、literal が 2.41 → 0.96、multiline
  が 3.37 → 1.01。執行イメージでは `from_toml_medium` −4.02 %、`from_jsonc_medium` −3.69 %、
  `from_json_medium` −3.55 %。エスケープの問いは `to_json_long_strings` の 75.12 % を測り、四つの長
  い値の書き手の床は −62.36 % から −60.37 %。短い値は別の形（約 26 %）で、一つだけ払いました —
  `to_json_medium` +0.52 %。
- **JSON の一行は八バイトずつ索引されます** — `pyrs_event::LineTable` は一歩ごとに UTF-8 文字を一つ
  数えていました。執行イメージではその歩みが `documents_long_strings` の 51.79 % を読みます。`u64`
  は一度に八バイトに答え、各候補のレーンは自分が主張するバイトに対して検査されます。

#### 変更

- **宣言された `%YAML` バージョンは要求時に尊重されます** — `parse`、`parse_file`、
  `parse_all_docs`、`safe_load`、`safe_loads`、`YAML(...)` へ `honor_version_directive=True` を渡す
  と、`%YAML 1.1` の宣言が 1.1 プロファイルを選べます（`flag: yes` は `True`、`012` は `10`）。
  `1.2`、`1.3`、宣言のない文書は引き続き Core で解決され、明示的な `schema` は宣言より優先されます。
  フラグが有効なとき、尊重された宣言はその `---` の前に `%YAML <version>` として再出力されます — 編
  集後や `reparse()` の後も同じで、Core の読み手が黙ってテキストの型を変えることもできません。既定の
  動作は変わらず、`schema` の既定値は `None` になったので「未指定」と「明示的な Core」を区別できま
  す。
- **`schema="1.1"` プロファイルは 1.1 が定義する数値族を解決し、書き手は型づけたものを引用します** —
  `1_000` は整数 1000、`0b101` は 5、`+0x1f` は 31、`+.inf` は無限大、`017` は 15 で、それぞれ
  PyYAML のローダーが同じテキストに答える値です。引用の検査はこのエンジン自身の Core の読み手だけに
  尋ねていたため、`safe_dump({"v": "1_000"})` は `v: 1_000` を出力し、PyYAML も ruamel も整数 1000
  を返していました。`8_0`、`0b101`、`+0x1f`、従来の bool の語 `yes`/`on`/`off`/`y`、日付のみの
  timestamp `1990-06-23`、`0x_1f` のように下線を伴う基数形は、1 ルートあたり 26 の綴りで同じ欠陥でし
  た。出力が変わるのはそれらの綴りだけ、`1_000` は `"1_000"` として書かれます。timestamp と
  sexagesimal はテキストのまま、`0o17` はここで型付きのままです（PyYAML はこれをテキストとして読む）
  — プロファイルは Core *plus* だからです。

  な TOML なのに、です。トークンのテキストは今や丸ごと保たれ、投影がある綴りにタグを付けるのは YAML
  Core が異なる値を解決するときだけです — `0x1f` と `+5` はタグなし、`1_000`、`0b1101_0110`、
  `-1_000` は `!!int` を運びます。値は変わらず `tomllib` と一致し、タグなしの引用符付き `"42"` は文
  字列のままです。
- **イベントストリームの注釈は自分の属するノードを告げます** — `StreamEventType::Comment` はフラグを
  1 つだけ持ち、二つの問いに同時に答えていました。注釈が自分だけの行を持っていたか（ソースについての
  事実）と、その注釈がどのノードに納められているか（ツリーについての事実）です。`owns_line` は前者を
  保ち、新しい `NoteOwner` が後者を運びます（`FollowingLeading`、`FollowingInline`、

  いに答えるので、見える細部が二つ出てきます: コンマの後に書かれた TOML の注釈は、以前の
  `standalone` ではなく `style: "inline"` を報告するようになり、TOML のテーブルの注釈はキーのイベン
  トの前にではなくその後ろに届くようになりました。

  `register_schema()`、`load_schema()`、`list_schemas()`、`YAML(schema=...)`、`rules:` の一覧は引き
  続き効きます。CLI の `validate` は `--schema`/`--schema-file` を一つの JSON Schema パラメータに束
  ね、どちらも与えられないときだけ構文を照査します。`TypeSpec`、`ValidateKind`、`ValidateRule`、
  `SchemaValidationError` は削除され、行列の `schema validation` 行もそれらとともに去り、fuzz 対象は
  `parse_schema` になります — 生き残った文法を fuzz するからです。

#### 修正

- **八つの注釈の位置が最初の出力で定まります** — ブロックのコンテナが自分の `&a` / `!tag` 行の上に書
  けなかった注釈は、1 ラウンドごとに見出しを一つ登っていました。見出しと本体の間に書かれたコンテナの
  注釈は見出しの上へ動き、コンパクトな項目の注釈は自分のシーケンスの見出しの上に定まり、ネストしたシ
  ーケンスに対するマッピングの注釈は項目のダッシュに着き、ブロックシーケンスの項目の注釈はマッピング
  全体をそれぞれ自前の行へ押し出し、タグだけの行（`- !fuzz2`、`{a: !t }`）は注釈を乗せる本体を残さ
  ず、シーケンス自身の注釈は自分の項目の中へ動いていました。八つのうち七つは `edit_yaml` のクラッシ
  ュ入力で、修復が入力を受け継ぐよう種子としてアーカイブされました。マッピングの注釈のケースはテスト
  名で固定されています。どのラウンドでも何も失われていなかったことこそ、他のどの層もこれを見なかった
  理由です。
- **空の値は、解決される null のつづりで書かれます** — `k:` と `-` は、それ自身のつづりが `~` である
  null として再読されるため、最初の出力は第二ラウンドでしか定まりませんでした。書き手は今や、本体が
  空になるところならどこでも null のテキストを書きます（ネストした値、ルートの値、シーケンスの項目、
  フローのペア、フローの項目）。タグ付きの空はそのままにします — タグは解決を抑えるため、本体はそれ
  を定める `''` のつづりを保ちます。アンカーは同じ場合ではなく、`- &a3` は `- &a3 ~` と書かれます。
- **アンカーを孤児にする編集は、書かずに拒否されます** — アンカーの改名、メタデータを運ばないままそ
  のノードを置き換えること、定義を移すこと、メンバが `&x` を運んでいたコンテナへの `set` は、いずれ
  も成功に答えて、このライブラリ自身の読み手が拒否するテキスト（`found unknown anchor`）を出力してい
  ました。それぞれの拒否は `anchor-is-referenced` に答えます。門はエンジンにすでにありましたが、四つ
  の入り口がそれを迂回していました。そこでその問いは、落ちる場所でおこなうようになりました。実際に宙
  ぶらりんになる別名の集合より意図的に広くしています — 別名は自分の名の*最も近い先行する*アンカーに
  束縛されるので、後方の `&x` が生かしていたはずの改名も拒否します。過剰に拒否すれば編集がもう一回増
  えるだけ、拒否が不足すれば何も読めないファイルが書かれます。
- **重複キーの畳み込みが落とすアンカーは、放置されずに内挿されます** — 畳み込みは*値のサブツリー*が
  `&x` を定義している項目を落とすのに、修復パスへ手渡されていたのは落ちた項目自身のアンカーだけでし
  た。そのため出力は、何も定義していない定義を名乗っていました。畳み込みは今や、ツリーを去るすべての
  定義を登録するので、生き残った使用はそのアンカーとともに内挿され、出力は 1 ラウンドで読み返せま
  す。
- **マージがマッピングへ二つ目の null 鍵を与えることはありません** — `~`、`null`、空の鍵、裸の
  `Null` ノードはすべて null に解決され、読み手は二つの null 鍵をあえて畳みます。しかしマージのフィ
  ルタは別の問いを尋ねていました（タグなしスカラーにはテキスト、それ以外にはノード全体の等値）。その
  ため `<<` の由来側が、マッピングがすでに持つものとは別に null の鍵を提供し、出力は `~:` を二度書い
  ていました。属性層が 20,000 件のケースで見つけました。
- **JSON5 と JSONC は、自分たちの文法が許すものを受理します** — 出荷済みのスタブは `load_json5` につ
  いて "Accepts the full JSON5 grammar" と書いていましたが、`\xHH` エスケープはどこでも解析されませ
  んでした（二桁は 1 バイトずつ積み重なります。`from_str_radix` が `\x+1` を受理してしまうためで、厳
  格な JSON と JSONC はこの形を拒み続けます）。引用符のない鍵の中のバックスラッシュ u エスケープ、文
  字列の中の CRLF・LS・PS の前のバックスラッシュは今や解析されます。ダブルクォートの JSON5 の文字列
  は CR と LF を除くすべての C0 バイトを運べます — RFC 8259 の規則が、厳格な JSON ではなくこの方言へ
  適用されていました。Unicode の空白だけの鍵（`U+2028`）が `null` に失せることもなくなりました。JSON
  の解決器は Unicode の規則でプレーンスカラーを削るのに、引用の規則は ASCII の空白と NBSP しか知らな
  かったためです。三つの方言をわたって鍵と値の両位置で Unicode の `White_Space` 全 25 コードポイント
  を洗い、同じバイト列について厳格なローダーは RFC に拘束されます。
- **長い整数のつづりで書かれた JSON の文字列は、ハブを通っても引用符を保ちます** — `i64` に収まらな
  い桁の並びに対して Core は `Str` と答えますが、JSON は整数リテラルに上限がありません。そのため
  `"9999999999999999999"` はプレーンスカラーとして投影され、`to_json` はそれを数として書き戻していま
  した。投影は、文字列を裸で書く前に JSON 自身の数値文法に尋ねるようになりました。
- **出力先の形式がつづれない値は、発明されず、拒否か書き換えです** — TOML に文法が無い YAML の float
  のつづり（`083e6`。Core の指数形は先行する 0 を許しますが、TOML の `float-int-part` は許しません）
  は、通り抜ける代わりに値からレンダリングされます。符号付きのゼロは `0` として書かれます — TOML に
  負のゼロは無く、`ist = -0` は `0` として再読されていたためです。TOML がそのペアの後に置けないルー
  トのテーブルは、マッピングを並び替えずに自分の位置をインラインで保ちます。空になったブロックシーケ
  ンスは自分のダッシュ行を保ちます。
- **`extends` を省いたスキーマは、文書が告げるとおりに解決します** — 既定は `core` ですが、パーサー
  は鍵が空の値で存在するときだけ Core に到達していました。そのためそれを省いたスキーマはすべてのスカ
  ラーをそれ自身のテキストとして型づけし、裁定の両側が何も言わずに逆転していました。`type: int` が
  `port: 80` を拒否し、`type: str` がそれを受理します。このエンジンが見つけない基の名前に対して依然
  として fallback はありませんが、それは公開されたエラー表面に関する別の決定です。
- **そのままつづられた `!<tag:yaml.org,2002:X>` は、`!!X` として登録されたプラグインに届きます** —
  YAML 1.2 §6.8 は二つのつづりを同じタグにしており、ローダーは自分で名指す五つのタグではすでにどちら
  も尊重していました。他のすべての名前では登録簿がレンダリング済みのテキストで鍵をひくため、
  `!<tag:yaml.org,2002:widget> 7` は `!!widget` プラグインを無視して整数 `7` を読んでいました。文書
  が使ったつづりが先に試されるので、二回目の探索は外れたときだけ払われ、YAML の名前空間の外にある
  URI は現在の読みを保ちます。
- **`pyq` はレンジをレンジとして答え、`--json` を二度同じふうに出力します** — `[0:2]` は鍵の分岐へ通
  り抜けていたため、`.list[0:2]` は `0:2` という名の鍵を引いて `null` に答えていました。文法は自分が
  アドレスできない `:` を拒否し、シェルはその構造を名指して拒否しますが、引用符付きの角括弧は引き続
  き鍵です。`pyq get --json` は一つの一致ではインデントし、多数の一致ではそれぞれを 1 行に書いていた
  ため、`.servers` と `.servers[*]` はそのフラグの意味について食い違っていました。今やすべての一致が
  同じレンダリングを受けます。`--as jq|yq` のもとでは、文書が持たない経路は `null` を印字して終了コ
  ード 0 で抜けます — 二つの本物のツールと同じで、ネイティブの `pyq get` は見逃しを報告して 1 で抜け
  ることを続けます。
- **黙って漂流していた文書が直されました** — ローカライズ済みの API ページは `parse_file`、
  `parse_all_docs`、`safe_load`、`safe_loads` を一つまたは二つのパラメータで説明していましたが、出荷
  済みのスタブは五つと六つを宣言します。`honor_version_directive` は利用者向けのどのページにも現れ
  ず、`reparse()` は拡張が使わない `schema` の既定値付きで文書化されていました。署名の門は今や四つの
  ロケールすべてで `ast` を通して両側を突き合わせます。`safe_dumps_async` は import できるのに
  `pyrs_yaml.__all__` に欠けていました。ベンチマークのページは CodSpeed が `WallTime` で走ると書いて
  いましたが、追加以来ずっと `mode: simulation` です。そこでミリ秒の表は CodSpeed の出力ではなく、1
  台のマシンで記録した実時間の読みとして注記されました —「small」の Rust の文書が 19 B で Python の
  表の 95 B であり、同名の行は比較できないことも含めます。

### [v0.16.0] — 2026-10-01

<details markdown="1">
<summary>厳格な `load_json` と外部の値オラクル · コア・パッケージ・CLI に届く JSONC/JSON5 · TOML 1.1
と toml-test が要求した拒否 · 往復で生き残る注釈と表記 · TOML/INI ハブ · `pyrs-yaml` と `pyq` ·
ネイティブコア · インタプリタの abort · 高速経路</summary>

#### 追加

- **`load_json`（厳格 RFC 8259）で `load_*` 一族がそろう** — `pyrs_yaml.load_json(s)` は正規文法
  だけを受理し、`//` と `/* … */` コメント、末尾カンマ、一重引用符文字列、裸の `Infinity` / `NaN`、
  `0x…` には型付き `YamlParseError` で答える。高速経路は `load_jsonc` と `json_fast::try_load` を
  共有し、非正規なバイトでは必ず抜ける。拒否した入力は STRICT な `from_json` AST パーサ経由で、
  `from_jsonc` には決して流れない。`pyrs_yaml.__init__` から `__all__` に再エクスポートし `.pyi` を
  再生成したため、CLI が到達する全形式（`to/from json|jsonc|json5|toml`）に `load_*` の兄弟がいる。
- **エンジンが返す値を、エンジンの所有しない読み手が採点する** — PyYAML と ruamel.yaml との値の
  一致を、正規 YAML Core 1.2 ドキュメント 20 件 × パリティ面 5 − ドキュメント化された乖離 2 件
  （duplicate-key の厳格性、YAML 1.1 従来 bool の schema-scope）= 122 比較で確認した。pyrs /
  `tomlkit` / `tomllib` の三者一致は 11 の正規構造に対する 24 比較で確認し、`>i64` は仕様準拠に
  固定した（TOML v1.0 §Integers: 64-bit signed）。`-2^63` は `tomlkit` を引き続き通過する。
  `pyrs_yaml.load_json(doc) == orjson.loads(doc)` は 16 ドキュメントで一致。これらのライブラリは
  これまで並べて計測されるだけで値の比較が無かった。orjson を権威にするのは、stdlib の
  `json.loads` が `allow_nan=True` で `NaN` / `Infinity` を受理するため。
- **JSONC と JSON5 がコア・パッケージ・CLI に届く** — `pyrs_yaml_core::json::from_jsonc` と
  `from_json5` は `from_json_with_options(text, JsonParseOptions)` の上に載る。`JsonParseOptions` は
  `allow_trailing_commas`、`allow_single_quoted`、`allow_unquoted_keys`、`allow_comments` を軸ごと
  に切り替え、`STRICT`、`JSONC`、`JSON5` をプリセットとして提供する。JSONC は空白が合法的な場所
  ならどこでも `// line` と `/* block */` を通す（`tsconfig.json` / `settings.json` 方言）だけで、
  それ以外は通さない — RFC 8259 の厳密な上位集合であり、`from_json` は引き続き RFC 8259 を強制する。
  `to_json_text` / `to_json_text_pretty` は AST に注釈が残ってもコメントを無視するため、保持は
  オプトイン。`pyrs_yaml.from_jsonc` / `load_jsonc` / `from_json5` / `load_json5` と
  `YamlDocument.to_jsonc()` / `to_json5()` は `json.dumps` ではなくネイティブエンジンを経由する —
  `pyrs_yaml.from_jsonc(...)` は `AttributeError` を投げていた。`emit_root_leading` はルートの
  `leading_comment` を最外側の `{`/`[` より前に書き、`pyq from-json` は
  `--jsonc` / `--json5` を得た。
- **JSON5 は JSON が拒否する字句と数値を受理し、どちらも元に戻す** — 引用なしキーは Unicode の
  `ID_Start`/`ID_Continue` 集合全体を通す（`unicode-ident`、新規依存）。区切りは RFC 8259 の 4 つに
  垂直タブ、フォームフィード、NBSP U+00A0、すべての Unicode `Zs` 空白、U+2028/U+2029、ZWNBSP
  U+FEFF を加える。文字列は行終端直前のバックスラッシュ、二重引用符内の `\'`、`\v`、`\0` を加える。
  数値は `0xDECAF`、`0XFF`、`-0x1F`、`.5`、`5.`、`+7`、`+.25`、`07`、`Infinity`、`NaN`、
  `-Infinity` を加え、それぞれ原文をそのままプレーンスカラーに残す。このすべては JSON5 に限定して
  おり、厳格な `from_json` と `from_jsonc` は引き続きこれらのキーに引用符を要求し、該当バイトを
  一つも受理せず挙動は一バイト変わらない。`\uXXXX` 内の孤立 UTF-16 サロゲートも引き続き拒否する —
  Rust の `String` は保持できないため。`Schema::Json5` はロード時に `0x1F` を `31`、`Infinity` を
  `float('inf')` と返し、`to_json5_text` / `to_json5_text_pretty` は単一の書き手 `Mode`
  （Json / Jsonc / Json5）の下で表記を復元する：`ScalarStyle::SingleQuoted` タグのスカラーは
  一重引用符、裸の数値トークン、`//` に正規化されたコメント、キーは常に引用符付き。
- **TOML は toml-test が不正とする文書を拒否する** — 公式コーパスを型タグアダプタで toml-test の
  `{"type": ..., "value": ...}` 形に載せ替えて再生し、バイト列として読む — `read_text()` が
  パーサに見える前で bare CR を LF に書き換えていたためだ。数値の UTC オフセットは範囲検査に入る
  （時 00..=23、分 00..=59）ので、`+12:60` / `+24:00` は失敗する。C0 制御コードと DEL U+007F は
  basic・literal・マルチライン文字列内で拒否する（タブのみ、マルチライン形式では改行も合法的）、
  コメント本体でも同じで、CRLF ペア外の bare `0x0D` はパース入口の中央走査で拒否する。点線鍵が
  暗黙に作ったテーブルは後続の `[header]` に閉じられ、`[tbl]` のあとの `[[tbl]]` は失敗する —
  1.0 と 1.1 の両方で不正 — 合法的な暗黙スーパーテーブルは引き続き解析される（30 → 21）。先頭ゼロ
  （`01`、`007`、`-01`、`01.5`）、基数接頭辞つき整数の符号（`+0x1F`、`-0b101`、`+0o644` —
  `signed-int` は 10 進整数しか包まない）、端や連続のアンダースコア（`1_`、`1__0`、`0x1_`）が
  拒否に変わった（71 → 48）。インラインテーブルは定義済みパスと同一・拡張・被覆の関係にある点線鍵
  （`{ a = 1, a.b = 2 }`、`{ a.b = 1, a = 2 }`）を拒否し、`{ a.b = 1, a.c = 2 }` は引き続き合法
  （48 → 39）。
- **TOML 1.1.0 文法、そして日時がついにデコードされる** — `from_toml` は 2025-12-18 公開の v1.1.0
  仕様を解析する：インラインテーブルは複数行にまたがれ末尾カンマも許される
  （`{\n a = 1,\n b = 2, \n}`）、`\xHH` は 0x00..=0xFF のコードポイントを覆い、`\e` は
  U+001B（ESC）を表し、秒は省略可能で、`t = 14:15` と
  `dt = 2010-02-03 14:15` はバイト安定に往復する。
  `TomlDialect::V1_0` と `from_toml_v1_0` は 1.0.0 に固定する利用側のため残り、1.0.0 の文書は両方言
  で同一に解析され、1.0 モードで `T` 無し日時を認識していなかった `space_time_sep` の off-by-one も
  修正した。日付のみ（`1979-05-27`）と時刻のみ（`07:32:00`）は別々の `!date` / `!time` タグを
  持つ（局所およびオフセット日時は `!timestamp` を維持）ようになり、*正当な* TOML で素の
  `ValueError` を投げる代わりに `date.fromisoformat` / `time.fromisoformat` へ
  流れる。`!time` は下限の 3.8 に合わせて省略秒を補い、`!timestamp` は小文字の
  `t`/`z` を正規化し、両者はいかなる精度の小数
  フィールドもマイクロ秒に正規化する（TOML は `.6` を許す、3.11 前の `fromisoformat` は 3 桁または
  6 桁のみ）。`datetime.fromisoformat` が `Z` を認識するのは 3.11 以降なので `...Z` は `+00:00` に
  なる。
- **TOML 往復は注釈・形・表記を保つ** — パーサはペアやヘッダーの上に独立した行の `# ...` と、
  同じ行の `key = value # ...` / `[name] # ...` 注釈を `NodeMeta::comment` に取り、
  `to_toml(from_toml(src))` が同じ位置へ再出力するため、`pyq edit` と `YamlDocument.set()` は注釈を
  剥がさなくなった。文書冒頭の `# note` も生き残り、コメントなし文書は余分な行を出さない。
  インラインテーブル内部の注釈はメンバー自身のスロットに載り、装飾のないテーブルはコンパクトな
  `{ a = 1, b = 2 }` の一行を保ち、配列にネストされた装飾付きテーブルは複数行のインライン形へ、
  トップレベルの装飾付きテーブルは `[section]` へ昇格する。修正によって `skip_all_blank` が
  露出した — 独立コメント自身の終端改行を空行として数えていた。マルチライン文字列（`"""…"""` と
  `'''…'''`）は `ScalarStyle::Literal` の YAML ブロックスカラーとして投射され、エスケープした一行に
  なる代わりに `"""` ブロックとして再出力される。単一行の `"a\nb"` は単一行のまま。`to_toml` は
  元の空行の区切りを再現する（`a = 1\n\nb = 2` はバイト安定に往復）が、文書最初のペアの直前だけは
  除く。16 進（`0xDEADBEEF`）、8 進（`0o755`）、指数つき浮動小数（`1e10`、`-3.14e-2`、`6.02E23`）は
  基数接頭辞を保ち、アンダースコア区切り、明示的な `+`、2 進（`0b101`）は YAML Core に規則が無いの
  で 10 進へ正規化する。
- **どのエンジンが書いた独立注釈も、一つとして扱われる** — `NodeMeta` は
  `leading_comment: Option<Comment>` と `blank_before: bool` を増やす（どちらも構造的な `Hash` /
  `PartialEq` から除外）。そのためセクションヘッダーや array-of-tables の要素は上の注釈*と* `]` の
  後の行内注釈を同時に保持でき、JSONC のメンバーも両方を載せる（上の `// ...` は `leading_comment`
  へ、`... value // trailing` は `comment` へ）— 単一スロット模型では表現できなかった形だ。
  granit-parser レシーバーが `comment(standalone = true)` ではなく
  `NodeMeta::decor.leading_comment` へ移った最後のエンジンで、`NodeMeta::eq` / `Hash` は同じ概念を
  どこに載っても同一視するため、解析済み YAML は手構築フィクスチャと引き続き等しい。
  `CustomNode::set_leading_comment` / `remove_leading_comment` / `remove_comment` は両スロットを
  アトミックにクリアし、書き手は `standalone = true` の `comment` へフォールバックするので、手構築
  ノードは変わらず描画され、厳格 JSON は依然 `//` を出さない。`to_yaml(toml_ast)` /
  `to_yaml(json_ast)` は先頭注釈を保ち、Python は `Node.remove_comment()` に並べて
  `Node.leading_comment` を得る。

  `from_toml(toml: str) -> str` と `to_toml(yaml: str, schema=...) -> str` は TOML ⇄ YAML テキストを
  変換し、`load_toml(toml: str) -> dict` は datetime を内蔵の `!timestamp` プラグイン経由で Python
  値として実体化する。TOML 文字列は再解決されないため `"true"` の値は文字列のまま。
  `load_ini(text: str) -> dict` は stdlib の configparser で INI を読む — 厳格、大文字小を保持、
  INI に公式文法が無いので設計上は読み取り専用。TOML 出力は表現不能な形（null 値、table 以外の
  ルート、別名、スカラー以外のキー）を安定したメッセージで拒否し、コメント・アンカー・splice の
  往復編集は設計上 YAML 限定のまま。`YamlDocument.to_toml()` は `to_toml(doc.to_yaml())` の代わりに

  `YAML().load_stream*()` が常に返していたクラス `YamlStream` は、いま import 可能だ。
- **`pyrs-yaml`、コマンドライン** — `pip install "pyrs-yaml[cli]"`（Python 3.10+）は Cyclopts 上の
  純 Python で 18 のコマンドを加えるため、ベースインストールは追加依存ゼロと Python 3.8 サポートを
  保つ：`fmt`（コメント・アンカー・順序を保つ往復整形）、`get`（JSONPath に
  `--format yaml|json|text`）、`set` / `delete` / `rename`（`--inplace`、`--string`、
  `--create-missing`）、`sort-keys`、`move`（既存の宛先へ）、`frontmatter`（Markdown
  フロントマター、本文の分割は任意）、`validate`（CI フレンドリーな終了コード、相互排他の
  `validate --schema <name>` と `--schema-file <path>`）、`compliance`（YAML Test Suite レポート、
  `--json`）、`to-json` / `from-json`。すべて `-` で stdin を読み、既定は stdout。`to-toml` /
  `from-toml`、`to-jsonc` / `from-jsonc`、`to-json5` / `from-json5` は `to-json` / `from-json` に
  倣い、`-A/--all-docs` はすべての編集・変換動詞をカバーする。ただし移動は両方のパスが解決する各
  ドキュメントに適用される。
- **`pyq`、実行時に Python を要さないネイティブ Rust CLI** — `crates/pyrs-yaml-cli`（clap ベース、
  `cargo install --path crates/pyrs-yaml-cli`）は `pyrs-yaml-core` を jq/yq スタイルのコマンドライン
  の裏側に置く：`fmt`、`get <path>`（JSONPath-lite — 点線キー、`[n]`/`[-n]`、角括弧キー、`*`、
  `--json`/`--raw`）、`set` / `delete`（`--create-missing`、`-i/--inplace`）は注釈と値のスタイルが
  残るよう再シリアライズされる。`rename` / `move` / `append` / `insert`、任意パスの `sort-keys`
  （ルートは `$`）、`validate` は構文チェック、または `--schema rules.yaml` によるスキーマ言語
  ルールへの検証、`frontmatter --body-out`、`to-json` / `to-toml`、インポータの `from-json` /
  `from-toml` / `from-ini`、形式は拡張子で決める（`--input` が上書き）、stdin は `-`、失敗時は core
  の安定したエラーテキストを携えて非ゼロ終了。
- **`pyq` の絞り込みはフラグであり、式言語ではない** — `--select 'PATH OP LITERAL'`、
  `--sort-by PATH` / `--desc`、`--unique`、`--first` / `--last`、`--skip N` / `--take N`、
  `--join SEP` は `select -> sort -> unique -> slice` → `join` という固定順で走る。式言語ではなく
  フラグなので、比較する型が混ざれば `false` と答える（jq との乖離として文書化済み）。
  `pyq completion` は `clap_complete` 経由で bash、zsh、fish、PowerShell のスクリプトを出力する。
  `-A/--all-docs` はすべての編集コマンドと `to-json -A` に及び、各ドキュメントはストリーム内の自分
  の区切りに対して splice される（`MultiDocEditor` + `DirtyUnit::shifted`）ため、触れていない
  ドキュメントとすべての `---` 区切り行は元のバイトを保つ。配線中に `move_path` が移動先 INSERT
  ユニットのみを返し、移動したサブツリーが重複していたことが露出した。

#### 変更

- **granit-parser 1.1 → 1.3、そしてアップグレードが黙って失わせた厳格性** — 1.2.0 は特殊な
  ドキュメント制限向けのオプションの `Options` フィールドを加え、1.2.1 はいくつかの解析結果を YAML
  仕様へ向けて厳格化し、1.3.0 はデフォルト実装付きの `Input` メソッド 2 つ
  （`fetch_block_scalar_line`、`take_quoted_scalar_ascii_chunk`）を加えて、スキャナがブロックおよび
  引用符付きスカラーのバイトをより速く進められるようにした。本プロジェクトは
  `Parser::new_from_str` 経由でパーサを消費し `EventReceiver` /
  `SpannedEventReceiver` のみを実装して `Input` は実装しないため、ソース変更は
  不要だった。動かされた判定が一つある。1.3 は続き行の
  インデントが enclosing のブロックキーより深くない複数行フローコレクションを*受理*するようになった
  （yaml-test-suite `9C9N`：`flow: [a,` のあとの行頭 column 0 の `b,`）ため、厳格性は
  `405/406 → 404/406` へ後退した — スイートの ≥95% しきい値の内側なので CI は緑を報告した。
  ツリー内のパース後ガードが過少インデントの続き行を拒否し、今は `405/406` を回復している。ガードは
  パーサが既に計算済みの span しか読まない。
- **ネイティブな JSON と TOML コア、`serde_json` と `toml_edit` は消えた** — `pyrs-yaml-core` は
  RFC 8259 エンジン（バイトレベルのスキャナ、数値は原文表記を保つため `from_json → to_json` が
  バイト安定で大きな整数と倍精度浮動小数の精度も失われない。型付きの行/列エラー。末尾カンマ・
  先頭ゼロ・孤立サロゲート・未エスケープの制御文字・複数ルート文書の拒否）と、全文法に及ぶ TOML 1.0
  エンジンを搭載する — bare/quoted/dotted キー、すべてのエスケープ形を備えた basic/literal/
  マルチライン文字列、アンダースコア区切りを許す 10 / 16 / 8 / 2 進整数、`inf` / `nan` と指数形を
  含む浮動小数、オフセット付きと局所の日付・時刻・日時。すべての拒否は granit-parser と同じ流儀で
  0-indexed の `line`/`col` を携えた `ParseError::Syntax` として表面化する。CLI、bindings、
  パッケージングの表面は変更していない。
- **`YamlDocument.validate()` はコンパイル済み validator をキャッシュする** — JSON テキスト*でも*
  dict でも、スキーマに対する初回の検証が成功すればコンパイル済みの `jsonschema` validator を
  保持するため、以降の呼び出しはスキーマ解析・メタスキーマ検査・validator 構築を省く。dict
  スキーマはオブジェクト同一性をキーにし、ディープコピーのスナップショットガードの裏側に置く。
  その場での変更は `==` で検出し、透過的に再コンパイルする。キャッシュ経路は
  `exceptions.best_match(validator.iter_errors(instance))` を送出し、`jsonschema.validate()` と
  同一の意味論を持つ。WSL の実時間：`document_validate` −98%（660µs → 13µs）。
- **出荷済みビルドと食い違っていた文書を書み換えた** — numpy ガイドの 0 次元節は 0-D 配列が
  「単一要素リストへ reshape される」（`assert data == [42]`）と述べていたが、出荷された挙動は素の
  スカラーへシリアライズする（`assert data == 42`）ため、
  `docs/{en,zh,ja,ko}/guides/numpy.md` を修正し、0-D `bool` → `1.0` という rust-numpy の癖に関する
  警告を加えた。各ロケールページでは `saphyr-parser` を `granit-parser` に、YAML 適合率 98.1% を
  99.75%（405/406 ケース）に、ABI3 サポート 3.9–3.13 を 3.8–3.15 に変え、ベンチ表は現在の CodSpeed
  の数値（parse は PyYAML より 21–43×、serialize は 55–177× 速）を載せ、Rust のベンチ節を
  Criterion から divan へ移した。

#### 修正

- **悪意のあるテキストがインタプリタを abort しなくなった** — 固定長のエスケープ読み取りは
  1 文字 1 バイトを前提に `&self.text[pos..pos+width]` をバイトオフセットで切っていたため、JSON の
  `\u` や `\x`、TOML の `\xHH` / `\uXXXX` / `\UXXXXXXXX` のあとにマルチバイト文字が来るとスライスが
  文字の途中で終わりプロセスが panic した。これらの読み取りは現在バイトバッファをスライスして
  UTF-8 検証を通すため、不正なエスケープはクリーンなパースエラーを返す。バイト単位で進み U+00A0 や
  U+0251 で `&str` を文字の途中で切っていた TOML の basic および multi-line basic 文字列パーサも、
  文字全体を消費するようになった。もう一つの abort は `0xC00000FD` STACK_OVERFLOW：TOML パーサには
  ネスト予算が無く（JSON の `DEFAULT_MAX_DEPTH`、YAML の `parse` の `max_depth` とは違い）、
  `parse_value` → `parse_array` と `parse_inline_table` が無制限に再帰するため、
  `load_toml("a = " + "["*5000 + "]"*5000)` が Python 例外も出さずにインタプリタを殺していた。
  `depth` カウンタが 1000 超で型付き `ParseError::MaxDepthExceeded` を返し、JSON と対称になった。
- **`<<` はマージできるソースのときだけマージされ、リテラル `<<` キーは生き残る** —
  `safe_dump({"<<": None})` → `<<: null` → `load` は `{}` を返してキーを失っていた（`<<: 1`、
  `<<: "x"`、他のキーと並んだ `<<:` も同じ）。レゾルバはすべての `<<` をマージとして扱い、Null や
  スカラーのソースを何もマージせずに消費していた。YAML では、マッピングへの別名、インライン
  マッピング、またはそのシーケンスのときだけこのキーはマージになる。そのため Null や
  プレーンスカラーの `<<`、および別名を含まず何も生まない `<<`（`<<: []`、`<<: [1, 2]`、
  `<<: {}`）は通常のキーで、今は往復を生き残る。別名を含む経路は常に消費されたままで、
  `<<: [*a, *a]` は再展開できない。適合率は `405/406` のまま。
- **アンカーガードはパススコープ化され、自己マージは終端し繰り返し別名は解決する** — 展開が自分
  自身のアンカー（`a: &a` の中の `b: {<<: *a}`）へ戻る `<<` は `resolve_merge_keys` の中で無限に
  展開され、インタプリタを落としていた（Windows の終了コード `0xC00000FD`）。循環ガードはマージ対の
  *収集*時のみ適用され、展開の*走査*時には適用されなかったためだ。いまはアンカー名はその展開が走査
  されている間も再帰パスにとどまり、そのパス上の祖先へ戻るマージは空の展開として終端する — 非循環
  AST は PyYAML の循環 dict を持てないため、自己マージは `{}` に収まる。同じ一巡で他の二つの意味も
  定まった：`<<: {x: 1}` はマージされ、マージシーケンス内の非別名要素（`<<: [*a, {y: 2}]`）は
  インラインマップを保つ。`to_dict()` には鏡写しの欠陥があった。別名を消されない*グローバル*な
  visited アンカー集合の裏側で展開していたため、最初の参照だけが値を作り、以降は黙って `None` に
  劣化していた（`{a: &x {p: 1}, b: {q: *x}, c: {q: *x}}` では `b` は値を、`c` は `None` を得る）。
  ガードは 1 回の展開中だけ push してあとで pop するため、真の循環は依然として終端する。
- **NumPy シリアライズは GIL なしで Python メモリを読まなくなった** — ndarray の書き手は
  `unsafe { as_slice() }` で配列のバッファを借用し、その借用を *`py.detach` の内側*、つまり GIL
  解放後に反復していた。`&[T]` は出所を問わず `Send` なので、そのメモリを Python が所有し他の
  スレッドが下で配列を resize や書き込みをしうることを借用チェッカは捉えられない。バッファは GIL を
  保持したまま Rust 所有のメモリへスナップショット（`slice.to_vec()`）し、スカラー→ノード変換だ
  けをスレッド外で行う。bindings 層で唯一の `unsafe` なバッファ借用であり、他のすべての
  `py.detach` 箇所も Rust 所有の状態（AST、ソーステキスト、`BufWriter<File>`）だけを触ると監査済み
  だった。
- **失われ、誤配置され、重複し、trim されないままだった注釈** — JSONC/JSON5 の値より前にある
  file-leading な `// note` は*行内*注釈と分類される（空白スキャナのヒューリスティックでは
  オフセット 0 の前に改行が無い）ため、`emit_root_leading` が注釈したルート容器ではなく最初の object
  メンバーが奪い、空の `{}` やルートスカラーでは完全に消失していた。JSON/JSONC/JSON5 **および
  TOML** の書き手は注釈本体を無加工で出力していたが、すべてのパーサは trim して保存するため、
  `text = " "` は pass を重ねるたび行末空白が振動していた。コメントのみの TOML 文書（`# note` の
  あとに key が無い）は空のルートを `""` へシリアライズしていた。YAML パーサは進行中の全コンテナで
  単一のコメントスロットを共有していたため、ネストされたコンテナの開始が AST に届く前の独立行
  ヘッダー注釈を消していた — スロット処理は現在コンテナごとのスタックである。そして、ペア自身の
  独立注釈を再生成テキストに載せた splice は旧注釈行を飛ばして両方が残っていたが、注釈行まで広げた
  範囲でもう起きない。5 フォーマットすべてが先頭注釈のバイト安定な不動点に達した。手構築した空で
  ない TOML ルートに独立注釈と先頭要素の注釈の両方を載せると、TOML テキストでは再帰属できない隣り
  合う 2 行の `#` として描画される — 実際の解析では生まれない形だ。
- **シリアライザは任意の深さで再解析可能な YAML だけを出力する** — ネストキーの下（`a:` の次に
  `b: |`、そのあとに本体）の字句スカラー・畳み込みスカラーは、`b: |` ヘッダーの下一段ではなく列 0
  から固定の 1 段で本体を出力していた。そのためすべてのネスト形で、出力が再パースするとエラーか
  誤値になっていた。スカラーの書き手は `block_base`（親行の列）を全出力箇所へ貫流させ、7 種のネスト
  形すべてでテキスト一致となった。同じ門が 5 つの表記を落ちた。自前の行へ追い込まれたマッピング値
  は、子（スカラー、null、flow 容器）が自分のヘッダーを書く場合でも子の anchor/tag を先出しし、
  `A: !a` のあとに `!a null` と二重に押していた。flow コレクション内のブロックスカラー（`[|`、
  `{k: >}`）とキー位置はダブルクォートへ降格する — flow 構文にはインデント付き本体の余地が無い
  ためだ。自前行を開始する flow 容器は行頭インデントを失い、complex key（`? …`）は値標識 `:` を
  列 0 に出して enclosing コレクションを何でも閉じていた。独立コメントか tag を本体に載せる
  complex key は曖昧なテキスト（行中の `? # c`）をシリアライズしていたため、注釈は `?` 標識の上へ、
  本体は 1 段深い自分行へ移す。flow コレクション内で端の空白を持つプレーンスカラー（`" %"`、
  `" "`）、または `,` `[` `]` `{` `}` の flow 標識を埋め込むものはクォートする。tag 付きの空 block
  容器はヘッダーを `{}` / `[]` と同じ行に畳み込み、compact な `- key: value` 項目は独立注釈付きの値
  をインライン化しない。
- **TOML が合法な最小 i64 を受理する** — `from_toml` / `load_toml` は `-9223372036854775808`
  （`i64::MIN`、TOML の定義では範囲内）で失敗していた。符号付き経路は `-` を外して
  `9223372036854775808` を符号なし i64 として読むため、反転が走る前に溢れていた。いまは符号が桁と
  一緒に解析され（`i64::from_str` は負方向に累積）、符号付き浮動小数は指数表記を保ったまま反転し、
  `pyrs_yaml.load_toml("a = -9223372036854775808")` は `{"a": -(2**63)}` を返す。これは
  TOML/JSON/JSONC/JSON5 を stdlib の `json` / `tomllib` / `pyjson5` オラクルに対して型厳密の同値で
  検証するプロパティテストから出たもので、既知の AST 曖昧表記 2 種も同時に固定している：裸の JSON5
  `Infinity`/`NaN` リテラルと、忠実性の契約により書き手が原文のまま出力する i64 超の数字列。

#### 性能

- **`safe_load` はイベントストリームを一巡して Python オブジェクトを組み立てる** — `safe_load`、
  `safe_loads`、`YAML().safe_load*` は完全な `CustomNode` AST を組み立てて `convert.rs` でもう一度
  走査しなくなった。プレーンスカラーは同じ schema チェーンで解決し、マッピングキーは原文の意味論を
  保ち、重複キーエラーも同じように報告される。一方、アンカー・tag・merge・マルチドキュメントの形は
  ゼロコストの事前除外（`&` のバイト含有チェック、区切り行の走査、ペイロードレベルの `<<` 検査）の
  裏側で AST パイプラインにとどまる。WSL の実時間：`safe_load_scalar_types` −21~25%、`safe_load`
  一族 −13~18%、フォールバックは変化なし。イベント span でアンカーを再生する変種は実装し、
  アンカー付きドキュメントで +48% と測られて撤回した。
- **JSON は双方向で高速経路にとどまる** — `load_jsonc` は正規の strict JSON（オブジェクトと配列、
  `i64` 整数、真偽値、`null`、エスケープなしの文字列）を中間の `CustomNode` AST を飛ばして直接
  Python オブジェクトへ解析する。AST 経路より約 5-6 倍速で、stdlib の `json.loads` も上回る。
  非正規な入力（浮動小数、エスケープ、コメント、範囲外整数、末尾カンマ、不正トークン）は一般経路へ
  退避するため、値とエラー報告は変わらない。浮動小数（正しく丸められ CPython の `float` と一致する
  parse）と 8 種の単純な 2 バイトエスケープも高速経路に加わった — ログ形式のペイロードでは約 15 倍
  速く、`\u` と不正なエスケープは引き続き AST 経路にとどまる。`YamlDocument.to_json` は
  `to_dict()` + `json.dumps` の代わりにネイティブエンジンを使い、ASCII はバイト単位同一で約 10 倍速
  （1200 項目のドキュメントは ~1450µs → ~120µs）。マッピングキーは `key_text` 経由でキーごとに
  `String` を作らず出力バッファへ直接書き（~60µs、さらに約 2 倍）、エスケープ不要の文字列は 1 回の
  `push_str` で一括コピーする（約 35%、41 → 27 ns/item、バイト単位同一）。JSON のシリアライズは
  インストールされている競合に対して #2 と測られ、上回る orjson は無い。挙動の変更が一つ：
  `to_json` は非 ASCII を `\uXXXX` エスケープではなく `to_jsonc` / `to_json5` と揃えて生の UTF-8 で
  出力する — それでも `json.loads` が同じように解析する正当な JSON だ。
- **コンテナ、レシーバー、エラー契約を単一ソース化した** — mapping と sequence のレンダリングは
  一つの `write_container_node` スケルトンを共有し（出力はバイト単位同一、`serialize_*` の中央値
  −5~11%）、パース入口は一つの `load_ast` エラー契約を共有し、schema チェーンは
  `bool_word`/`numeric_tail` を共有し、`register_anchor` と standalone/inline の分類
  （`is_standalone_placement`）は全レシーバーで単一化され、パス編集メソッドは `apply_metadata_edit`
  に委譲する。重複率は 5.25% → 3.45% → 2.60% に動いた。
- **読み手は必要のありえない仕事を飛ばす** — `extract_anchors` は `&` のバイト含有チェック 1 回で
  空を返すため、アンカーなしドキュメントは文字単位の引用符状態機械を完全に飛ばす（`parse_large`

### [0.3.0] — 2026-07-27

<details markdown="1">
<summary>NumPy ndarray 逐次化（N-D）· 引用符スカラーの型 · 負数の往復</summary>

#### 追加

- **NumPy ndarray シリアライズ** — `safe_dump()` / `safe_dumps()` / `from_dict()` / `dump_file()` が
  全次元（0-D から N-D）の `numpy.ndarray` をサポートするようになりました
    - 対応 dtype：`int8/16/32/64`、`uint8/16/32/64`、`float32/64`、
    `complex64/128`、`bool`
    - 多次元配列は正しいインデントでネストした YAML リストとしてシリアライズ
    - 複素数は `(re+imj)` 文字列形式でシリアライズ
    - `0-D` スカラー配列は 1-D に reshape され、単一要素リストとしてシリアライズ
    - ゼロコピー dtype ディスパッチ用の `PyUntypedArray` + `PyArrayDyn`
    （`numpy` Rust crate 経由）
    - 最大パフォーマンスのためのスライス反復時の GIL 解放
- **`quoted_scalar()`** — 単一引用 YAML 形式を必要とする値用の
  新 `CustomNode::quoted_scalar()` コンストラクタ
- **引用付きスカラーの型解決** — 引用付き負数の正しいラウンドトリップのため
  `resolve_yaml_type` が `SingleQuoted`/`DoubleQuoted` スカラーに適用されるようになりました
- **包括的 NumPy テストスイート** — 全 dtype、次元（0-D から 4-D）、
  負の数、無限大、NaN、空配列、エッジケースをカバーする 42 個のテスト
- フローコレクション（`{}`/`[]`）のラウンドトリップサポートを
  Mapping/Sequence AST ノードの `flow_style` フィールドで追加
- `parse()` が `str` と `bytes` の両方の入力を接受
- `parse()` がマージキー展開のオプトアウト用 `resolve_merges` パラメータをサポート
- saphyr イベントによる複数ドキュメントパース用 `parse_all_docs()`
- `indent_size`、`explicit_start`、`explicit_end`、`sort_keys` パラメータ付き
  `to_yaml_with_options()`
- デフォルト値パラメータをサポートする `get()`
- YAML をファイルに書き込む `dump_file()`
- `benches/yaml_bench.rs` の Criterion ベンチマーク（パース/シリアライズ/ラウンドトリップ）
- マトリクステスト付き GitHub Actions CI（3 OS × 4 Python バージョン）
- アンカー名パーサーが全 YAML 1.2 仕様（ドット、コロン、ハッシュ、引用アンカー）に拡張
- `__version__` 属性、`py.typed` PEP 561 マーカー

#### 修正

- **負の数ラウンドトリップ** — YAML 1.2 のブロックシーケンスに `-` で始まるプレーンスカラーは含めら
  れないため、負の数はシリアライズ時に引用され、整数/浮動小数点数として正しくパースされるようになり
  ました
- **N-D 配列サポート** — 1-D のみに限定されず任意次元の配列をサポートするよう
  `PyArray1<T>` を `PyArrayDyn<T>` に置換
- **正しいネスト深さ** — 多次元配列がちょうど N レベルのネストを生成
  （shape[1..] が内部次元を処理、ルート次元が `plain_sequence` でラップ）

  `None` ではなく参照値に解決されるようになりました

  saphyr のドキュメントイベントを使用
- パース中のマッピング/シーケンスタグが廃棄されなくなりました
- `format_scalar_for_key()` が Literal/Folded ブロックスカラー形式を処理するようになりました

  `find_standalone_comment_before`、`format_yaml_type`（テスト専用）
