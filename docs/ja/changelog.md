### [v0.18.2] — 2026-10-22

### 追加

- **キャンセルされた CI レグは自動的に再実行されます** — `.github/workflows/ci-rerun-cancelled.yml`
  は pull request 上で CI ワークフローが終了したときに発火し、`scripts/ci_rerun_gate.py` 経由で、あ
  るレグが `cancelled` なのに他のレグは緑で `failure` はゼロ、というときだけ、試行回数の上限を超えな
  い範囲でその実行を再実行します。上限はループを防ぎます。以前は `cancel-in-progress` の置換やランナ
  ーの回収でキャンセルされたレグが、変更とは無関係な理由で必須の `Test matrix (all legs)` 判定を赤に
  し、人が Re-run を押すまで合併できませんでした。判定の受理集合は変えていません — `cancelled` は今
  も合併を拒む — ゆえにこれは例外ではなく再試行 one つを足すだけです。`tests/test_ci_rerun_gate.py`
  は決定を双方向で、配線を契約として固定します。

- **YAML エンジンは標準ライブラリを持たないターゲットでもビルドできるようになりました** —
  `pyrs-yaml-core` は `#![no_std]` になりました。パーサー、ラウンドトリップのシリアライザ、コメント
  を保つ編集層、スプライスは `core` + `alloc` だけで動き、その下にある `granit-parser` はもともと
  std なしでビルドされていました。`std` feature は既定で有効なままなので、Python バインディング、
  CLI、各ベンチマークは従来の API を保ったままです。`std` が足すのはエンジンそのものではなく OS を要
  する三つの面だけです。翻訳済みのエラーメッセージカタログ（rust-i18n はプロセスグローバルな locale
  を持ちます）、実行時のスキーマレジストリ（グローバルな `RwLock`）、そして regex を使う利用者定義ス
  キーマ言語です。`no_std` の呼び出し側は `pyrs_schema::types::Schema` のバリアントを直接組み立てて
  スキーマを選びます。`ci.yml` の三つの `no-std-check` ステップは `thumbv7em-none-eabi` 用にこの
  crate をビルドし、その単体テストをホストで走らせるようになり、`tests/test_no_std_gate.py` は
  `#![no_std]` を宣言した crate のルートから foundation 一覧を読み取ります。no_std に入ったのにゲー
  トに入っていない crate は、無言の抜けではなく赤の判定になります。`no_std` ビルドはすでに出現したス
  カラーキーを `HashSet` ではなく crate の順序付きノードマップに記録します。`alloc` にはハッシュ関数
  がないためです。`parse_medium` の割り当て上限は 74 回で、std ビルドの 67 回より各マッピング 1 回多
  く、`tests/alloc_gate.rs` は feature ごとに上限を記録します。

- **no_std の記述は、実際に宣言されている crate と突き合わせられるようになりました** — foundation の
  一覧は `#![no_std]` と書いた crate のルートから読み取られ、`tests/test_no_std_gate.py` はそれをさ
  らに二つ、`ci.yml` の三つの `no-std-check` ステップと、現行の文書が名指しする crate と突き合わせま
  す。`AGENTS.md` にはずっと無かった `no_std` の foundation の記述が加わり、`docs/dev/boundaries.md`
  のそれを指す段落は、YAML エンジンがこの集合に加わったあとも五つの crate を名指ししていました。そう
  言えたはずのゲートは注釈にすぎないものでした。日付のついた記録は対象外です。`CHANGELOG.md` とその
  四つのミラー、そして `docs/dev/quality-ledger.md` は歴史であり、歴史は五つの crate からなる
  foundation を名指ししてかまいません。書かれた時点での事実だからです。

- **crate マトリクスは記述ではなく測定で保たれるようになりました** —
  `scripts/check_rust_python_decoupling.py` が manifest 自体からマトリクスを導出し、四つの規則を
  強制します。cdylib の crate はちょうど一つ（拡張本体）、他のどの crate の依存の閉包にも Python
  ランタイムの crate は入らない、拡張 crate は Rust のテスト階層を持たず `[lib] test = false` を
  宣言する、そして `required-features` の各項目は宣言済みで既定ではない feature を名指しする、で
  す。このゲートは厳格な TOML リーダーを自前で持つので `cargo` も `tomllib` も要らず、本
  パッケージと同じ Python 3.8 の下限で動きます。cargo が無い Python のテスト腿でも動くのはその
  ためです。`tests/test_rust_python_decoupling_gate.py` が反証の制御です。どの規則についても合成
  ツリー上で破り、判定が反転することを要求し、リーダーはこのリポジトリのすべての manifest を
  `tomllib` と突き合わせ、リーダーが読み取れない manifest は通過ではなく終了コード 2 を返しま
  す。`crates/pyrs-yaml/Cargo.toml` は `test = false` を宣言するようになり、cargo は拡張のテ
  ストターゲットを組み立てません。`prek.toml` のフックは manifest か crate に触れた変更ごとに
  このゲートを走らせます。

### 変更

- **イベントストリームのコメントはどのノードのものかを語ります** — `pyrs-event` の
  `StreamEventType::Comment` はフラグを 1 つだけ持ち、`standalone` と呼ばれていました。そのフラグは
  2 つの問いに同時に答えていました。コメントが自分だけの行を持っていたか（ソース的事実）と、コメント
  がどのノードに納められるか（ツリー的事実）です。ツリーが納めた場所へ戻したい利用者は 2 つ目の問い
  を尋ねられません。よってフラグは 2 つになりました。`owns_line` はソース自身の答えを保ち、新たな
  `NoteOwner` enum がツリーの答えを運びます: `FollowingLeading`、`FollowingInline`、
  `PrecedingLeading`、`PrecedingInline`。利用者が組み立てる順に名付けられており、`following_*` は
  これから利用者が組み立てるノード、`preceding_*` は直前に組み立てたノードです。
  `StreamEventType::Comment` を組み立てる Rust の呼び出し側は同じ変更の中で合わせて更新され、
  これらの crate は公開されていないため、出荷済みの API は動きません。`parse_stream` の Python
  呼び出し側が見る `style` キー（`standalone` / `inline`）は変わらず、新しく `owner` キーが同じ
  4 つの綴りで追加されます。3 つの producer はいずれもコメントを納めたノードから新しい問いに答える
  ので、ストリームとツリーは食い違いません: YAML の producer はノードに続くコメントをそのノードの
  行内スロットへ、次のノードへ先行するコメントをそのノードの前置きリストへ置きます。TOML の
  producer はテーブルの自身のコメントをテーブル名の後に報告します（`[a]` の上のコメントが先行する
  のは `a` が持つマッピングであって名前ではないため）。JSON の producer はツリー自身の規則に従って
  各グループのコメントの向きとスロットを報告します。ここから見える差が 2 つ出ます: コンマの後に
  書かれた TOML のコメントは `style: "inline"` を報告するようになり、以前の `standalone` とは
  違います。そのコメントは自分の行を持っていず、どのものかは `owner` が語ります。TOML のテーブルの
  コメントは、キーのイベントの後に届くようになりました。JSON の producer はコメントのオフセットの
  ためにソースを読み直すこともやめました（オフセットは記録と一緒に運ばれます）ので、ストリームの
  走査は二度とテキストを読みません。この分割はツリーとストリームに同じ問いを投げるテスト層が証明
  します: `crates/pyrs-yaml-core/tests/event_notes.rs` は 14 の文書を二度ずつ歩き、ツリーが納めた
  すべてのコメントが同じスロット、同じ向き、同じ行所有の事実で報告されることを検証します。JSON と
  TOML の replay suite はコメント全体を比較し、片方のフィールドを読み飛ばしません。1 つの JSONC
  文書は自身のイベントから畳み直され、厳格な writer を通した往復で同じテキストに戻ります。

- **`rules:` スキーマ言語が外部から判定される** — `tests/test_parse_schema_spec_table.py` は、文法が
  受け付ける各 `type:` 名について、本リポジトリが所有しないものに問いかけます。あるルールが解決する
  値は、その名が指し示す JSON スキーマ型のインスタンスなのか。この帰属は `jsonschema` が裁定し、
  Python の `bool` が `int` のサブクラスであるにもかかわらず `boolean` と `integer` を排反に扱うた
  め、型を誤ったルールは同意ではなく赤い実行になります。各行は同じ値が満たしてはならないおとり型を伴
  い、確認がゴム印に落ちぬようにしています。`Schema rule language` 行の `external authority` セルは
  `no` から `yes` へ移り、`authority-tier:schema-rule-language` の穴は登録解除され、
  `.ci/quality-holes.json` は再び空になりました。`scripts/quality_matrix.py` はオラクル集合に
  `jsonschema` を加え、認定がテストの実際に呼ぶ読み手から来るようにしました。ファイル名の接尾辞では
  ありません。

- **分離ゲートが bench レグを守る** — `scripts/check_rust_python_decoupling.py` に規則 R5 を加えまし
  た。拡張 crate は `required-features` を伴わない `[[bench]]` 目標を持ってはなりません。その種の目
  標はあらゆる workspace 級 bench コマンドに選択され、CI の bench レグが今除外した
  `pyo3-build-config` のインタプリタ探索を再構築してしまうからです。ゲートは四規則でしたが、この第五
  規則が bench レグのスコープ化で得たものを固定し、`crates/pyrs-yaml` に無条件の bench が将来現れれ
  ば、結合の静かな再帰ではなく失敗ランになります。`tests/test_rust_python_decoupling_gate.py` は合成
  ツリーで R5 を壊し判定の反転を要求します（反証制御は 13 本）。そしてクリーンなワークスペースは引き
  続き通過します。

- **CI の Rust ベンチマークレッグもインタプリタを不要に** — CodSpeed の `Rust benchmarks` は、Python
  ランタイムをビルドに取り込んでいた最後のレッグで、原因はテストレッグと同じく依存エッジではなく
  workspace の*メンバーシップ*でした。`cargo codspeed build` は全メンバーを選択するため、`pyrs-yaml`
  の cdylib と、インタプリタを探す `pyo3-build-config` のビルドスクリプトをコンパイルしていました。
  `yaml_bench`（`pyrs-yaml-core` 内）も `cli_bench`（`pyrs-yaml-cli` 内）もバインディング crate に依
  存していません —— `cargo tree -i pyrs-yaml` は workspace のどのメンバーも挙げません。このレッグは
  テストレッグが以前から使っていた除外に合わせ
  `cargo codspeed build --workspace --exclude pyrs-yaml` を実行し、インタプリタを探すものが作業内に
  なくなったため `setup-python` ステップも削除しました。本ツリーの実測：スコープ化後も `yaml_bench`
  と `cli_bench` は選択され、`pyo3`/`numpy` のコンパイル数はゼロです。`ir_gate` ターゲットは影響を受
  けません —— `ir-gate` でゲートされ、CodSpeed ベンチマークではなく、`scripts/ir_gate.py` が CPython
  を起動すると明示的にビルドするときのみ構築されます。

- **Rust のベンチマークは測っている crate に置かれます** — divan のベンチマークセットは
  `crates/pyrs-yaml/benches/yaml_bench.rs` から `crates/pyrs-yaml-core/benches/yaml_bench.rs`
  へ移りました。47 個のベンチマークが測るコードは以前とまったく同じです。バインディング crate は
  エンジンの API を再公開していただけなので、どの import も名前が変わっただけで、それ以外は
  変わりません。ベンチの package closure はバインディング crate から受け継いだ 6 つの Python
  ランタイム crate（`pyo3`、`pyo3-ffi`、`pyo3-macros`、`pyo3-macros-backend`、
  `pyo3-build-config`、`numpy`）を落とし、1 つも持ちません。ベンチのバイナリはもともと Python
  ランタイムに依存していなかったのです。Linux の `DT_NEEDED` に `libpython` はなく、Windows の
  import テーブルに `python3.dll` はありません。ただしそれはいかなるシンボルも参照しない依存を
  リンカが剪断したからにすぎません。今は依存そのものが無いので、独立性は構造的なものであり、
  ゲートが assert できます。拡張モジュールは `libpython3.12.so.1.0` への独自のリンクを保ちます。
  Python 拡張はそうあるべきものです。測られるコードは変わっていないので、見える違いは CodSpeed
  ID の package セグメントだけで、ベンチマークの項目は `pyrs-yaml-core` の下で再ベースラインされ
  ます。

- **イベントストリームと merge 解決器はアンカーを crate のノードマップに保持します** —
  `#![no_std]` の crate は `std::collections::HashMap` を名前で持てないため、
  `event_to_stream_event` と `resolve_anchor_name` は `&mut NodeMap<usize, String>` を受け取り、
  merge 解決器のアンカーテーブルも `NodeMap<String, _>` になりました。AST がすでに使っていた
  `FxHasher` 上の `IndexMap` そのものなので、アンカーの順序は挿入順になり、キー参照も実測で
  安くなります。命令数ゲートの YAML シナリオで、木は `parse_anchors` -2.36%、
  `parse_inline_merge` -2.32%、`parse_medium` -0.15%、`parse_small` -0.21% 動きました。確定済みの
  下限は触っていないので、ゲートがこれら二つのシナリオで受け入れている余裕は速い方向に古くなり、
  実行イメージでの更新を待っています。

- **Ir ゲートは cargo の要約ではなくコンパイラ自身の診断を表示します** — harness のビルドが
  失敗したとき、これまでは
  `error: could not compile pyrs-yaml (lib) due to 1 previous error` だけが表示され、続きが
  ありませんでした。ゲートは `--message-format=json` でビルドするため、rustc の診断は
  `compiler-message` レコードとして stdout に移りますが、表示していたのは `res.stderr` だけ
  でした。隠れていたのはゲートが最も説明すべき失敗——リンクエラー
  `rust-lld: unable to find library -lpython3.12`——であり、手作業で cargo を再実行して初めて
  見えました。`build_diagnostics()` はビルドストリームの rendered 診断をすべて連結し、stdout に
  一件もない場合にだけ stderr の末尾へフォールバックします（ツールチェーン欠如や不正な
  manifest であり、コンパイルエラーではありません）。
  `tests/test_ir_gate_diagnostics.py` は両方のストリームとフォールバックを固定し、stderr だけを
  返す実装へ戻す変異で 3 件中 2 件が失敗しました。

- **標準の JSON Schema 面は公式コーパスによって判定され、独立した行を持ちます** —
  `Document.validate()` は評価を Python の `jsonschema` に委ね、AST からインスタンスへの変換、
  schema の受け付け、`YamlValidateError` 契約だけを本リポジトリに残します。そのため、マトリクスの
  既存の `schema validation` 行は*別の*面——`validate_against_schema()` が評価する、本リポジトリが
  発明した規則言語——を測っていました。新しい `JSON Schema validation` 行は
  `tests/test_document_validate_suite.py` が公式 JSON-Schema-Test-Suite（コミット `0b4a7fa`、
  46 ファイル、1302 ケース）を再生することで `yes` と記録されます。`jsonschema` 4.26.0 での実測:
  1261 ケースがコーパスの結論に達し、`refRemote.json` は契約境界としてファイルごと除外され
  （リゾルバーを公開しておらず、除外を生かすために代表 1 ケースだけを試行）、10 個の
  `dynamicRef`/`vocabulary`/`\p{...}` ケースが委譲先エンジンの境界として名付けられています。
  同じコーパスを `jsonschema.validate()` で直接再生しても全 1302 ケースで同じ結論になるため、
  変換に帰属できる除外はありません。除外集合はインストールされたバージョンで切り替わります——
  Python 3.8 レッグは 4.23.0 を解決し、`unevaluatedProperties` の 1 ケースを追加で除外する必要が
  あります（4.25.1 で修正済み）——そして両方向を検証します。名前付きのケースが通り始めても、
  名前のないケースが落ち始めても失敗します。発明された言語はこのコーパスの信用を借りず、登録済みの
  穴 `authority-tier:schema-validation` を保持します。その出口は、`Document.validate()` に置き換え
  れば穴が閉じると明記するようになりました。

- **`rules:` 規則言語は固有の行を再び持ち、その盲点も再び名前を得る** — マトリクスの schema 段落は、
  2026-10-21 に検証器を退役させた後も、規則言語の「Rust の入口点は削除済み」と書いていました。
  しかし*言語*そのものは残っています。`parse_schema_yaml()`、`RuleResolver` と `YamlTypeKind` は今も
  `pyrs-yaml-core` が公開しており、`register_schema()`、`load_schema()`、`list_schemas()`、
  `YAML(schema=...)` は今も `rules:` ブロックをそれ経由で読みます。表にはその行がまったくなく、
  ページは表面が四行だと主張しながら実際には五つを納品し、登録表は `holes: []` と書かれていました。
  外部の読み手なら誰にも反論できない文法を、その作者自身のテストだけが測っていました。今回の行は
  手書きではなく導出です。`scripts/quality_matrix.py` は各行の単体層と属性層を、その表面を宣言する
  ファイルに限定する。だからこの言語は `crates/pyrs-yaml-core/src/parser/yaml/schema_language.rs` の
  十一個の `#[test]` と、この言語を指名する唯一の属性 `prop_schema_parse_no_panic` だけを記録し、
  YAML エンジン了整个の crate 件数ではありません。往復列と parity 列は `n/a` です。この言語は
  スカラー型の解決だけを行い直列化器を持たず、この文法には比較対象になる二つ目の実装も存在
  しないからです。authority 列は `no` であり、それが正直な答えです。この文法は本リポジトリが
  発明したものであり、単体層・属性層・fuzz 層の三層はいずれもエンジン自身の信念を問うにすぎません。
  計測は盲点 `authority-tier:schema-rule-language` を導出し、登録表は検証可能な出口とともに
  それを受け取り、`QUALITY_MATRIX.md` は盲点表でそれを名指します。よって登録表は再び中身を持ち、
  そして新たな第二の証偽制御が、退役した検証器の記号が確かにないことと、生き残った言語が確かに
  存在することの両方を主張します。ページが「削除済み」へ漂流することは、もう起こりません。

- **スカラーパスに対する `sort_keys` は、暗黙の成功ではなく文書化された no-op になりました** —
  `sort_keys("$.a")` は `None` を返して何も変えず、`sort_keys("$.missing")` は `YamlEditError` を
  送出するのに、同梱物はそのことを何も述べていませんでした。レジストリ項目はこの不一致を記録し、
  出口は「存在しないパスと同じように答えるか、同梱のスタブに no-op であると明記する」でした。
  スタブはいまそれを明記しています——スカラーに解決するパスには並べ替えるキーがないため呼び出しは
  `None` を返し、解決しないパスは従来どおり拒否します。この形を固定していたテストは契約にちなんで
  改名され、両側を検証します。`api:sort-keys-scalar-path-noop` は `.ci/known-residuals.json`
  から外れ、マトリクスの Known residuals 表には `api:set-comment-container-owner` だけが残ります。

- **リーダーが限定されていなくても、パリティ列はテストユニットを読みます** — 従来の
  `crosslib_parity` は、限定されたリーダーがないと判断した時点でどのテストも読まずに `yes` を返して
  いました。そのため、すべてのテストレッグにインストールされるリーダーだけを持つファミリーは import
  一覧だけで加点され、すべての比較に `@pytest.mark.skip` を付けた `test_*_crosslib.py` も、テストが
  一つもないファイルも `yes` と表示されました。ユニット規則はすべてのモジュールに適用されます。YAML
  が `yes` のままなのは、ガードが発火しないからです。すべての比較に `skipif(pyyaml is None)` または
  `skipif(not _ruamel_available())` が付き、どちらのリーダーもマーカーなしで宣言され、ヘルパーはその
  本体（`return _ruamel is not None`）で解決されます。一方、`skipif(sys.version_info < ...)` は依然
  として加点を拒否します。YAML の比較を `safe_load`、`safe_dump`、`parse` から読み取るには、方言の正
  規表現が接尾辞のない既定の動詞を知る必要がありました。制御は「生きた比較がない」四つの形
  （`@pytest.mark.skip`、テストなし、モジュールレベルの `pytestmark`、インタープリターのゲート）を
  `partial` に、死んだ可用性ガードを `yes` に固定します。計測されたツリーは変わらず、YAML、JSON、
  TOML のパリティは `yes` のまま、導出されるホール一覧も唯一の `authority-tier:schema-validation` の
  ままです。

- **コーパススイートは、それが名指すコーパスによって加点されます** — 外部権威列のリーダーなし
  分支は、リーダーを import しない `tests/test_*_suite.py` や `*_spec_table.py` をすべて `yes`
  としていました。そのため、正しい接尾辞とプレースホルダーテストだけを持つファイルも `yes` と
  表示され、ドキュメントの「コーパスファイルは再生するスイートで数える」という記述と食い違って
  いました。分支は、モジュールが文字列定数でコーパスを名指すことを要求するようになりました——
  3 つのスイートがローダーに渡す `Reference/` ルートです——コメント内の言及はロードではありま
  せん。制御は両側を固定します。接尾辞だけのファイルと、コメントだけでコーパスに触れるファイル
  は `no`、実際のコーパススイートは `yes` のままで、測定済みのツリーは不変です——
  `test_yaml_suite.py` がこの分支に到達する唯一のファイルであり、7 つの権威ファイルはすべて
  `yes`、4 つのフォーマット行は `authority=yes` のまま、派生するホール一覧は単一の
  `authority-tier:schema-validation` のままです。

- **外部権威の列は import だけでは加点されなくなります** — `tests/test_*_suite.py` や
  `*_spec_table.py` のファイルは、どのマーカーにも束縛されないリーダーをインポートしていれば、
  そのリーダーを実際に使うコードが残っているかどうかに関係なく `yes` と数えられていました。セルが
  問うていたのはテストではなく依存関係であり、生きているように見える import の隣で比較が削除されて
  も列は緑のままでした。ファイルがリーダー加点を得るのは、そのリーダーに「手を伸ばす」場合だけに
  なります。テスト内の呼び出し、またはテスト実行前にモジュールレベルの表へ配線される呼び出し可能
  オブジェクト——ライタースイートが使っている形です。`json is None` は比較ではなく能力の探査で
  あり、使われない import はどちらでもありません。境界付きの分岐はより厳しい規則を保ちます。そこ
  でのスキップは、あるレッグからリーダーを外す当のものになり得るからです。コーパススイートは今も
  リーダーを必要としません。コーパスには不在になり得るリーダーがないからです。
  `tests/test_yaml_suite.py` は裸の import で `yes` と読まれていた唯一のファイルでした。
  `import yaml` はそのゲートが使う `HAS_PYYAML` フラグを導くためだけに存在し、PyYAML は
  `pyrs_yaml.compliance` の中でコーパスを読み込みます。そのためフラグはそのモジュールから取るよう
  になり、ファイルは実行するスイートによって加点されます。対照ケースは四つの形すべてを固定します。
  インポートのみと `json is None` の探査は `no`、モジュールレベルのリーダー表とコーパススイートは
  `yes` と読みます。実測ツリーは変わりません。七つの権威ファイルはすべて `yes`、四つのフォーマット
  行は依然 `authority=yes`、導出されるホール一覧は依然として単一の
  `authority-tier:schema-validation` です。

- **最後の対照ホールが閉じます: JSON5 と JSONC はすべてのレッグに参照実装を持ちます** — 登録された項
  目が名指しした 2 つの方言は、唯一の外部リーダーが `pyjson5`
  （`python_version >= '3.9' and python_version < '3.14'`、armv7l/s390x/ppc64le を除外）でした。その
  ため本パッケージが約束する 3.8 フロアと 3.14+ では、両方言は「何もない」ものと比較され、レッグは緑
  のままでした。純 Python の `json5` パッケージ（`>= 0.17.3`、`requires-python >= 3.8`、
  `py3-none-any` wheel）を test 依存グループに追加し、この方言を判定する 2 つのファイルが無条件にイ
  ンポートします。この方言を判定する比較はスキップマーカーを持たず、`pyjson5` は wheel をインストー
  ルできるレッグの第二意見として残ります。2 つの参照実装は 2 つの構文で見解が分かれるため、テストは
  差異を隠さず本エンジンの読み方を固定します。サロゲートペアはここでは 1 文字に結合されますが純
  Python 参照は 2 つの UTF-16 コード単位を保持し、孤立サロゲートはここでは拒否されますが同参照は受け
  入れます。`tests/test_json5_spec_table.py` はモジュール全体を `pyjson5` でゲートしなくなったため、
  仕様表の行はフロアでもスキップされません。実測: `cross_library.restricted` は空、JSON 行の parity
  セルは `yes`、`.ci/quality-holes.json` は schema の 1 行のみ、そして external-authority 列はファイ
  ル名ではなくファイルごとの判定を返すようになりました。有界リーダーだけに退行した仕様表は、ファイル
  名を持つ `authority-tier` 種別のホールとして現れます。

- **TOML の三者一致は 3.11 以上だけでなく全レッグで走ります** — クロスライブラリモジュールは 3.8 か
  ら 3.10 で pyrs/tomlkit/tomllib の 11 件の対照をスキップしていました。`tomllib` は 3.11 で入り、そ
  れ未満のレッグには参照リーダーが入っていなかったためです。バックポート `tomli>=2.0` を
  `python_version < '3.11'` として test グループに宣言し、`tomllib` の名前で import するようにしたの
  で、全レッグが 24 件すべてを実行します。行は `tomli` と `tomllib` をそれぞれの境界とともに別々に示
  し、`tomlkit` はどのレッグでも方言を判定するため判定は `yes` のままです。リーダー検索もディストリ
  ビューション名の末尾で止まります。`_dependency_marker("tomli")` は以前 docs グループの `tomli-w`
  要求に答えており、どのテストも import しないパッケージのマーカーを報告していました。新しい統制テス
  トは `tomli` を自身のマーカーに、`tomli-w` をマーカーなしに固定します。公式コーパスのエンコード側
  も、同じ `tomllib` 判定で同じレッグでは丸ごとスキップされていましたが、これらのレッグでも走るよう
  になりました。小数秒を 1 桁で書く `spec-1.1.0` の 3 件は、テスト自身の変換器で小数を 6 桁に揃えて
  います。CPython < 3.11 の `fromisoformat` は 3 桁か 6 桁しか受け付けないためです。

- **`partial` な対照セルは登録された穴であって脚注ではありません** — 対照列は各 `test_*_crosslib.py`
  の oracle の import と `pyproject.toml` のマーカーから判定を導出しており、`orjson` と `pyjson5` が
  `python_version >= '3.9' and python_version < '3.14'`（armv7l/s390x/ppc64le 除外）で宣言されている
  ため JSON 一族は `partial` と読めていました。ページは散文でそれを説明していましたが台帳は黙ってい
  たので、「JSON 一族にはクロスライブラリ層がある」という文が、このパッケージが約束する 3.8 レッグ——
  モジュールは何も import せずスキップし、43 の対照をすべて走らせたレッグと同じ緑を返す——について
  引用可能でした。`parity_gaps()` は同じ導出から `parity-tier:json-jsonc-json5` を発行し、
  `.ci/quality-holes.json` はそれを消す出口（`restricted` が空、同じ測り方）とともに記録します。穴
  id のスラッグはラベルの英数字から導出し、`JSON / JSONC / JSON5` は誰も読めない id に化けられませ
  ん。

- **JSON リーダーを設置できないレッグでも RFC 8259 を判定します** — JSON のクロスライブラリ・モジュ
  ールはゲートをファイル全体にかけていたため、このパッケージが約束する 3.8 のフロアや 3.14+ では 43
  の対照がすべてスキップされ、第三者のリーダーを必要としない比較まで消えていました。そのひとつが標準
  ライブラリの `json` になりました — `parse_constant` が標準ライブラリの既定で通る三つのリテラルを拒
  絶するので、宣言で境界を引かれず、どのレッグにもある RFC 8259 の参照になります。除外レッグを模擬し
  た実測（`orjson` と `pyjson5` のどちらも import できない）では 29 の対照が走り 44 がスキップ、前は
  0 / 43 でした。両方のリーダーが入るレッグでは 73 が走ります。これを報告するにはセルを方言ごとに作
  る必要があり、`crosslib_parity()` はテスト自身が境界のないリーダーを呼び、そのテストをスキップでき
  ない場合にだけその方言を計上します — `@needs_pyjson5`、モジュールの `pytestmark`、散文の中の言及、
  テストの後に定義した helper はいずれも計上されません。穴は登録されたまま、対象は一族全体ではなく
  `json5` と `jsonc` になりました。

- **解釈器が引く境界も、行が報告する境界になりました** — parity 列は「あるリーダーがレッグで欠ける
  か」を `pyproject.toml` にだけ問い、リーダーもモジュールレベルの import からしか探していませんでし
  た。`tomllib` はその両方から姿を消します — 宣言するファイルがなく、`tests/test_toml_crosslib.py`
  では第二の検証を要求する一つのテストの中で `pytest.importorskip` が束縛するだけです。レッグ自身の
  スキップ計数がセルの言えなかったことを語りました — CI のフロアレッグはそのモジュールの 24 件中 13
  件を実行し 11 件をスキップし、3.9 と 3.10 も同じ 11 件をスキップします — つまり行は一つのリーダー
  を数えていましたが、ファイルは二つに尋ねています。`STDLIB_SINCE` は `requires-python` から読み出し
  た床に対して標準ライブラリのリーダーに境界を引き、`_oracle_locals()` は構文から `importorskip` の
  束縛を取ります。TOML の判定は `yes` のまま、そして誠実なままです — `tomlkit` は無制約で宣言されす
  べてのレッグに入るので、3.8 から 3.10 が失うのは三者一致であって、何も判定しない方言ではありませ
  ん。あのモジュールは今 `tomlkit` を素で import します — どんな marker にも制約されない番人は、緑の
  あいだは死んだコードで、緑でなくなったあかは静かなスキップになるからです。そして `tomllib` が制約
  ありと数えられた瞬間、そのファイル全体の `pytestmark` は単位を却下し、実在しない穴を作り出していま

  す。

- **JSON5 `\xHH` エスケープを通します — 他の JSON5 エスケープはすでにありました** —
  `load_json5` と `from_json5` は `\v`、`\0`、行続き入力は受けましたが、JSON5 のエスケープ
  集合に含まれる `\x` + 16 進 2 桁を拒否していました。同梱の stub は `load_json5` について
  "Accepts the full JSON5 grammar" と公言していたところです。参照実装と突き合わせた測定で、
  pyjson5 は `{a: '\x41'}` に `{'a': 'A'}` を返すのに pyrs は "invalid escape sequence" を
  返していました。2 桁は 1 バイトずつ累算する方式にしています — `from_str_radix` は先頭の
  `+` を通すため `\x+1` が有効なエスケープになってしまう — 厳格 JSON と JSONC は引き続き
  拒否します。Rust テストは両方の引用符、`\x0A` と `\x00`、切断・非 16 進の後部、それに
  マルチバイト文字をまたぐ不正なエスケープを固定し、pyjson5 突き合わせテストは受理と 2 つの
  狭い方言の拒否を固定します。

- **JSON5 のエスケープキーと全ての行終端子、それを固定する表** — 同じ stub が約束したままで
  欠けていた構文が 2 つあります — 引用符なしキーの中のバックスラッシュ + u エスケープ（JSON5 が
  継承する ES5 の `IdentifierName` は識別子文字の位置ならどこでも許します）、そして文字列の中で
  バックスラッシュに続く CRLF・LS・PS です。続き入力の欠けは同一方言の 2 つのスキャナが食い違って
  いることでもあり、CRLF 形式は複引用符では通りましたが単引用符では失敗しました。エスケープ文字は
  それを表すコードポイントとしてそのまま採用し、`ID_Start`/`ID_Continue` で再検証
  しません。だからエスケープした数字やドットはキーになれるのに、そのままの文字ではなれません。
  両方の引用符が 1 つの行終端子規則を共有するようになりました。この 2 点を発見した突き合わせは
  ゲートにもなりました — `tests/test_json5_spec_table.py` は受理 41・拒否 11 の構文を `pyjson5` と
  比較します。リーダーが一度も受けなかった表記は property 層と fuzz 層には見えないためで、両者の
  oracle は既存の経路しか比較できないからです。

- **フローマッピングはブロック様式の鍵を綴れない、生成器ももう作らない** — 2 万ケースの property 階
  層がランダムに `{? [null]: A, ? [null]: B}` で赤くなった。同じ 1 要素の列を 2 つの鍵に持ち、一方は
  ブロック、一方はフローで綴った形です。ブロックの親ではこの 2 つは実際に別の鍵で、`? - null` と
  `? [null]` は再読込でも 2 項目のまま（実測）。しかし `{...}` の内側にブロックの列は合法な形が無
  く、書き出し側は両方にフロー記号を出すので、読み込み側が重複鍵を拒否するのは正しい。このツリーは文
  書でなく生成器のものです：`arb_mapping` は文脈を問わない規則で鍵を振るっていました。
  `keys_collide_in_flow` は比較の前に、フローの親が許す唯一の綴りに両方の鍵を畳みます。畳むのは写し
  で、模型は `KeyIdentity` 一枚のまま。一致検査は同じ表をフローの親でもう一度問い直し、生成器が責任
  を持つ方向だけを守ります：規則が通した鍵の組は、読み込み側でも残っていなければなりません。

- **防御マトリクスが外部の権威を測るようになります** — `scripts/quality_matrix.py` は 6 番目の列
  `external authority` を導出します。ある方言に `tests/test_*_suite.py` か

- **Unicode の空白だけの JSON 文字列が、その値を保つようになった** — 鍵が U+2028 ひとつ、という文書
  に `load_json5` は `{None: 1}` と答えていました。`load_json` と `load_jsonc` は文字列を返し、
  `pyjson5` もそちらの側です。ハブはデコードした JSON 文字列を YAML のスカラーに載せ、`needs_quotes`
  が言うまでプレーンに書きます。ところが JSON の解決器はプレーンスカラーを Unicode 規則でトリムする
  — `resolve_json_type` は `str::trim` を意図して残しています。JSON5 の構造空白が本当にそこまで広い
  からです — だから ASCII でない空白で始めたり終えたりする文字列はその文字を落とし、それだけの文字列
  は null になりました。引用符の規則は ASCII の空白と NBSP を知っていましたが、いまは Unicode の
  `White_Space` 25 個すべてを両端で知ります。これで二つの表の食い違いはなくなります。その判断は、バ
  イト走査が非 ASCII バイトを含むテキストで必ずたどり着く文字の側に置いたので、純 ASCII のテキストは
  何も払いません。`tests/test_json_whitespace_scalar.py` はこの集合を鍵と値の両位置で三つの方言に問
  い、`pyjson5` と `json` に「これは null ではなく文字列だ」と確認させます。

- **JSON5 の文字列は生の制御バイトを内容に持つ** — 二重引用符のスキャナは 0x20 未満のバイトで止めて
  拒否していましたが、それは strict JSON 向けの RFC 8259 §7 の規則で、JSON5 のものではありません。こ
  の方言が引用符の中で禁じるのは行終端だけです。それで実際のタブを含む文書を `load_json5` が拒否する
  間に `pyjson5` は読み、しかもこのファイルの一重引用符は同じバイトを以前からそのまま写していた — ひ
  とつの方言が二つの答えを返し、どちらの引用符で開いたかで割れていました。停止集合はこれから方言に従
  います。JSON5 は CR と LF を除くすべての C0 バイトを受け入れ、strict JSON と JSONC は 32 すべてを
  引き続き拒否し、JSON5 の書き出し側は読んだものをエスケープするので往復もやはり一行です。
  `tests/test_json5_spec_table.py` は 30 個を両方の引用符で参照実装に問い、二つの strict ローダは同
  じバイトで RFC に釘付けられます。

- **JSON の書き出し側に、この倉庫が所有しない読み手を与えた** — 書き出し側は自前の読み手でしか検証さ
  れていませんでした。不動点は「同じ誤りを二度する」実装でも同じように満たされます。
  `tests/test_json_writer_suite.py` はこれから 1500 本の木を生成し、`to_json`、`to_jsonc`、

  路とも拒否 0・値の変化 0。そして実際に噛みます: `write_json_string` に生のタブを出させると、strict
  の二本が紅になり、JSON5 の一本は緑のままです。

- **1.1 が数字と定める綴りの YAML 文字列が、読み戻すと数字になっていた** —
  `safe_dump({"v": "1_000"})` は `v: 1_000` を出し、PyYAML と ruamel はどちらも整数 1000 を
  返しました。`8_0`、`0b101`、`+0x1f`、旧式の真偽語 `yes`/`on`/`off`/`y`、日付だけの
  タイムスタンプ `1990-06-23`（読み戻すと `datetime.date`）も同じです。経路ごとに 26 の綴りが
  漏れ、キー位置も値位置も、Python 経路も JSON→YAML 経路もそうでした。引用を決めるガードは
  `resolve_core_type` だけを尋ねていました。これはこのエンジン自身の 1.2 core の読み手で、
  それらの綴りはそこではすべて文字列です。YAML 1.1 の型リポジトリに従う読み手は型を付け、この
  エンジン自身の `schema="1.1"` プロファイルも `y` と `yes` に付ける — 書き出し側と自分の
  プロファイルの一つが同じトークンで意見が違っていたのです。ガードは今、1.1 の表を第二の問いと
  して尋ね、四つの族を見ます: core が並べていない真偽語、数字の中の `_`、core が見通せない基数
  接頭辞（`0b`、そして符号付きの `0x`/`0o`）、`YYYY-MM-DD` です。引用は安全側の誤り — 引用した
  スカラーは解決されない — なので、各族はパーサではなく表が受け入れる形にしました: `a_b`、
  `0x`、`2026-10` はプレーンのまま、`12:00` はここを要しません。コロンが一段下でプレーンな
  出力を拒むからです。出力が変わるのはこれらの綴りだけです: `1_000` は `"1_000"` 書かれます。

- **YAML の書き出し側に、この倉庫が所有しない読み手を与えた** —
  `tests/test_yaml_writer_suite.py` は `safe_dump`、`from_json`、編集層で文書を出し、それを

  YAML の行に記します。編集層はデータ経路より狭い規則に縛られ、このファイルはその両方を

  `rename("$.v", "yes")` は `true` と読めるキーを書いた — 引用します。日付と時刻は外に
  置いてあります: `!date` は SafeLoader に構築者のないローカルタグで、よその読み手は値を
  変える代わりにその文書自体を拒否します。これはタグ設計側の境界です。

- **TOML の書き出し側に、この倉庫が所有しない解析器を与えた** — 書き出し側三マスの最後の一格です。
  TOML の外部階層（`test_toml_test_suite.py`、`test_toml_crosslib.py`）はどちらも読み手だけを示して
  いたため、`to_toml` は自前の読み手でしか検証されていませんでした。
  `tests/test_toml_writer_suite.py` は `to_toml` と `YamlDocument.to_toml()` で生成した 400 本の木を
  書き出し、`tomlkit` に、Python 3.11+ では `tomllib` にも手渡します。実測: 1200 本のうち 1074 本が
  出力・読み戻され、拒否 0・値の変化 0。残り 126 本は一つの型付き拒否 `toml-cannot-represent-null`
  で止まりました — その書式に語彙のない値はつづりの作り替えではなく拒否されます。二つの境界は
  固定します: `datetime.time` は素のローカル時刻（1.1 のつづり）、i64 を超える整数は引用付き（ハブは
  文字列と呼んでいる）。挙動は変えていません。

- **完全形 `!<tag:yaml.org,2002:X>` も `!!X` で登録したプラグインに届きます** — YAML 1.2 §6.8 では
  二つの表記は同じタグです。手作業で列挙する五つのタグ（`!!str`、`!!int`、`!!float`、`!!bool`、
  `!!binary`）は両方とも見ていましたが、それ以外の名前はレンダリング済みの文字列で引くため、完全形は
  スキーマ解決に落ちていました。2026-10-18 の主幹で実測：`!<tag:yaml.org,2002:widget> 7` は
  `!!widget` の登録を無視して整数 `7` として読みます。まず文書自身の表記で引き、外れたときだけ接頭の
  判定を一度足すので、YAML 以外の名前空間の URI は今までどおり「タグなし」として読まれ、エラーには
  なりません。

- **パリティ列が別名で宣言済みのオラクルを認識します** — `scripts/quality_matrix.py` は
  `pyproject.toml` が各クロスライブラリ・オラクルに付けた境界を読みますが、import 名を字面のまま
  探していました。`ruamel.yaml` はその名前で import され `ruamel-yaml` と宣言されているため、検索は
  `undeclared` を返し、どのレッグにもインストールされるオラクルを「宣言されていない」と
  報告していました。
  検索は PEP 503 のように `-`・`_`・`.` と大文字小文字を正規化し、`tests/test_quality_matrix.py` は
  `undeclared` を拒否するので、探針がオラクルを見失えば誤った報告ではなく失敗します。

- **`extends` を省いたスキーマがドキュメントどおりの既定で解決されます** — `extends` は省略可能で、
  `docs/ja/guides/custom-schema.md` は既定を `core` と明記しています。ところがパーサが Core を選ぶの
  はキーが空値で存在するときだけでした。キーそのものを省いたスキーマは土台となる解決器を持たず、すべ
  てのスカラーがそのままテキスト扱いになるため、判定が両方向で音もなく反転します。`type: int` は
  `port: 80` を断り（エラー文は `expected int but got Str("80")`）、`type: int` ではなく `type: str`
  はこれを受け入れていました。旧規定を留めていた Rust の行は二つになり、二つ目は残った境界を記録しま
  す。このエンジンが見つからない名前はいまだ解決器なしに落ち、誤った名前の拒否は公開されたエラー範囲
  の別の判断です。

- **アンカーを孤立させる編集は書き込まれず拒否されます** — `base: &x 1` に `use: *x` がある文書で、

  返して、残った参照が誰も定義しないアンカーを指す文書を書いていました。このライブラリ自身の読み手が
  `found unknown anchor` で拒否します。規則はすでにエンジンにありました — 元データを保つ値の置き換え
  では `with_metadata_from` が文書側のアンカー名を守ります — 今回の三つの入口がそれを迂回していたの
  で、検査は実際に名前が落ちる場所、つまり `set_path`（`set_many_path` と `move_path` が共用）、
  `delete_path`、そしてアンカー動詞に置かれました。検査は実際に参照が宙に浮く場合より広くかかります:
  エイリアスは同名アンカーのうち*直前の*ものへ束縛されるため、後の `&x` が生かし続けるはずだった改名
  も、アンカーとそれを名指すエイリアスを一緒に含む部分ツリーの削除も拒否されます。過剰な拒否はもう一
  手間で済みますが、不足であれば誰も読めないファイルを書き出します。改名がエイリアスを連れて行く仕様
  は動詞の意味をきめる決定であり、そのまま課題に記録しました。

- **編集層専用の fuzz ターゲットが増えました** — ワークスペースは九つになり、以前の八つはいずれも
  *文書*をエンジンに渡すだけで、*変更*を駆動する対象がありませんでした。往返保証の主眼である層です。
  `fuzz_targets/edit_yaml.rs` は `document NUL script` を読み、読み手が実際に辿れた経路を選び、許可
  された各編集について再解析・書き込んだ値が指定位置に残ることを要求します。削除に関する検証は種別を
  分けます — キーは同一性ですが配列の下標は次の要素が繰り上がる位置だからです。上のアンカー欠陥は最
  初の種子再生で、さらに最初の探索の数分後に再び検出され、三つの形状は主張せず記録にとどめました: ス
  カラーへの整列要求は "ok" を返して何も変えず、注釈は指定した節に残るとは限らず, タグと注釈を一緒に
  持つ flow メンバは二周目で安定します。最後は未解決の欠陥であり、次の改修が入力をそのまま受け取れる
  よう種子として保存しました。

- **`date` と `datetime` を、どのリーダーも知るタグで書き出すようになりました** —
  `safe_dump()` は `!date` と `!timestamp` を出しており、ローカルタグはこのライブラリの外に
  コンストラクタがありません。2026-10-18 の主幹で実測：`yaml.safe_load` と `ruamel.yaml` は
  いずれも `ConstructorError` を返し、値は型を違えただけではなく読み戻せませんでした。両者は
  これから YAML が定義する唯一のタイムスタンプタグ `!!timestamp` で出力され、両リーダーとも
  日付のみのテキストを `date`、時刻を含むものを `datetime` と解釈します。本ライブラリも同じ分岐を
  します。`!date` と `!timestamp` は登録を残し、以前の版が書いた文書も同じオブジェクトとして
  読み戻ります。ローカルタグで読み込んだ文書はそのまま再出力され、標準タグは Python オブジェクトから
  新しく作る値だけに付きます。`!time` はローカル拡張のままです。YAML は日時のない時刻のタグを
  定義していません。TOML から読み込んだ値は中枢タグ `!date`/`!timestamp` をそのまま持つため、
  そちらは次の項目で Rust 側も同じ置き換えをしています。

- **TOML の日付と日時も同じ標準タグでハブに入ります** — `crates/pyrs-toml/src/lib.rs` の投影は
  日付のみに `!date`、日時 `datetime` は `!timestamp` を付けていたため、TOML を読んで YAML に
  書き出すだけの文書は、上の項目が Python の境界でやめたローカル表記のまま出ていました。今は
  どちらも `!!timestamp` で、読み取り側はテキストで分岐するので TOML の日付は真夜中の `datetime`
  ではなく `date` のままです。`parse_stream` の `tag` に見えるようになりました。時刻だけの場合は
  `!time` を保ち、`!date` は今までどおり読めます。

- **値がタグだけで本文を持たない flow 要素は、注釈を 1 ラウンド目で固定する** — `{a: !t }` は値を
  空に書き出すため、タグの後に書かれた注釈は係れる本文を失う。リーダは注釈を外側のペアへ渡し、
  タグはその後ろへ移り、文書は 2 ラウンド目の出力でようやく安定した。往復で失われるものはないため、
  他のどの層もこの欠陥を見ていなかった。ライタは注釈が続くとき、その空の本文を `''` と書く —
  注釈の前にある空の値を `~` と書くのと同じ判断（libFuzzer `edit_yaml` crash-b23eed05）。

- **ブロック列の要素の注釈はダッシュ行に残る** — 編集層で要素のマップに設定した注釈は `-` 行に居場
  所がないため、ライタはマップ全体を別の行へ追い出していた。リーダはその注釈をブロックの末尾のペアに
  帰属させ、次の出力は行を再び短縮したので、テキストは 2 ラウンド目で安定した。短縮形は要素自身の注
  釈を載せる（`- a: 1  # n`）。その行が YAML の行末スロット（1 行に 1 つ）を既に使っていれば、注釈は
  ダッシュの上へ移る（`# n`、続いて `- a: 1  # m`）— どちらも不動点（libFuzzer `edit_yaml`
  crash-61474da6）。

- **空の plain スカラーは解決される null のつづりで書く** — テキストも属性もないスカラーは何も書き出
  さず、空行から同じノードは戻らない：`k:` も `-` も null として再読され、そのつづりは `~` なので、
  最初の出力は 2 ラウンド目で安定した。引き金は `- >` のスタイルを plain に設定した編集（libFuzzer
  `edit_yaml` crash-63749496）。ライタはこれから正文が空になる箇所すべて — ネスト値、ルート値、列の
  要素、flow の値、flow の要素 — で null のつづりを書く。タグ付きの空はそのまま：タグは解決を抑える
  ため、安定する `''` のつづり（#514）を保つ。アンカーは別の場合です。ノードに名前を付けるだけで解決
  を抑えないので、`- &a3` は `- &a3 ~` と書く（crash-07b6a10e）。

- **TOML ライタの方言保証に属性テスト層を追加しました** — 1.1 が与える可視の自由は行内テーブル内の改
  行、つまりコメントを置けることですが、コメントを持たないツリーが 1.0 で読める文字列になったかを問
  う検査がありませんでした。`prop_toml_undecorated_output_loads_as_1_0`
  （`crates/pyrs-yaml-core/src/fmt_pbt.rs`）は、どこにも note を持たない生成ツリーが
  `from_toml_v1_0` で再読込されることを要求し、
  `an_undecorated_inline_table_writes_compact_and_loads_as_1_0` と
  `the_1_0_reader_refuses_the_1_1_inline_table_freedom`（`crates/pyrs-toml/src/writer.rs`）は該当枝
  とその判定前提を形で固定します。実測：複数行枝を強制した当初は具名テストだけが落ち、20 000 件の生
  成ケースは緑のままでした。そこで行内テーブルを必ず含む入力を生成する方針を属性に追加し、同じ強制な
  ら今は 0.01 秒以内に属性も落ちます。3つ目の属性は、この層に欠けていた等値そのものを主張します：
  `prop_toml_roundtrip_preserves_the_tree` は1往復前後のツリー（値・形・順序）を比べ、値を落とす2つ
  の突然変異がどちらも赤くしました（同じ2回の実行でテキストの不動点も赤くなっているので、断言を直接
  書いただけで、より強い検証者ではありません）。挙動は不変。件数は Rust テスト 720、属性 29 です。

- **編集のティアが出力も訊くようになった** — ハブ文書こそが `doc.to_toml()`、`doc.to_json5()`、CLI
  の TOML/JSON 出力が書くものなので、「編集してから出力」は利用者が実際に通る道です。ところがそれま
  での各ティアはこれらの書き手に*読み手が*作ったツリーしか渡しておらず、`toml_roundtrip` と
  `json_roundtrip` はスプライス層が書き換えたツリーを見たことがありません。`edit_yaml.rs` はこれで安
  定したツリーをすべての方言（美化形も含む）にそれぞれ渡し、その方言自身の読み手がテキストを受け取る
  こと、二度目の出力が同じバイト列になることを要求します。ある方言がツリーを拒否するのは合格です。
  TOML にトップレベルのスカラーはなく、厳密な JSON は非有限の浮動小数を拒否するからです。編集動詞は
  設計上 YAML 専用で（`crates/pyrs-toml/src/lib.rs` にそう書かれており）、ひとつのティアが七人の書き
  手に訊く形になります。同じ二つの問いは `json_roundtrip` にも入り、美化した三種の JSON つづりを、
  誰も生成を選んだのではないテキストに対して問い直しています。

- **容器を置き換える `set` が、その内側で参照されていたアンカーの定義を失わなくなった** — `set_path`
  のガードは置き換えられるノード*自身*のアンカーしか見ていませんでしたが、そのノードにはアンカーがな
  く、子にあったのです。`preserve_metadata: true` はまさにその自身の子属性だけ写すため、マップを上書
  きすると `x` のただ一つの定義が消え、`use: *x` は誰も定義していない名前を指し、このライブラリ自身
  の読み手が拒否しました（libFuzzer `edit_yaml` crash-fbd364b3）。`delete_path` はすでに
  `anchors_in` でもっと広い部分ツリーへの答えを持っていたので、この扉でも同じ問いを同じ
  `anchor-is-referenced` で断り、ツリーはそのまま残ります。

- **タグのみの列要素に書いた注釈はその行にとどまる** — `- !fuzz2` は値を空として書くので、タグのうし
  ろの注釈は載る本体がありません。読み手はその要素の先頭注釈として登録し、二度目の出力ではダッシュの
  上の行に書く——何も失われていないのに、テキストが二ラウンド目で動いていました（libFuzzer
  `edit_yaml` crash-3dd60cad）。書き手はこれから、行内注釈の前に保留中のタグ行を閉じます。注釈行の前
  にすでにそうしていたのと同じです。要素は `- !fuzz2 ~  # fuzz 47` と書かれます。

- **符号付きゼロは、TOML が読み戻すゼロとして TOML に届きます** — 整数の素通しは plain スカラー自身
  のつづりを守り、`-0` は正当な TOML テキストです。しかし TOML に負のゼロはなく、`ist = -0` は `0`
  と読み戻されるので、二回目の出力が動きました。定点は読み手のつづり方で書くものなので、符号付きゼロ
  は `0` と書き、読み手が本当に保つ進数のつづり（`0xDEAD`、`0b1`）はそのまま通します（libFuzzer
  `edit_yaml` crash-917e103b）。

- **空になったブロック列がダッシュの行を保ちます** — ブロック列の最後の項目を消すと flow の目印が残
  りますが、空の容器にはブロック形がなく、常にキーの行で `[]` と書かれます。つまりコンパクト規則は出
  力が持たないコンパクト性を拒否していたのです。最初の出力は `-\n  t: []`、読み手の答えは `- t: []`
  で、二ラウンド目にテキストが動きました（libFuzzer `edit_yaml` crash-a58caa38）。

- **長い整数の形をした JSON 文字列は、ハブを越えても引用符を保ちます** — `i64` に収まらない桁の並び
  について Core の解決器は `Str` と答えますが、JSON は整数リテラルに上限を設けません。そこで
  `"9999999999999999999"` は plain スカラーとして投影され、`to_json` はそれを数値として書き戻しまし
  た。`load_json` が文字列として保っていた値が、ハブを一度渡るだけで整数になったのです。投影はこれか
  ら、文字列を plain で書く前に JSON 自身の数値文法にたずねます。書き手がそのテキストにたずねるのと
  同じ問いです（libFuzzer `json_roundtrip` crash-09341b75）。

- **`schema="1.1"` が 1.1 の数字書式を解決します** — `1_000` は整数 1000、`0b101` は 5、`+0x1f` は
  31、`+.inf` は無限大、`017` は 15 で、いずれも PyYAML の既定ローダーが同じテキストに返す答えです。
  このプロファイルは Core に旧来の真偽語だけを足すもので、書き手の条項は #504 から「1.1 の読み手が型
  づける」書式を引用符で守っていたので、このエンジンに存在しない読み手のために守っていたことになりま
  す。タイムスタンプと六十進法はテキストのまま（タグのないテキストはテキストとする裁定、コロンはすで
  に一段下の層で引用符を強制）、`0o17` は PyYAML ではテキストなのにここでは型がつきます。このプロフ
  ァイルは Core に足す方式で、`0o` は Core の接頭辞だからです。

- **1.1 の読み手だけが型づける文字列を、そのまま出さなくなりました** — `0x_1f` は PyYAML では 31、
  Core ではテキストですが、「1.1 の読み手が型をつけるか」に答える条項は下線を一進語句でしか調べてい
  なかったため、Python 文字列 `"0x_1f"` はそのまま出力され、読み戻すと数値になっていました。この穴
  は、このプロファイルが型づけるすべてのテキストについて `needs_quotes` の同意を求める新しい不変条件
  テストが見つけたものです。

- **TOML ライターの節見出しがキー名を実体化しなくなった** — `to_toml` は各ルート表の見出し
  文字を独自の `String` に取り出してから最上位のペアの後に書いていました。しかし節の一覧はキー
  节点をすでに保持しているので、見出しの分岐はペアの行と同じく `push_scalar_key` で直接追加でき
  ます。これがライターの唯一の実体化されたキーでした: `to_toml_medium` は計測命令 26,741,057、
  床 28,939,722 に対し -7.60%。見出しごとに確保と複製が一度ずつ減ります。

- **TOML でペアの後に置けないルート表は、位置を保つためインラインになる** — TOML はルート table
  ヘッダーの後にルート key/value を認めないため、`to_toml` はすべての節をすべてのペアの後へ書いて
  いました。その結果、`0` が表をもち、続いて `a` が来るツリーは `a`, `0` と戻ってきました。生成器は
  20 000 ケースのproperty層でこれに到達しています
  （`prop_toml_roundtrip_preserves_the_tree`）。いまこの形の表は自分の位置にインラインで書かれ、
  解析済みドキュメントが持ちうる順序では従来どおりヘッダー形を保ちます。

- **シーケンス自身のコメントが要素のダッシュ行を奪わない** — 編集層が*コンテナ*に付けた
  コメントは、そのコンテナのブロックを終えた行の上に書かれていました。コンテナがシーケンスの場合、
  それを終える行は要素自身のダッシュ行で、granit はダッシュ行の下に書かれたコメントをその要素の
  先頭コメントとして報告するため、2 回目の出力でコメントがシーケンスから要素へ動いていました
  （`edit_yaml` crash-08b30707：`?ss:` の後にタグ付きの空要素が 2 つ）。シーケンスのコメントは
  現在シーケンスの先頭行の上に置かれます。読み手がシーケンス自身のコメントを保管する場所であり、
  `lift_first_item_notes` がすでに依拠する場所と同じです。マッピングのコメントは従来どおりその
  ブロックを終えたペアの上に置かれます。読み手がそこでペアのコメントを読み戻すからです。

- **#522 が壊したベンチマークは、通常のテストスイートで契約を検証する** — `Python benchmarks`
  レッグは `806811c5` で `assert '[server]' in ...` により赤くなり、必須の
  `Test matrix (all legs)` は成功を報告していました。#522 は後続のルートペアより前にある
  ルートテーブルをインラインで出力するため、フィクスチャの `[server]` ヘッダーは出力ではなく
  なりました。元の断言は文書の性質ではなく #522 以前の綴りを記述していました。断言は現在、
  通常のスイート
  （`tests/test_toml.py::TestToToml::test_benchmark_fixture_roundtrips_by_values_and_order`）に
  あります。ベンチマークモジュールは `--codspeed` なしでは選択解除されるためです。出力を
  再読み込みすると失われた・変更されたキーが分かり、ルートキーのリスト比較で順序が分かります。
  出力された 2 本のルート行を入れ替えると最初の比較は等しいまま 2 番目が反転します。
  ベンチマーク本体は計測対象の呼び出しだけに戻りました。

- **命令数ゲートがマージ判定の一部になりました** — `Instruction-count baseline` ジョブは
  `.github/workflows/codspeed.yml` にありましたが、`Test matrix (all legs)` は `ci.yml` の
  ジョブだけを集約するため、その結果は報告にすぎませんでした。#522 が赤くした
  `Python benchmarks` レグは必須チェックが緑のままトランクに到達し、Ir ゲートも同じ道を
  たどり得ました。ジョブはそのまま `ci.yml` に移り、他の重いレグと同じ `changes` 分類で

  マージを拒否します。2 つの CodSpeed ジョブは `codspeed.yml` に助言として残ります。
  10% 未満のウォールタイムの揺らぎはランキング向けであり、マージ判断には向きません。

- **Ir ゲートが、ツリーに追い越されたフロアを拒否するようになりました** — ゲートはベースラインの
  片側だけを読んでいました。許容値を超えて増えたシナリオは失敗しますが、現在のツリーよりはるかに
  高いフロアは黙って受理され、エンジンが速くなるたびに許容される余裕が広がっていました。
  2026-10-14 のリフレッシュはその蓄積を測っています。6 つのライターシナリオがフロアより 22–46%
  低く、4 つのリーダーが 4.7–11.2% 低い状態でした。`scripts/ir_gate.py` は両側を読むようになり、
  フロアより 2% を超えて低いシナリオは `FLOOR_STALE` として警告し、5% を超えると失敗します。失敗

  移動）動かし、`from_toml_medium` を −3.00% 動かしました。最大の上昇は `serialize_block` の
  +0.32% で、各シナリオの反復測定のばらつきは 0.000% でした。`.ci/ir-baseline.json` はその成果物
  そのままで、編集は加えていません。

- **ネストしたシーケンスで終わるマッピングの注記が 1 ラウンドで安定します** — ブロックが
  ネストしたシーケンスの内側で終わるマッピングのインライン注記は、最後の項目のダッシュ行の上に
  書かれ、リーダーはそれをその項目の先頭注記として報告していました：
  `ss:\n  - !a\n  # fuzz 35\n  - !a\n` は `ss:\n  - \n    # fuzz 35\n    !a\n  - !a\n` として
  再読され、最初の出力は不動点ではありませんでした。コンテナ自身のインライン注記を配置する
  `pair_line_start` フィールドは、ブロック値の書き込みが独自の開始位置を上書きするため、
  シーケンス項目の行を指したままでした。各ペアは戻る前に自分の行を復元するようになり、注記は
  マッピングのブロックを終えたペアの上に置かれます。注記の所有者は移動しますが（コンテナに対する
  `set_comment` の裁定はそのままです）、テキストは 1 ラウンドで安定し、
  `a_mapping_note_over_a_nested_sequence_settles_in_one_round` が 3 つの形状で固定しています。

- **TOML 整数は書かれたときの綴りを保ちます** — `1_000`、`+5`、`-1_000` および各基数形式は
  ハブを通る際にソーステキストを失っていました。パーサーが記録前にトークンを整形していたため、
  `to_toml(from_toml("a = 1_000"))` は `a = 1000` を返していました。区切り記号と明示的な符号は
  どちらも合法な TOML（ABNF の `underscored` と `signed-int`）であり、損失は文法ではなく記録側に
  ありました。パーサーはトークン全体を保持するようになり、YAML Core が異なる値を解決する場合に
  だけ投影がタグを付けます（`0x1f` と `+5` はタグなし、`1_000`、`0b1101_0110`、`-1_000` は
  `!!int` 付き）。ライターのリテラル判定も、出力するのと同じ文法を受け入れます。タグ付き整数は、
  先頭の `-` のために YAML エミッターが必要とした引用符より優先され、タグなしの引用符付き `"42"`
  は文字列のままです。値は変わらず `tomllib` と一致し、
  `TestIntegerSpellingFidelity`、`decimal_spellings_reach_the_hub_word_for_word`、
  `a_quoted_integer_stays_a_string_unless_a_tag_says_otherwise` で固定しています。

- **宣言された `%YAML` バージョンは要求時に尊重され、出力にも明記されます** — 文書ヘッダーは
  これまで `version()` が報告するだけでリーダーは無視していたため、`%YAML 1.1` も Core で解決され、
  ディレクティブは出力から失われていました。`parse`、`parse_file`、`parse_all_docs`、
  `safe_load`、`safe_loads`、`YAML(...)` に `honor_version_directive=True` を渡すと、
  `1.1` 宣言が YAML 1.1 プロファイルを選択します（`flag: yes` は `True`、`012` は `10`）。
  `1.2`、`1.3`、宣言のない文書は引き続き Core で解決され、明示的な `schema` は宣言より優先されます。
  フラグ有効時、採用された宣言は `---` の前に `%YAML <version>` として再出力され（編集後や
  `reparse()` 後も同様）、Core リーダーがテキストを黙って型変換しないようにします。ストリーム内で
  後続する文書の宣言前には、文法が要求する `...` 終端マーカーが付きます。既定の動作は不変です
  （フラグ無効、Core 解決、出力にディレクティブなし）。`schema` の既定値は `None` になり、
  「未指定」と「明示的な Core」を区別できます。`TestYamlVersionNegotiation` で固定しています。

- **独自開発のルールバリデータを退役し、`Document.validate()` を唯一のスキーマ面にする** ——

  ぶ）か、`jsonschema.validate()` を直接使います。CLI の `validate` は `--schema` と `--schema-file`
  を 1 つのパラメーター（JSON Schema ファイル）に束ね、どちらも指定しない場合は構文チェックのみを行
  います。スカラー型解決は影響を受けません: `register_schema()`、`load_schema()`、`list_schemas()`、
  `YAML(schema=...)`、`rules:` リストは引き続き機能します。退役した言語のためだけに存在した Rust 型
  （`TypeSpec`、`ValidateKind`、`ValidateRule`、`SchemaValidationError`）も削除され、マトリクスの
  `schema validation` 行もそれに伴って消えます。表は 4 行を導出し、`.ci/quality-holes.json` は
  `holes: []` と測定します。その行を担っていた fuzz ターゲットは `validate_schema` から
  `parse_schema` に改名されました。曖昧化するのは JSON Schema の評価ではなく、生き残った `rules:` 文
  法だからです。4 ロケールのガイド、クイックスタート、チュートリアル、機能表、API ページは
  `Document.validate()` を記述するようになり、出荷されるスタブに削除された関数名は現れません。

  `comment(standalone = true)` ではなくなります。#117 の正規化で hand-built fixture は引き続き等価、
  かつ `CustomNode ::remove_comment` が**両スロット**をアトミックにクリアするので Python の
  `Node.remove_comment()` は YAML 起源ドキュメントでも従来通り動作します。
- **スロット横断の standalone 正規化 + Python `Node.leading_comment`** — `NodeMeta::eq` / `Hash` は
  standalone コメントを新しい `leading_comment` スロット（TOML / JSON エンジンが使用）と古い
  `comment(standalone = true)` スロット（YAML レシーバーと hand-built fixture が現在も使用中）のど
  ちらにあっても同一概念として扱います。setter / remover は両スロットにアトミックに作用し、YAML シ
  リアライザは正規化されたビューを読むので `to_yaml(toml_ast)` の leading note が失われません。
  Python の `Node.leading_comment` getter / setter / remover は `Node.comment` をミラーし、TOML /
  JSONC ソースの standalone note を初めて Python 側に露出します。
- **TOML 1.1.0 文法** — `from_toml` が TOML v1.1.0（2025-12-18 公開）を解析します。四つの追加：
  **(A1)** インラインテーブルの改行と後尾カンマ許容、**(A2)** 基本文字列 `\xHH` バイトエスケープ
  （0x00..=0xFF）、**(A3)** `\e` = U+001B、**(A4)** time / date-time の秒省略（`t = 14:15` /
  `dt = 2010-02-03 14:15`）。厳密 1.0.0 用のエスケープハッチとして `TomlDialect::V1_0` と
  `from_toml_v1_0` を保持。1.0.0 ドキュメントは両方言で同じ解析結果になります。同時に space 区切り
  date-time 検出の off-by-one 索引バグ（`T` 無し date-time が 1.0 モードでも認識されなかった）を修
  正。
- **JSON dual-slot コメント保真** — JSONC パーサーは独立行の `// ...` を #114 が追加した
  `leading_comment` スロットに書き、同じ行の `// trailing` は `comment` に残します。オブジェクトメ
  ンバーや配列要素が同じノードで両方のコメントを保持でき、#112 の単一スロットモデルでは表現不能な形
  状が可能になります。`to_jsonc_text_pretty` は `leading_comment` を優先読みし、hand-built fixture
  向けに `comment` (`standalone = true`) の fallback を保持します。厳密 JSON (`to_json_text`) の挙動
  は変化しません（依然 `//` を出力しない）。
- **TOML 空行と dual-slot コメント保真** — `NodeMeta` に `leading_comment: Option<Comment>` と
  `blank_before: bool` を追加（どちらも構造的な `Hash` / `PartialEq` から除外）。section ヘッダーや
  AOT 要素が `]` の後ろにある行末コメントと、その上にある独立行の先頭コメントを同時保持できるように
  なりました。`to_toml` は元の空行区切りを再現します（`a = 1\n\nb = 2` は byte-stable に往復）。手構
  築ノードと YAML 由来ノードは writer の fallback 読み取りでそのままレンダリングできます。
- **JSON5 方言** — `pyrs_yaml_core::json::from_json5(text)` と

- **JSONC コメント保持** — `from_jsonc` が拾った `// 行` と `/* ブロック */` コメントを AST の
  `NodeMeta::comment` に添付します（独立部は key ノード、行末部は value ノード）。PR #109 で導入し
  た TOML モデルと対応します。対となる `to_jsonc_text(node)` / `to_jsonc_text_pretty(node, indent)`

- **JSONC パース** — `pyrs_yaml_core::json::from_jsonc(text)` と

- **TOML コメント忠実性** — パーサーがペアやセクションヘッダーの上に独立した行で現れる `# ...` コメ

#### 変更

- **granit-parser 1.1 → 1.3** — YAML イベントパーサを 1.1.0 から 1.3.0 へバンプしました。1.x 系列内
  でのセムバー互換のマイナー升级です：1.2.0 は特殊なドキュメントの制限向けのオプションの `Options`
  フィールドを追加し、1.2.1 はいくつかの解析結果を YAML 仕様に合わせて厳密化し、1.3.0 はデフォルト
  実装付きの 2 つの `Input` メソッド（`fetch_block_scalar_line` と
  `take_quoted_scalar_ascii_chunk`）を追加して、スキャナがブロック・引用符付きスカラーのバイトをよ
  り速く進めるようにしました。本プロジェクトは `Parser::new_from_str` 経由でパーサを消費し、
  `EventReceiver` / `SpannedEventReceiver` のみを実装して `Input` は実装しないため、ソース変更は不
  要でした——新規の trait メソッドはデフォルト実装に解決されます。全テスト正常：
  `cargo nextest run --all`（359）、`pytest`（1436 + 43 numpy）、純 Rust `--no-default-features` ビ
  ルド、および YAML テストスイートの適合ゲートは不変。
- **ネイティブ JSON / TOML コア** — `serde_json` と `toml_edit` 依存を完全に
  削除しました。`pyrs-yaml-core` は RFC 8259 に準拠した JSON エンジン（バイトレベル
  スキャナ、数字はソース表記を保持するため `from_json → to_json` がバイト安定で、
  大きな整数/浮動小数点の精度も失われません。型付き行/列エラー、末尾カンマ・先頭ゼロ・
  単独サロゲート・未エスケープ制御文字・複数ルート文書を厳格に拒否）と、 TOML 1.0
  全文法をカバーするエンジン（bare/quoted/dotted キー、basic/literal/マルチライン
  文字列、区切り `_` を許す 10/16/8/2 進整数、`inf`/`nan`/指数付き float、
  offset/local の日付・時刻・日時）を内蔵します。すべての拒否は granit-parser と同じ
  スタイルで 0-indexed の `line`/`col` を携えた `ParseError::Syntax` として
  報告されます。公開 API は不変、ラウンドトリップテストと `tests/test_toml.py` は
  新しいエンジンでグリーン。
- **内部の重複コード整理** — ベンチマーク fixture を共有ブロックの合成に変更、PyO3 の
  パス編集メソッドを既存の `apply_metadata_edit` ヘルパーへ委譲、重複したファイル読み込み/
  エラーマッピングと行オフセットの定型コードを共有関数に集約しました。公開動作の変更は
  ありません。jscpd で測った重複コード率は 5.25% から 3.45% に低下。
- **`YamlDocument.validate()` がコンパイル済み validator をキャッシュ** — スキーマ
  （JSON テキストまたは dict）に対する初回検証成功時に `jsonschema` validator を
  キャッシュし、以降の呼び出しではスキーマ解析・メタスキーマチェック・validator
  構築をスキップ。dict キーはオブジェクト同一性＋ディープコピー・スナップショット
  ガードで管理され、その場の変更は `==` で検出され透過的に再コンパイル。キャッシュ
  経路は `exceptions.best_match(validator.iter_errors(instance))` を送出し、
  `jsonschema.validate()` と完全に同一のセマンティクス。WSL 実測: `document_validate` −98%。
- **パーサー/シリアライザーカーネルの構造的重複排除** — mapping と sequence の
  レンダリングを単一の `write_container_node` スケルトンに統一（出力はバイト単位
  同一、`serialize_*` 中央値 −5~11%）；単一/複数文書パーサーは同一の `load_ast`
  エラー契約を共有；schema 解析チェーンは `bool_word`/`numeric_tail` を共有し、
  YAML 1.1 は core の null/bool 語をスカラーごとに再チェックしない；アンカー登録
  （`register_anchor`）と standalone/inline 注釈分類（`is_standalone_placement`）を
  AST と stream receiver で単一化。リポジトリ重複率 3.38% → 2.60%。

#### 修正

- **`\u` / `\x` エスケープ直後のマルチバイト文字でパーサが panic** — 固定長エスケープ読み取りが
  `&self.text[pos..pos+width]` をバイトオフセットで切っていた。JSON `\u` / TOML
  `\xHH`/`\uXXXX`/`\UXXXX` の後にマルチバイト文字が来るとスライスが文字途中に落ちプロセス abort
  （#153 の同族）。バイト切り＋UTF-8 検証に直し、不正エスケープはクリーンにエラー。方言 fuzz で発
  見、両パーサに決定的 Rust 回帰テストで固定。
- **非マージ値のリテラル `<<` キーが黙って破棄されていた** — `load(safe_dump({"<<": None}))` はキー
  を失い `{}` を返した。マージ解決器は Null/Scalar 値でも全ての `<<` をマージとして消費していた。
  YAML では `<<` は値がマッピングのエイリアス / インラインマッピング / そのシーケンスのときのみマー
  ジ。Null/プレーンスカラーの `<<`、およびエイリアスを含まず合成内容が無い `<<`（`<<: []`、
  `<<: [1, 2]`、`<<: {}`）は通常のキーとして往復保持される。Alias/mapping/sequence 経路（#166 の自己
  参照アンカーガード含む）は無変更、yaml-test-suite は 405/406 維持。往復プロパティ fuzz が非決定に
  検出（#163/#165/#166 級の欠陥）、決定的な Rust 回帰テストで固定。
- **TOML 深いネストがネイティブスタックを溢れプロセスを abort** — TOML パーサにはネスト予算が無く
  （JSON は `DEFAULT_MAX_DEPTH`、YAML は `parse` の `max_depth`）、`parse_value` →
  `parse_array`/`parse_inline_table` が無制限に再帰。深い配列/インラインテーブルは解釈器を即クラッシ
  ュ（検証済み：exit `0xC00000FD` STACK_OVERFLOW）— #166 の YAML merge オーバーフローの TOML 版。パ
  ーサは `depth` を追跡し 1000 超で `ParseError::MaxDepthExceeded` を返し JSON と対称に。プロセス内
  Python 境界テスト + subprocess クラッシュカナリア + 大スタック Rust テストで守る。
- **方言 writer/parser がドキュメントレベルの注釀を消失・誤配置** — 固定点プロパティが捕捉した 3 欠
  陥：(a) JSONC/JSON5 の値より前の file-leading `// note` が inline と誤分類（オフセット 0 の前に改
  行なし）され、writer が注釈する root ではなく最初の object メンバに取られ、空 `{}` や root スカラ
  ーでは完全に消失；(b) JSON 系・TOML writer は注釀本体を無加工で出力していたが parser は trim して
  保存するため、未 trim 注釀は pass 毎に行末空白振動——writer も出力時 trim し初回スペルから安定；(c)
  注釀のみ TOML 文書（`# note` 後に key なし）は再パースで注釀が落ち空 root が `""` 化——未消費の
  standalone 注釀を空 root テーブルに付加。5 フォーマットの leading 注釀がすべて逐字安定の固定点到達
  （3 件の targeted Rust テストで固定）。
- **ネスト式ブロックスカラー本体が親行のインデントを保持** — ネストキー下の字句/畳み込みスカラーが本
  体行を列 0 から固定 1 段で出力しており、`b: |` ヘッダ行の下一層に配置されず、すべてのネスト形態
  （ペア・シーケンス項・compact dash・任意深度）の出力が再パース不能または誤値になっていた。スカラー
  出力系は `block_base`（親行の列位置）を全書出箇所に貫流。7 種のネスト形態で往復が完全一致。TOML ホ
  ットスポットベンチが共有シリアライザ経由で発見。
- **シリアライザが再パース可能な YAML のみ出力** — テキストレベルゲートが検出した 5 つの欠陥：(a) 改
  行分岐での anchor/tag プリエミットが子ノード（スカラー/null/flow 容器）の自己ヘッダと二重化
  （`A: !a` … `!a null`）→ block 容器のみに限定；(b) flow 容器内のブロックスカラー（`[|`、`{k: >}`）
  とキー位置はダブルクォートに降格；(c) 自行を開始する flow 容器の行頭インデント欠落と complex key
  （`?`）の値標識 `:` の列 0 出力→いずれも親インデントに従うよう修正；(d) standalone コメント/tag 付
  き complex キーの曖昧テキスト（コメントは `?` 上部へ、本文は常に 1 段深い独立行へ）；(e) flow 容器
  内で先頭/末尾空白または `,[]`{} 埋め込みの plain スカラーはクォート化（素文出力だと token を途切れ
  るか再パースで消える）。さらに tag 付き空 block 容器はヘッダを `{}`/`[]` と同列化、compact dash 項
  は standalone コメント付き値をインライン化しない。9 個の targeted Rust テストと Python 回帰で各系
  統を固定。
- **TOML が合法な最小 i64 整数を拒否** — `from_toml`/`load_toml` が `-9223372036854775808`
  （`i64::MIN`）で失敗：符号付き経路は絶対値を先に解析するため反転前に溢れていた。現在符号は桁と同
  時に解析され（`i64::from_str` は負方向に累積）、符号付き浮動小数は指数スペルを保ち、旧 negate 経
  路は削除。新設の Python 側 Hypothesis 方言ファジング（`tests/test_property_dialects.py`、stdlib
  `json`/`tomllib`/`pyjson5` をオラクルとする型厳密比較で発見；JSON5 のベアラ `Infinity`/`NaN` と
  i64 超過の数値文字列という AST 曖昧スペル 2 種も固定）。Rust 回帰：
  `toml::parser::tests::i64_lower_bound_negative_integer_is_accepted`。
- **誤ってインデントされたフロースケンスの続き行が再び拒否される** — YAML パーサを granit-parser 1.3
  へアップグレードすると（*変更*を参照）、続き行のインデントが enclosing block key よりも浅い複数行
  フロアコレクション（yaml-test-suite `9C9N`：`flow: [a,` の次に行頭 column 0 の `b,`）を静かに *受
  理*するようになり、厳密性が `405/406 → 404/406` へ後退した — suite の ≥95% しきい値ゲートには見え
  ないため緑 CI を通過した。AST receiver のパース後 in-tree ガードが enclosing block のインデントを
  追跡し、インデントが足りないフロア続き行を拒否して `405/406` を回復する。ガードはパーサが既に計算
  済みの span のみを使うため、正しくインデントされた複数行フロアは影響を受けない。`9C9N` は
  `tests/test_yaml_suite.py` にケース単位のハードゲート（リテラル入力、`skipif` なし）として固定さ
  れ、加えて Rust ユニットテスト（`parser::tests::flow_continuation_under_indented_is_rejected`）を
  追加。
- **自己参照マージキーがネイティブスタックを溢れさせなくなった** — 展開が自分
  自身のアンカー（`a: &a` に `b: {<<: *a}`）へ戻る `<<` は `resolve_merge_keys` 内で
  無限に展開され、ネイティブスタックを枯渇させてインタプリタプロセス全体を
  落としていた（Windows 終了コード `0xC00000FD`、セグメンテーションフォールト）。
  循環ガードはマージ対の*収集*時のみ適用され、展開の*走査*時には適用されなかった
  ため、再帰的再進入は一度も検出されなかった。アンカーガードは別名展開と同様に
  パススコープ化：アンカー名はその展開が走査されている間パスにとどまり、既にその
  パス上の祖先へ戻るマージは再帰せず空の展開として終端する。非循環 AST は PyYAML の
  循環 dict を持てないため、自己マージはクラッシュせず `{}` に収まる。同じ変更で
  4 つの関連マージセマンティクス欠陥も修正：null / スカラー / 配列のマージソースは
  リテラル `<<` キーとして残らなくなり、マージ値として直接使われるインラインマップ
  （`<<: {x: 1}`）はマージされ、マージ配列内の非別名要素（`<<: [*a, {y: 2}]`）は
  インラインマップを保持する。Rust 6 件・Python 9 件の回帰テストでカバー
  （`merge::tests`、`tests/test_gaps.py::TestSelfReferentialMerge166`）。
  [@bourumir-wyngs](https://github.com/bourumir-wyngs) による #166 の報告。
- **NumPy シリアライズが GIL 無しで Python メモリを読まなくなった** — ndarray ライタは
  `unsafe { as_slice() }` で配列のデータバッファを借用し、その借用スライスを `py.detach` の**内側**
  （＝ GIL 解放後）に反復していた。`&[T]` は出所によらず `Send` なので借用チェッカーは捕捉できない
  が、このメモリは Python 所有であり他スレッドが並行して resize / 書き込みしうる：不健全なデータ競
  合 / UB で、並行時のみ顕在化。バッファは**GIL を保持したまま** Rust 所有メモリへスナップショット
  （`slice.to_vec()`）するようになり、スカラー→ノード変換のみをスレッド外で行う。bindings 層で唯一
  の `unsafe` バッファ借用であり、他の全 `py.detach` Closure は Rust 所有状態（AST、ソーステキス
  ト、`BufWriter<File>`）のみ触及と確認済み。回帰カバレッジは
  `tests/test_numpy.py::TestNumpyConcurrency`。[@bourumir-wyngs](https://github.com/bourumir-wyngs)
  による #165 の報告。
- **繰り返しエイリアス参照が `None` にならないよう修正** — `to_dict()` は**グローバル**
  な visited 集合の後でエイリアスを展開し、クリアすることがなかったため、各アンカーの
  **最初の**参照のみが値になり、それ以降は無言で `None` に劣化していた：
    ```yaml a: &x 1 b: *x      # 1 c: *x      # 従来は None、現在は 1```
    影響範囲は「2 回目の参照」より広く、同一コンテナ内の兄弟参照同士も汚染し合った
    （`{a: &x {p: 1}, b: {q: *x}, c: {q: *x}}` で `b` は値、`c` は `None`）。この guard を現在の再帰
    パスに限定し、1 回の展開中のみ push してその後 pop するようになったため、繰り返し参照と兄弟参照
    はそれぞれ完全に構築された値を得、真の循環は依然として終了する。`<<` マージ解決と AST 自体は影
    響を受けないことを確認済み。`tests/test_direct_load.py` に PyYAML との一致を固定する 6 例を追加
    し、誤った出力を期待値として固定していた 2 テストを書き直した。
    [@bourumir-wyngs](https://github.com/bourumir-wyngs) による #163 の報告。
- **第一キーの値がネストコンテナの場合のドキュメントヘッダーコメント消失を修正** —
  パーサーは進行中の全コンテナで単一のコメントスロットを共有しており、ネスト
  コンテナの start が未配置の standalone ヘッダーを消していた（parse 段階で
  破棄、`to_dict` では見えず `dump` で顕在化）。コンテナごとのスタック管理に変更。
- **splice 編集での先頭コメント重複を修正** — 再生成されたリージョンテキストが
  pair/item 自身の standalone コメントを含む場合、置換範囲が旧コメント行を
  覆わず両方が残っていた。plan がコメント行へ範囲を拡張（`pyq set`/`delete`
  と bindings の splice 経路が共通で修正）。
- **`!timestamp` がサポート全 Python で末尾 `Z` を受理** — `datetime.fromisoformat` は UTC-`Z` 接尾
  辞を 3.11 以降でしか認識せず、プラグインで `...Z` を `+00:00` に正規化し、3.8～3.10 における YAML
  `!timestamp` スカラーおよび `load_toml` / `from_toml` 経由の TOML datetime の
  `Invalid isoformat string` を解消。

#### パフォーマンス

- **イベントストリーム→Python オブジェクトの直接構築** — `safe_load`、`safe_loads`、
  `YAML().safe_load*` は完全な AST を構築してから `convert.rs` で再走査する代わりに、granit イベント

  `parse_all_docs` −9.7%、`safe_loads`（マルチドキュメント）−9.5%、`YAML().safe_loads` −6.7%。
- **ストリーミング書き込みは文書間で単一バッファを再利用** — 新しい `direct_dump_into` は各文書を再
  利用の `String` へ書き込み、`dump_iterable` はテキストが改行 1 つで終わる通常ケースで
  `normalize_doc` の再コピーをスキップ。WSL 実測: `dump_stream_multi_doc` −27.2%、`dump_stream`
  −4.4%。
- **AST ビルダのスカラ高速パス** — `unescape_double_quoted` はバックスラッシュなしでは
  即返答、`detect_chomping` はブロックスカラ毎に全文行を collect せず遅延取得。
  WSL 実測: `to_dict` 系 −4〜9%、スカラ型ロード −3〜4%、退行なし。
